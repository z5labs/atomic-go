# Atomic RPC API

This reference describes the Atomic RPC API as defined and implemented by libatomic at commit [`a6c3e359456e83cf5a967a2e8265f11e0ba45d80`](https://github.com/atomicdotdev/atomic/commit/a6c3e359456e83cf5a967a2e8265f11e0ba45d80). Every citation in these pages is a permalink pinned to that commit, so moving the reference to a newer libatomic means re-checking every citation against the new source, not only updating the links.

The pages keep the contract and the implementation apart. The `.proto` files are the contract; the handlers in `libatomic/src/daemon/` decide what actually happens. Where the two differ, each page states the handler's behaviour and lists the difference under its "Open questions".

## Overview

### What the API serves

The API is one protobuf contract, package `atomic` ([`common.proto#L38`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/atomic/common/common.proto#L38)), that `atomicd` serves to both a local daemon and a hosted server, over a Unix-domain socket, named pipe, TLS or iroh; there is no second protocol ([`README.md#L3-L4`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/README.md?plain=1#L3-L4)). libatomic owns the contract with its code generation and the handlers that implement it. One implementation has two callers: the `atomicd` transport serves the handlers over a socket, and the CLI's local service mode calls the same handlers in-process ([`lib.rs#L1-L20`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/lib.rs#L1-L20)). The transport itself (socket bind, single-instance lock, tonic `Server` wiring and the `atomicd` binary) is not in libatomic ([`lib.rs#L22-L24`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/lib.rs#L22-L24)), so anything decided only there, such as authentication middleware and version-header checks, is outside this reference; see [transport.md](transport.md).

One daemon state serves many repositories. Each resolved root is registered under its ID and opened lazily; each RPC takes the repository's serialization gate, opens the database, runs and drops the handle ([`mod.rs#L9-L15`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/mod.rs#L9-L15)).

### What this API does not cover

This is the contract between a client and `atomicd`. It is not the protocol a client uses to reach a hosted Atomic server.

- Push and pull to a remote don't travel over this contract. The daemon's [PushChanges](services/sync.md#pushchanges) and [PullChanges](services/sync.md#pullchanges) handlers are themselves HTTP clients of the remote. Each builds an `atomic_remote::HttpRemote` for the remote URL ([`services_sync_remote.rs#L500-L505`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L500-L505), [`services_sync_remote.rs#L1189-L1192`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1189-L1192)), and adds the request's `auth_headers` to it as HTTP headers ([`services_sync_remote.rs#L141-L155`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L141-L155)).
- libatomic does not serve this contract to remote callers. The transport shell (socket bind, tonic `Server` wiring, the `atomicd` binary) lives outside it ([`lib.rs#L22-L24`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/lib.rs#L22-L24)). No libatomic handler validates a remote caller's bearer token. Handlers only check whether one is present ([`sandbox_grants.rs#L588`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/sandbox_grants.rs#L588), [`compact.rs#L22-L33`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_maintenance/compact.rs#L22-L33)). See [Authentication and authorization](transport.md#authentication-and-authorization).
- A remote client that writes a change ([SubmitChange](services/sandbox.md#submitchange)) sends V3 change-file bytes. libatomic treats them as opaque, because the contract says their encoding is owned elsewhere ([`common.proto#L125-L129`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/atomic/common/common.proto#L125-L129)). See [the V3 change-file format](#the-v3-change-file-format) under Open questions.

The hosted server's HTTP protocol and the V3 change-file format are documented separately; see [#6](https://github.com/z5labs/atomic-go/issues/6).

### Concepts a client meets everywhere

**Repository references.** Every repository-scoped request names one repository with a [RepositoryRef](types.md#repositoryref) ([`common.proto#L50-L66`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/atomic/common/common.proto#L50-L66)). A local client gets one from [ResolveRepository](services/daemon.md#resolverepository), which walks the path to the repository root and registers it ([`services.rs#L249-L251`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services.rs#L249-L251)). libatomic accepts only authority `"local"`, and an ID that this daemon state has not registered fails with `ERROR_CODE_REPOSITORY_NOT_FOUND` and the hint "resolve it by path first", with no filesystem fallback ([`state.rs#L329-L348`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/state.rs#L329-L348)). The ID is a BLAKE3 digest of the canonical root path, which the code calls a slice limitation against IDs assigned at init ([`state.rs#L66-L75`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/state.rs#L66-L75)). A client should therefore resolve again after a daemon restart, or when it switches to another `LocalService` instance; see [Repository resolution](transport.md#repository-resolution).

**Views, snapshots and fences.** A [ViewRef](types.md#viewref) names a view; the contract calls `view_id` a stable opaque identity ([`common.proto#L68-L74`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/atomic/common/common.proto#L68-L74)), but the handlers issue it as the BLAKE3 digest of the view name ([`sandbox_grants.rs#L558-L561`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/sandbox_grants.rs#L558-L561)). A [ViewSnapshot](types.md#viewsnapshot) is a server-derived digest of a view's effective state that callers echo back and never construct ([`common.proto#L76-L85`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/atomic/common/common.proto#L76-L85)). Mutations that accept a snapshot or an [ExpectedState](types.md#expectedstate) use it as a fence, but libatomic has three different fence implementations, and many handlers do not read their fence fields at all; [ViewSnapshot](types.md#viewsnapshot) describes which method fences on what. A stale fence fails with `ERROR_CODE_VIEW_STALE`, which travels as gRPC `FAILED_PRECONDITION` ([`services.rs#L1250-L1255`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services.rs#L1250-L1255), [`state.rs#L435-L439`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/state.rs#L435-L439)). When a request omits the view, handlers fall back to "the current view", but they read it from different places: the `.atomic/current_view` marker, defaulting to `dev` ([`state.rs#L77-L85`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/state.rs#L77-L85)), the opened repository's current view ([`services_query.rs#L346-L349`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_query.rs#L346-L349)), or the working copy's registered view, as KnowledgeService's `query_view_name` does ([`services_agent.rs#L3737-L3749`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L3737-L3749)).

**RequestMeta and ResponseMeta.** The contract makes every mutation carry a UUID v4 `request_id` that the server echoes, replays and checks for reuse with different contents ([`common.proto#L8-L17`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/atomic/common/common.proto#L8-L17); [`CONTRACT.md#L54-L59`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/CONTRACT.md?plain=1#L54-L59)), and `ResponseMeta` sits at field 100 of successful mutation responses ([`common.proto#L111-L117`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/atomic/common/common.proto#L111-L117)). libatomic implements no replay. The shared helper copies `request_id` with `replayed: false` and no snapshot, and returns no `ResponseMeta` when the request had no `RequestMeta` ([`services_agent.rs#L1233-L1239`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L1233-L1239)). The one `ResponseMeta` that carries a snapshot is `SubmitChange`'s after an accepted submission ([`services_sandbox.rs#L839-L843`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sandbox.rs#L839-L843)). Send a fresh `request_id` per logical mutation, but treat a resent mutation as a new request; see [Request metadata and idempotency](transport.md#request-metadata-and-idempotency).

**Method options and capabilities.** Every rpc declares four options: execution scope, allowed callers, required capabilities and effects ([`options.proto#L57-L70`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/atomic/common/options.proto#L57-L70)). The contract treats them as four independent checks that fail closed, and says the advertised method matrix comes from the descriptors ([`CONTRACT.md#L13-L24`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/CONTRACT.md?plain=1#L13-L24)). libatomic's handlers check capabilities only against sandbox grants ([`sandbox_grants.rs#L495-L504`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/sandbox_grants.rs#L495-L504)), and treat a request with neither a host-attached grant nor a sandbox token as a local, trusted caller ([`sandbox_grants.rs#L9-L20`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/sandbox_grants.rs#L9-L20)). [GetCapabilities](services/daemon.md#getcapabilities) advertises a hard-coded list of 58 methods ([`services.rs#L60-L119`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services.rs#L60-L119)). Six of them, CompactDatabase, ReplayVaultEvidence, GetProjectIdentity, GetWorkflowSnapshot, AppendHookLog and LoadHookLog, carry their declared options ([`services.rs#L149`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services.rs#L149), [`services.rs#L158`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services.rs#L158), [`services.rs#L167-L168`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services.rs#L167-L168), [`services.rs#L183-L184`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services.rs#L183-L184)); every other entry has scope `BOTH` and empty capability, caller and effect lists ([`services.rs#L204-L212`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services.rs#L204-L212)). Read a method's options from the [descriptor set](transport.md#descriptor-set) or from its page, not from that matrix. See [method options](types.md#method-options).

**Contract version and feature tokens.** The contract revision is 2 ([`common.proto#L42-L48`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/atomic/common/common.proto#L42-L48)), and `GetCapabilities` returns `protocol_version: 2` with the feature tokens that gate add-only request fields ([`services.rs#L216-L225`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services.rs#L216-L225)). The contract requires `x-atomic-contract-version: 2` on every call after negotiation ([`CONTRACT.md#L34-L38`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/CONTRACT.md?plain=1#L34-L38)); libatomic does not check it, but a client should send it. See [Version negotiation](transport.md#version-negotiation).

**Serialization.** Each registered repository has one async mutex. Gated handlers are fully serialized per repository, reads included; the code calls the read/write split future work ([`state.rs#L35-L58`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/state.rs#L35-L58)). A few reads skip the gate, for example [ResolveRepository](services/daemon.md#resolverepository) ([`services.rs#L253-L256`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services.rs#L253-L256)), [ListRemotes](services/sync.md#listremotes) ([`services_sync.rs#L52-L58`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync.rs#L52-L58)) and [CheckRepository](services/maintenance.md#checkrepository) ([`services_maintenance.rs#L205-L215`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_maintenance.rs#L205-L215)). A long gated call delays every other gated call on that repository: for example, `PushChanges` takes the gate at the start of the call ([`services_sync_remote.rs#L433-L434`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L433-L434)) and still holds it while it uploads to the remote ([`services_sync_remote.rs#L864`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L864)).

## How a client talks to the API

[transport.md](transport.md) covers the connection. The API is standard gRPC with protobuf messages generated by tonic from the `.proto` files ([`build.rs#L42-L45`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/build.rs#L42-L45)); a method's path is `/atomic.<Service>/<Method>` ([`local.rs#L65-L66`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/local.rs#L65-L66), [`local.rs#L92`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/local.rs#L92)). libatomic also exports the compiled contract as a `FileDescriptorSet`, from which bindings can generate their types without `protoc` ([`lib.rs#L46-L50`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/lib.rs#L46-L50); [`build.rs#L36-L39`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/build.rs#L36-L39)); the method options are extensions of `MethodOptions` ([`options.proto#L57-L70`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/atomic/common/options.proto#L57-L70)), so the descriptor carries them too. A client calls [GetCapabilities](services/daemon.md#getcapabilities) first, checks the contract version, resolves its repository with [ResolveRepository](services/daemon.md#resolverepository), and passes the returned `RepositoryRef` on every repository-scoped call. Trusted local Rust applications can instead call the handlers in-process through `LocalService`, which routes 23 methods and returns `UNIMPLEMENTED` for the rest ([`local.rs#L358-L360`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/local.rs#L358-L360)); see [In-process LocalService](transport.md#in-process-localservice).

[errors.md](errors.md) covers failures. Most handler errors are a gRPC status whose message starts with `atomic:<NAME>: `, where `<NAME>` is the [ErrorCode](errors.md#errorcode) without its prefix; the `ErrorInfo` the helper builds is not attached ([`state.rs#L423-L452`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/state.rs#L423-L452)). Only `CompactDatabase` attaches an encoded `ErrorInfo` as the status details ([`compact.rs#L189-L204`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_maintenance/compact.rs#L189-L204)). Domain refusals that carry recovery data arrive inside a successful response as a `oneof` outcome instead ([`error.proto#L15-L19`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/atomic/common/error.proto#L15-L19)). See [How handlers produce errors](errors.md#how-handlers-produce-errors).

Status is the handler's state at this commit: implemented, partial (the handler runs but ignores or narrows part of the contract), not implemented (the handler returns `UNIMPLEMENTED`) or no handler. Each method's page section gives the details.

Each method's request table has a Required column, with these values:

- **Required**: the call needs the field. The handler refuses the request or panics without it, or libatomic's code shows that the call depends on it, as with a generation fence or a lookup key whose miss returns an error or no result.
- **Optional**: the handler accepts the field's absence; the row gives the default or the effect.
- **Ignored**: no handler code reads the field, whatever the contract says about it.
- **Contract only**: the method, or the branch of it that reads the field, has no working handler at this commit (there is no handler, or it refuses that branch, for example with `UNIMPLEMENTED`), so the row gives the contract's description.
- **Unconfirmed**: the handler does not check whether the field is empty or zero, and libatomic does not show how the code it passes the field to treats such a value; that is decided in another workspace crate. It does not mean the field may be left out: send the value the row describes. The page's Open questions say what could not be confirmed.

## Open questions

These questions cut across services. Each page's own list follows.

- <a id="the-v3-change-file-format"></a>**The V3 change-file format.** Changes cross the API as V3 change-file bytes, schema `atomic.change.v3`, in a [ChangeBundle](types.md#changebundle) ([`sandbox_wire.rs#L23-L24`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/sandbox_wire.rs#L23-L24)). SubmitChange takes them, and GetChanges returns them. The contract says their encoding is owned elsewhere ([`common.proto#L125-L129`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/atomic/common/common.proto#L125-L129)). On input, libatomic checks only the schema and the hash's shape before it passes the bytes on ([`sandbox_wire.rs#L316-L328`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/sandbox_wire.rs#L316-L328)). The byte layout and how the change hash is computed are decided outside libatomic, so this reference cannot document them. A client that only relays bytes it received can work from this reference. A client that writes new changes cannot.
- **What the transport shell enforces.** The contract puts version checks, credential checks, method allowlists and caller-class checks before dispatch ([`CONTRACT.md#L34-L51`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/CONTRACT.md?plain=1#L34-L51)), but libatomic contains no transport ([`lib.rs#L22-L24`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/lib.rs#L22-L24)) and its handlers trust any request without a sandbox credential ([`sandbox_grants.rs#L19-L20`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/sandbox_grants.rs#L19-L20)). Which of these checks `atomicd` performs, and with which status codes, cannot be confirmed from libatomic. See [Authentication and authorization](transport.md#authentication-and-authorization).
- **Handlers that panic on a missing repository.** Many handlers call `unwrap()` on `request.repository`, for example GetChange ([`services_query.rs#L314`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_query.rs#L314)), CreateTag ([`services_tag.rs#L76`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_tag.rs#L76)), ListRemotes ([`services_sync.rs#L53`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync.rs#L53)), CreateVaultEntity ([`services_agent.rs#L1262`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L1262)) and ReserveTurn ([`services_provenance.rs#L430`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_provenance.rs#L430)); each page lists its own. Others substitute an empty reference, which `resolve` refuses with `INVALID_ARGUMENT` ([`services.rs#L1138-L1144`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services.rs#L1138-L1144); [`state.rs#L332-L340`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/state.rs#L332-L340)), and `CompactDatabase` checks explicitly ([`compact.rs#L56-L59`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_maintenance/compact.rs#L56-L59)). Only `LocalService` rejects a missing reference before dispatch for every method it routes ([`local.rs#L435-L440`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/local.rs#L435-L440)). What a gRPC client receives when a handler panics depends on the transport. A client should always send `repository` on repository-scoped calls.
- **Idempotency.** The contract requires replay and `IDEMPOTENCY_MISMATCH` ([`CONTRACT.md#L54-L59`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/CONTRACT.md?plain=1#L54-L59)); no handler implements either ([`services_agent.rs#L1233-L1239`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L1233-L1239)). Whether the transport will add replay, or the handlers will, is not stated.
- **The advertised method matrix.** `GetCapabilities` advertises 58 of 105 rpcs ([`services.rs#L60-L119`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services.rs#L60-L119)), all but six of them with scope `BOTH` and empty lists ([`services.rs#L204-L212`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services.rs#L204-L212)), although the contract says the matrix comes from the descriptors and missing annotations fail closed ([`CONTRACT.md#L22-L24`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/CONTRACT.md?plain=1#L22-L24)). Several unadvertised methods have handlers, and some are routed by `LocalService`, for example `GetChange` ([`local.rs#L228-L237`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/local.rs#L228-L237)). Whether a client may call a method the endpoint does not advertise is not stated.
- **Error details.** `domain_status` builds an `ErrorInfo` and drops it, carrying the code only in the message prefix until "rich grpc-status-details-bin attachments land" ([`state.rs#L423-L431`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/state.rs#L423-L431), [`state.rs#L447-L452`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/state.rs#L447-L452)), while `CompactDatabase` already attaches a bare `ErrorInfo` ([`compact.rs#L203`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_maintenance/compact.rs#L203)). A client must parse both shapes, and either may change. See [errors.md](errors.md#open-questions).
- **View identity.** The contract says authorization uses `view_id` and recreating a name never revives a grant ([`common.proto#L68-L70`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/atomic/common/common.proto#L68-L70)); the wire `view_id` is the BLAKE3 digest of the name ([`sandbox_grants.rs#L558-L561`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/sandbox_grants.rs#L558-L561)), so a recreated view has the same `view_id`. Sandbox grants guard against revival with an internal view ID that is not on the wire ([`services_sandbox.rs#L143-L168`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sandbox.rs#L143-L168)). Provenance session and turn ownership does not use that ID: it is keyed by view name ([`sandbox_grants.rs#L309-L318`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/sandbox_grants.rs#L309-L318), [`sandbox_grants.rs#L346-L348`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/sandbox_grants.rs#L346-L348)), so a grant for a recreated view inherits the old view's sessions; see [ProvenanceService](services/provenance.md#open-questions). Whether clients may rely on name-derived IDs is not stated.
- **Fences.** The contract says the own Merkle state is diagnostic and not enough to fence, and that view-dependent mutations require a matching snapshot ([`CONTRACT.md#L312-L316`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/CONTRACT.md?plain=1#L312-L316)). The Record and InsertChanges fences prefer `own_merkle` when it is present ([`services.rs#L1187-L1190`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services.rs#L1187-L1190), [`services.rs#L1256-L1264`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services.rs#L1256-L1264)), both accept an absent fence, and many mutations do not read their fence fields. The doc comment on the shared fence says the vault writes use it ([`services.rs#L1228-L1230`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services.rs#L1228-L1230)), but only InsertChanges calls it ([`services.rs#L2285`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services.rs#L2285), [`services.rs#L2308`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services.rs#L2308)). See [ViewSnapshot](types.md#viewsnapshot).
- **Host working-copy refresh.** `CONTRACT.md` says InsertChanges, Unrecord and PullChanges do not refresh host files ([`CONTRACT.md#L335-L336`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/CONTRACT.md?plain=1#L335-L336)). InsertChanges rematerializes the working copy when the target is the checked-out view ([`services.rs#L2599-L2628`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services.rs#L2599-L2628)), and PullChanges does so when it pulls the current view ([`services_sync_remote.rs#L1632-L1657`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1632-L1657)). Which behaviour is intended is not stated; see [InsertChanges](services/repository-mutation.md#insertchanges) and [PullChanges](services/sync.md#pullchanges).
- **Generation fencing codes.** `PublishProvenance` reports a generation mismatch as `ERROR_CODE_GENERATION_CONFLICT` ([`services_sandbox.rs#L713-L720`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sandbox.rs#L713-L720)), the only producer of that code, while the provenance journal surfaces the store's fencing error text verbatim ([`provenance_core.rs#L11-L12`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/provenance_core.rs#L11-L12)) inside a `JournalError` that carries the journal's own store-classified code ([`provenance_core.rs#L70-L74`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/provenance_core.rs#L70-L74)); see [generation fencing](services/provenance.md#generation-fencing). A client cannot rely on one code for a stale generation.
- **Which view is "current".** The three sources listed under [Concepts](#concepts-a-client-meets-everywhere) ([`state.rs#L77-L85`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/state.rs#L77-L85), [`services_query.rs#L346-L349`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_query.rs#L346-L349), [`services_agent.rs#L3741-L3749`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L3741-L3749)) need not agree; a libatomic test sets the marker to another view and calls it non-authoritative ([`query_view_service_test.rs#L56-L57`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/tests/query_view_service_test.rs#L56-L57)). libatomic does not say which source a client should treat as authoritative when it omits the view.
- **Reads that serialize or open for writing.** The shared rules say reads run as concurrent read transactions ([`common.proto#L30-L32`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/atomic/common/common.proto#L30-L32)) and the proto README says read-only operations never enter the write queue ([`README.md#L114-L119`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/README.md?plain=1#L114-L119)), but the gate serializes every gated call, reads included ([`state.rs#L35-L40`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/state.rs#L35-L40)). Several read methods also open the repository through the writable path, for example [ListStashes](services/repository-mutation.md#liststashes), declared with read effects only ([`repository_mutation_service.proto#L107-L113`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/atomic/services/repository_mutation/repository_mutation_service.proto#L107-L113)) but opened with `repository()` under the gate ([`services.rs#L2862-L2865`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services.rs#L2862-L2865)); the method pages list the others.
- **Ambient host state.** Some handlers depend on the serving process's environment rather than the request: the attestation handlers open the serving process's default identity store ([`services_agent.rs#L2984-L2996`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L2984-L2996)), and so does ListVaultEntries to compute its verification column ([`services_agent.rs#L1015-L1031`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L1015-L1031)); `ExplainTurns` runs a Claude CLI subprocess ([`provenance_service.proto#L194`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/atomic/services/provenance/provenance_service.proto#L194)), and database open waits honour `ATOMIC_DB_LOCK_WAIT_MS` ([`state.rs#L26-L33`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/state.rs#L26-L33)). A remote client cannot select or observe this state.
- **Sandbox principals on unscoped methods.** The sandbox allowlist includes Vault, Knowledge and Attestation methods and the provenance session reads, but their handlers do not enforce the grant's scope, and libatomic tells hosts to refuse sandbox principals outside `SANDBOX_SCOPED_METHODS` ([`sandbox_grants.rs#L105-L127`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/sandbox_grants.rs#L105-L127)). Whether `atomicd` does so is decided outside libatomic.
- **Workspaces.** `RepositoryRef.workspace_id` is described as required for working-copy operations ([`common.proto#L65`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/atomic/common/common.proto#L65)), but every reference libatomic issues omits it ([`state.rs#L87-L93`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/state.rs#L87-L93)), `resolve` ignores it ([`state.rs#L331-L348`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/state.rs#L331-L348)), and nothing produces `ERROR_CODE_WORKSPACE_REQUIRED`.
- **Stale counts in libatomic's own documents.** The service protos declare 105 rpcs; `proto/README.md` says 94 ([`README.md#L43`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/README.md?plain=1#L43)) and the crate documentation 97 ([`lib.rs#L7-L8`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/lib.rs#L7-L8)). `COVERAGE.md`'s tables also omit methods, for example five ProvenanceService rpcs ([`COVERAGE.md#L31`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/COVERAGE.md?plain=1#L31)).
