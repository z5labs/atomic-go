# VaultService

VaultService is the RPC surface of the `.vault/` knowledge store: intents, memories and goals, vault sync, and the agent context pack [`vault_messages.proto#L1-L2`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/atomic/services/vault/vault_messages.proto#L1-L2). Intents, memories and goals are one entity model selected by a kind enum, not three RPC families [`vault_messages.proto#L4-L17`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/atomic/services/vault/vault_messages.proto#L4-L17). Both proto files are marked `DRAFT — add-only` [`vault_service.proto#L1-L3`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/atomic/services/vault/vault_service.proto#L1-L3) [`vault_messages.proto#L4`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/atomic/services/vault/vault_messages.proto#L4). The handlers are the `VaultImpl` implementation of the generated `VaultService` trait in `services_agent.rs` [`services_agent.rs#L654-L656`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L654-L656) [`services_agent.rs#L1253-L1254`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L1253-L1254).

## Behaviour common to every method

**The vault is repository-wide, not view-scoped.** The contract says every request names its view, reads see that view's effective vault, and edits to inherited entities create target-local versions [`vault_messages.proto#L23-L31`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/atomic/services/vault/vault_messages.proto#L23-L31); CONTRACT.md makes the same obligations normative and adds that direct RPC writes return the new ViewSnapshot in ResponseMeta [`CONTRACT.md#L193-L206`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/CONTRACT.md?plain=1#L193-L206). The handlers do not implement this. GetVaultEntry, ListVaultEntries and GetVaultContext reject any request that sets `view` with `UNIMPLEMENTED`, because "vault storage is currently repository-wide" [`services_agent.rs#L658-L667`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L658-L667). No write handler reads `view`, `expected_snapshot` or `expected`, and no response sets a `ViewSnapshot`. libatomic's README states the same limitation for reads: explicit view requests and continuation cursors fail closed, and responses do not claim a ViewSnapshot [`README.md#L88-L92`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/README.md?plain=1#L88-L92).

**ResponseMeta is an echo, not idempotency.** Every write response builds its `meta` with `response_meta`, which copies `request_id`, sets `replayed = false` and leaves `snapshot` unset; when the request has no `meta`, the response has none [`services_agent.rs#L1233-L1239`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L1233-L1239). No vault handler checks that `request_id` is present or replays a previous outcome, although CONTRACT.md requires a nonempty UUID request ID and replay keyed on it for ordinary mutations [`CONTRACT.md#L54-L58`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/CONTRACT.md?plain=1#L54-L58). A retried write runs again. See [RequestMeta](../types.md#requestmeta) and [ResponseMeta](../types.md#responsemeta).

**Every call is serialized per repository.** Each handler acquires the repository's `exclusive()` gate, a mutex that allows at most one open database handle per repository [`state.rs#L54-L58`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/state.rs#L54-L58), including the read-only methods (for example [`services_agent.rs#L1838-L1839`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L1838-L1839)). ReplayVaultEvidence releases the gate while the external checker runs ([ReplayVaultEvidence](#replayvaultevidence)).

**Writes open the repository writable and create a missing vault.** Write handlers other than InitVault open the repository through `vault_repository`, which opens it writable and calls `ensure_vault`; read handlers open it read-only so a read never initializes the vault [`services_agent.rs#L1241-L1251`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L1241-L1251) [`state.rs#L212-L229`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/state.rs#L212-L229). InitVault opens a workspace transaction instead [`services_agent.rs#L2678-L2679`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L2678-L2679). ExportVault uses the write path even though its proto comment classifies it as a read ([ExportVault](#exportvault)).

**A missing `repository` is not handled uniformly.** GetVaultEntry, ListVaultEntries and GetVaultContext return `INVALID_ARGUMENT` "repository required" (for example [`services_agent.rs#L1832-L1835`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L1832-L1835)). Every other handler calls `request.repository.as_ref().unwrap()` (for example [`services_agent.rs#L1262`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L1262)), which panics when the field is absent; libatomic produces no gRPC status for that case. Through `LocalService`, the routed methods reject a missing reference with `INVALID_ARGUMENT` before the handler runs [`local.rs#L435-L440`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/local.rs#L435-L440).

**Sandbox callers are not scoped by these handlers.** The contract lists VaultService methods in the sandbox allowlist [`sandbox_grants.rs#L64-L69`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/sandbox_grants.rs#L64-L69) [`sandbox_grants.rs#L89-L97`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/sandbox_grants.rs#L89-L97). The subset whose handlers enforce a sandbox grant's view and capabilities contains no VaultService method, and libatomic tells a host to refuse a sandbox principal on every method outside that subset [`sandbox_grants.rs#L105-L127`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/sandbox_grants.rs#L105-L127); a unit test asserts that `CreateVaultEntity` is outside it [`sandbox_grants.rs#L767`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/sandbox_grants.rs#L767). Method options in this page are the contract; who enforces them is described in [authentication and authorization](../transport.md#authentication-and-authorization).

**GetCapabilities does not restate these method options.** For every VaultService row except ReplayVaultEvidence, the advertised descriptor has scope `BOTH` and empty capability, caller and effect lists [`services.rs#L204-L212`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services.rs#L204-L212); only ReplayVaultEvidence is advertised with its proto values [`services.rs#L158-L166`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services.rs#L158-L166). GetCapabilities also lists the feature `vault-memory-create-options-v1` [`services.rs#L216-L225`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services.rs#L216-L225), the gate for CreateVaultEntity's `memory_id` and `memory_status` fields [`services.rs#L121-L122`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services.rs#L121-L122).

### InitVault

`rpc InitVault(InitVaultRequest) returns (InitVaultResponse)`, unary [`vault_service.proto#L13-L21`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/atomic/services/vault/vault_service.proto#L13-L21).

The contract describes it as initializing the authorized view's vault namespace, not host files [`vault_service.proto#L13`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/atomic/services/vault/vault_service.proto#L13). The handler opens a workspace transaction in `Reconcile` mode and returns `already_initialized = true` if the repository already has a vault [`services_agent.rs#L2677-L2683`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L2677-L2683). Otherwise it initializes the vault, adds every file under the vault directory to tracking, and records the `.vault` path as a change titled "Initialize vault" [`services_agent.rs#L2684-L2700`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L2684-L2700).

**Behaviour**

- A failure of the "has a vault" probe is treated as "no vault" and initialization proceeds [`services_agent.rs#L2681`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L2681).
- Tracking errors for individual files are discarded [`services_agent.rs#L1219-L1226`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L1219-L1226), and every recording error yields `recorded = false` rather than an error [`services_agent.rs#L2696-L2700`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L2696-L2700).
- A second call returns `already_initialized = true` without initializing or recording again [`services_agent.rs#L2681-L2683`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L2681-L2683). This, not RequestMeta replay, is what makes a retry harmless.
- CONTRACT.md says InitVault creates view storage and does not scaffold host files [`CONTRACT.md#L203`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/CONTRACT.md?plain=1#L203). **Order and limits**

- `sort` resolution: `UNSPECIFIED` becomes `ID` for intents and `UPDATED` for memories; intents reject `UPDATED` and `ABOUT`, memories reject `TITLE`; any key other than `UNSPECIFIED` on the goal, whole-vault or tool-result listing is rejected [`services_agent.rs#L830-L853`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L830-L853).
- Keys compare `status_label` or `memory_status` for `STATUS`, `manifest_kind` or `memory_kind` for `KIND`, `updated_at_label` newest first for `UPDATED`, fresh, stale, none for `ATTESTED`, and yes, no, na for `VERIFIES`; ties fall back to `id` [`services_agent.rs#L873-L903`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L873-L903).
- In the memory listing's default order (`UPDATED`, not reversed), the list is cut to `max_items` before the per-row attestation work; otherwise every row is computed, sorted, then cut [`services_agent.rs#L2177-L2186`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L2177-L2186) [`services_agent.rs#L2285-L2290`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L2285-L2290).
- After the listing is built, the `status` filter runs and then the final `max_items` cut [`services_agent.rs#L2382-L2390`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L2382-L2390). **Behaviour**

- INTENT: the domain creates the intent, then the handler overwrites its content with the feature or review scaffold (with `{id}` replaced by the new UID) through a forced update, so the daemon writes the same artifact as the CLI [`services_agent.rs#L1290-L1300`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L1290-L1300) [`services_agent.rs#L1301-L1325`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L1301-L1325).
- MEMORY: the handler refuses before writing if the entry exists in the vault database or a file exists on disk, so an existing memory or an untracked user file is never overwritten [`services_agent.rs#L1458-L1466`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L1458-L1466) [`services_agent.rs#L1487-L1494`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L1487-L1494). **Behaviour**

- MEMORY `body` keeps the existing frontmatter, sets `updatedAt` to the server clock, stores the new body bytes exactly as sent and materializes the file [`services_agent.rs#L1662-L1674`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L1662-L1674). CreateVaultEntity instead trims the text and adds a newline [`services_agent.rs#L1448`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L1448).
- `memory_write` stores `content` and `frontmatter_json` at `path` as given, with entry type memory, and materializes it; the handler does not validate `path` or the frontmatter [`services_agent.rs#L1696-L1710`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L1696-L1710).
- `goal_stop` with no `goal` stops the first goal the domain lists as active [`services_agent.rs#L1733-L1746`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L1733-L1746).
- No fencing: `expected` is not read, so concurrent updates are not detected by this RPC [`services_agent.rs#L1575-L1586`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L1575-L1586).
- The proto comment and COVERAGE.md describe goal start, stop and resume as `status` transitions on this RPC [`vault_service.proto#L82-L84`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/atomic/services/vault/vault_service.proto#L82-L84) [`COVERAGE.md#L169`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/COVERAGE.md?plain=1#L169). The `status` member's own comment says the same [`vault_messages.proto#L267-L268`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/atomic/services/vault/vault_messages.proto#L267-L268). In the handler, goal start is [CreateVaultEntity](#createvaultentity) with `kind = GOAL`, stop and resume are the `goal_stop` and `goal_resume` members, and `status` is refused for goals [`services_agent.rs#L1809-L1812`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L1809-L1812).

## Open questions

- **Who enforces the method options.** libatomic contains no server wiring; the transport lives in the reactor crate [`lib.rs#L22-L24`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/lib.rs#L22-L24). Whether atomicd enforces each method's scope, caller class and capabilities cannot be confirmed here. The descriptors GetCapabilities advertises for most vault methods carry scope `BOTH` and no capabilities, callers or effects [`services.rs#L204-L212`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services.rs#L204-L212), which differs from the proto options (for example SyncVault is `LOCAL`-only [`vault_service.proto#L25-L29`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/atomic/services/vault/vault_service.proto#L25-L29)).
- **Sandbox callers.** Nine vault methods are in the sandbox allowlist [`sandbox_grants.rs#L89-L97`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/sandbox_grants.rs#L89-L97), but none is in the set whose handlers enforce a grant, and libatomic says a host should refuse sandbox principals outside that set [`sandbox_grants.rs#L105-L127`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/sandbox_grants.rs#L105-L127). Whether atomicd refuses them, or dispatches them to these unscoped handlers, is decided outside libatomic.
- **Missing `repository` over the daemon transport.** InitVault, SyncVault, ExportVault, CreateVaultEntity, UpdateVaultEntity, DeleteVaultEntity, ValidateVaultEntity, ReplayVaultEvidence and LinkVaultEntities unwrap `repository` (for example [`services_agent.rs#L1262`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L1262) [`services_agent.rs#L2518`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L2518)). What a client receives when the handler panics depends on the transport [`lib.rs#L22-L24`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/lib.rs#L22-L24).
- **View isolation and fencing.** The proto and CONTRACT.md specify view-scoped reads and writes, target-local revisions and tombstones, and a ViewSnapshot in ResponseMeta [`vault_messages.proto#L23-L31`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/atomic/services/vault/vault_messages.proto#L23-L31) [`CONTRACT.md#L193-L203`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/CONTRACT.md?plain=1#L193-L203). The handlers are repository-wide and ignore `view`, `expected_snapshot` and `expected` on writes; README.md says view isolation remains separate work [`README.md#L90-L92`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/README.md?plain=1#L90-L92). No source in libatomic says when this changes.
- **Idempotency.** CONTRACT.md requires a nonempty UUID `request_id` and replay for ordinary mutations [`CONTRACT.md#L54-L58`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/CONTRACT.md?plain=1#L54-L58); `response_meta` only echoes [`services_agent.rs#L1233-L1239`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L1233-L1239). Whether a transport layer adds replay is not visible in libatomic.
- **Empty `id`.** GetVaultEntry, UpdateVaultEntity and DeleteVaultEntity do not check `id` before the domain lookup (for example [`services_agent.rs#L1887`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L1887) [`services_agent.rs#L1628-L1630`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L1628-L1630) [`services_agent.rs#L2867`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L2867)). The result for an empty intent ID is decided in atomic-repository. The same applies to an empty INTENT `title` in CreateVaultEntity [`services_agent.rs#L1290-L1292`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L1290-L1292).
- **InitVault and host files.** CONTRACT.md says InitVault does not scaffold host files [`CONTRACT.md#L203`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/CONTRACT.md?plain=1#L203), and the proto says it initializes the view's namespace, not host files [`vault_service.proto#L13`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/atomic/services/vault/vault_service.proto#L13). The handler tracks and records files it finds under the vault directory on the host [`services_agent.rs#L2686-L2700`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L2686-L2700), which implies `init_vault` creates them; that call is in atomic-repository.
- **ExportVault fields and effects.** `destination` and `kinds` are in the contract [`vault_messages.proto#L214-L215`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/atomic/services/vault/vault_messages.proto#L214-L215) but not read [`services_agent.rs#L2819-L2825`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L2819-L2825); where files are written is decided by the domain's materialize calls. The declared daemon-ledger effect [`vault_service.proto#L71`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/proto/atomic/services/vault/vault_service.proto#L71) has no code in the handler.
- **GetVaultEntry bundle shape.** The `entry` member of `atomic.vault.entry.bundle.v1` is the serde serialization of atomic-core's `VaultEntry` [`services_agent.rs#L814-L817`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L814-L817), defined outside libatomic. Its JSON field names, and the encoding of the tracked attestation's `content` bytes [`services_agent.rs#L917-L923`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_agent.rs#L917-L923), cannot be confirmed from libatomic alone.
