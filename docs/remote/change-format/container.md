# V3 change-file container

A change travels between an Atomic client and a server as one V3 change file: the exact bytes the recording client wrote. A push reads the change file from disk and uploads those bytes unchanged, falling back to re-serializing the change only when no file exists ([`services_sync_remote.rs#L375-L399`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L375-L399)); that fallback can change the bytes' identity ([Identity comes from the original bytes](#identity-comes-from-the-original-bytes)). The push carries each file as a `Change` [ObjectRecord](../endpoints/project.md#objectrecord) keyed by its base32 hash in the [`sync_push`](../endpoints/project.md#sync_push) pack ([`services_sync_remote.rs#L688-L695`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L688-L695); [Building the pack](../flows.md#building-the-pack)). A pull receives change files the same way, in the [`sync_pull`](../endpoints/project.md#sync_pull) pack, and refuses a file whose computed hash differs from its key ([`services_sync_remote.rs#L1011-L1016`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1011-L1016), [`changes.rs#L214-L223`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/repository/changes.rs#L214-L223); [Saving changes](../flows.md#saving-changes)). [`download_change`](../endpoints/project.md#download_change) fetches one file by its hash. This page documents the container: the file header, the hash dedup table, section framing, compression, the trailer, the change hash, the signature, content chunking and versioning. The decompressed payload of each section is documented on [sections.md](sections.md) (HEADER, DEPS, PROVENANCE, SIGNATURE, SPAN, UNHASHED) and [graph.md](graph.md) (GRAPH, SEMANTIC).

The container is implemented in `atomic-core/src/change/format_v3/`. The module describes the format as a replacement for the older bincode-based V1/V2 change format, using postcard encoding and per-section zstd compression ([`mod.rs#L1-L10`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/mod.rs#L1-L10)). "V3" names the format family. The `version` field inside a V3 file is a separate schema number, and its allowed values are 1, 2 and 3; see [Versioning](#versioning).

Where a doc comment and the code disagree, this page documents the code and lists the disagreement under [Open questions](#open-questions). Facts about postcard, zstd, BLAKE3, FastCDC and Ed25519 come from those external crates. This page cites the `Cargo.lock` lines that pin each one.

## File layout

A V3 change file is these regions, in this order, with no padding or alignment between them ([`mod.rs#L16-L41`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/mod.rs#L16-L41)). The reader reads them back to back: the 64-byte header, then the table, then the sections ([`mod.rs#L412-L428`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/reader/mod.rs#L412-L428)), then the trailer ([`sections.rs#L264-L267`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/reader/sections.rs#L264-L267)):

| # | Region | Size | Compressed | In the change hash | Details |
|---|---|---|---|---|---|
| 1 | File header | 64 bytes | No | No | [FileHeader](#fileheader) |
| 2 | Hash dedup table | `hash_table_entries` × 32 bytes | No | Yes | [HashDedupTable](#hashdeduptable) |
| 3 | Sections | Each: a 5-byte [SectionHeader](#sectionheader) (45-byte [ContentChunkHeader](#contentchunkheader) for CONTENT), then `compressed_len` bytes of zstd data | Payload only | Yes, except SIGNATURE and UNHASHED | [Sections](#sections) |
| 4 | Trailer | 32 bytes | No | No (it is the hash) | [Trailer](#trailer) |

All multi-byte integers in the fixed-size structures are little-endian ([`header.rs#L164-L165`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/header.rs#L164-L165)). The structures are written field by field with `to_le_bytes`, not with postcard ([`header.rs#L253-L265`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/header.rs#L253-L265), [`section.rs#L317-L322`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/section.rs#L317-L322), [`section.rs#L412-L420`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/section.rs#L412-L420)). Postcard is used only inside the decompressed section payloads ([Postcard encoding](#postcard-encoding)).

The file carries no section count terminator and no section index. A reader learns how many sections follow from the header's counts and flags ([FileHeader](#fileheader)), reads that many, then reads the 32-byte trailer ([`mod.rs#L427-L428`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/reader/mod.rs#L427-L428), [`sections.rs#L264-L267`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/reader/sections.rs#L264-L267)).

The smallest file Atomic's tests build by hand is 138 bytes: the header, a one-entry table, two empty section frames and the trailer ([`mod.rs#L570-L571`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/mod.rs#L570-L571)). The [worked example](#worked-example-a-version-2-file) walks a real 275-byte file.

## Sections

### Section order and multiplicity

Sections appear in a fixed order. The order follows each type's `ordering()` value, not its type byte: CONTENT (`0x20`) comes after SEMANTIC (`0x30`) ([`section.rs#L254-L266`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/section.rs#L254-L266)). Writers emit this order ([`mod.rs#L10-L14`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/mod.rs#L10-L14), [`change.rs#L461-L540`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L461-L540)). Readers of version 2 and 3 files reject a section whose `ordering()` is lower than the previous section's ([`change.rs#L630-L640`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L630-L640)).

| Order | Type byte | Name | Count in a version 2 or 3 file | Required | Hashed | Frame | Payload Rust type | Serializer | Field-by-field layout |
|---|---|---|---|---|---|---|---|---|---|
| 0 | `0x01` | HEADER | exactly 1 | **Required** | Yes | 5-byte | `ChangeHeaderV2` in versions 2 and 3; `ChangeHeader` in version 1 | postcard | [HEADER section](sections.md#header-section) |
| 1 | `0x02` | DEPS | exactly 1, possibly an empty list | **Required** | Yes | 5-byte | `Vec<u16>` of [hash indices](#hashindex) | postcard | [DEPS section](sections.md#deps-section) |
| 2 | `0x03` | PROVENANCE | 1 if `HAS_PROVENANCE`, else 0 | **Optional** | Yes | 5-byte | `Vec<Provenance>` | postcard | [PROVENANCE section](sections.md#provenance-section) |
| 3 | `0x04` | SIGNATURE | 1 if `HAS_SIGNATURE`, else 0 | **Optional** | **No** | 5-byte | `ChangeSignature` | postcard | [ChangeSignature](sections.md#changesignature); see also [Signing](#signing) |
| 4 | `0x10` | GRAPH | `graph_section_count` | **Optional** | Yes | 5-byte | `GraphSectionPayload` | postcard | [GraphSectionPayload](graph.md#graphsectionpayload) |
| 5 | `0x11` | SPAN | exactly 1 in version 3, none in version 2 | **Required** in version 3 | Yes | 5-byte | `SpanPatch` (`SpanPatchV1` when its version byte is 1) | the 4 bytes `ATSP`, then postcard | [SPAN section](sections.md#span-section) |
| 6 | `0x30` | SEMANTIC | `semantic_section_count` | **Optional** | Yes | 5-byte | `Vec<FileOps>` | postcard | [SEMANTIC section](graph.md#semantic-section) |
| 7 | `0x20` | CONTENT | `contents_chunks` | **Optional** | Yes | 45-byte | none: raw bytes, one chunk of the content blob | none | [Content chunking](#content-chunking) |
| 8 | `0xF0` | UNHASHED | 1 if `HAS_UNHASHED`, else 0 | **Optional** | **No** | 5-byte | `serde_json::Value` | JSON (`serde_json::to_vec`) | [UNHASHED section](sections.md#unhashed-section) |

In every row, the serialized payload is then compressed with zstd ([Compression](#compression)), and the frame's `compressed_len` counts the compressed bytes.

The `SectionType` comments give HEADER as `postcard(ChangeHeader)` and SEMANTIC as a per-file `postcard(SemanticSection)` ([`section.rs#L49-L52`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/section.rs#L49-L52), [`section.rs#L97-L107`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/section.rs#L97-L107)), and the payload module's table gives SEMANTIC as `SemanticSectionPayload` ([`sections.rs#L10-L13`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/sections.rs#L10-L13)). The format allows many GRAPH and SEMANTIC sections, one per modified file ([`section.rs#L76-L83`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/section.rs#L76-L83)). The current writer emits at most one of each: one GRAPH section if the change has any graph operations, and one SEMANTIC section if it has any file operations ([`change.rs#L426-L436`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L426-L436)). A reader concatenates the operations of every GRAPH section, and of every SEMANTIC section, in file order ([`change.rs#L695-L707`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L695-L707), [`change.rs#L725-L730`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L725-L730)).

Any type byte outside the table fails with `InvalidSectionType` ([`section.rs#L153`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/section.rs#L153)). A test checks that `0x00`, `0x0F`, `0x12`, `0x21`, `0x31` and `0xFF` are refused ([`tests.rs#L223-L230`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/tests.rs#L223-L230)). The reader decides the frame length from the type byte ([`sections.rs#L43-L46`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/reader/sections.rs#L43-L46)), so a section of an unknown type cannot be skipped.

### Compression

Every section payload, including CONTENT and UNHASHED, is compressed with zstd before it is framed. Typed payloads are serialized with postcard, then compressed with `zstd::encode_all` at the writer's level ([`helpers.rs#L98-L103`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/helpers.rs#L98-L103)). Pre-serialized payloads (HEADER, GRAPH, SPAN, SEMANTIC) take the same path ([`helpers.rs#L133-L140`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/helpers.rs#L133-L140)), and so do CONTENT chunks and UNHASHED ([`sections.rs#L137-L139`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/sections.rs#L137-L139), [`sections.rs#L207-L209`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/sections.rs#L207-L209)).

- **Level.** The default is 3 ([`options.rs#L7-L12`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/options.rs#L7-L12)). A custom level is clamped to 1 to 22, and presets exist for 1 and 19 ([`options.rs#L61-L84`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/options.rs#L61-L84)). `Change::serialize` always uses the default ([`change.rs#L462`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L462)). The level is not recorded in the file.
- **Library.** The `zstd` crate is 0.14.3 over `zstd-sys` 2.1.2, which bundles libzstd 1.5.7 ([`Cargo.lock#L5652-L5653`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.lock#L5652-L5653), [`Cargo.lock#L5670-L5671`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.lock#L5670-L5671)). This is external. The frame format is [RFC 8878](https://www.rfc-editor.org/rfc/rfc8878) and, for that library version, [zstd_compression_format.md at v1.5.7](https://github.com/facebook/zstd/blob/v1.5.7/doc/zstd_compression_format.md).
- **Frames in practice.** Every payload in the three full-file fixtures is a single zstd frame. Each begins `28 b5 2f fd` (the zstd magic), then frame header descriptor `00` (no content size field, no checksum, no dictionary), then window descriptor `58`, then one block ([`span_opaque_v2_reference.hex#L2-L4`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/fixtures/span_opaque_v2_reference.hex#L2-L4), [`atomic_0_19_1_file_add.hex#L4-L23`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/fixtures/atomic_0_19_1_file_add.hex#L4-L23), [`cb_fmt1_legacy_v1_object.hex#L1`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/fixtures/cb_fmt1_legacy_v1_object.hex#L1)). Small payloads are stored as raw blocks, so their bytes are readable in the hex. This describes the files, not a rule: a reader must accept any valid zstd data.
- **Decoding.** The reader decompresses with `zstd::decode_all`. A section whose `compressed_len` is 0 yields an empty payload without invoking zstd ([`sections.rs#L131-L136`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/reader/sections.rs#L131-L136)). A decoding failure is `FormatError::Decompress` ([`sections.rs#L135`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/reader/sections.rs#L135)). `zstd::decode_all` decodes every frame in its input and concatenates the output: its decoder starts a new frame whenever input remains after one ends (external: zstd 0.14.3, [`functions.rs#L49-L66`](https://github.com/gyscos/zstd-rs/blob/75bc74045a2f6ea0439aeed7e159a266da20aac0/src/stream/functions.rs#L49-L66), [`reader.rs#L39-L48`](https://github.com/gyscos/zstd-rs/blob/75bc74045a2f6ea0439aeed7e159a266da20aac0/src/stream/zio/reader.rs#L39-L48), [`reader.rs#L272-L292`](https://github.com/gyscos/zstd-rs/blob/75bc74045a2f6ea0439aeed7e159a266da20aac0/src/stream/zio/reader.rs#L272-L292)). So Atomic's reader accepts a payload made of several zstd frames. Atomic's writer compresses each payload with one `zstd::encode_all` call ([`helpers.rs#L98-L103`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/helpers.rs#L98-L103)), which writes one frame (external: [`functions.rs#L94-L98`](https://github.com/gyscos/zstd-rs/blob/75bc74045a2f6ea0439aeed7e159a266da20aac0/src/stream/functions.rs#L94-L98)).
- **Checksums.** Sections carry no checksum of their own. Integrity comes from the trailer hash ([Change hash](#change-hash)) and, for CONTENT, an unverified `chunk_hash` ([Content chunking](#content-chunking)).

The compressed bytes are what the change hash covers. A different compression level, or a different zstd implementation, gives different bytes and so a different change hash. A reader test's comment says so for compression levels ([`tests.rs#L809-L815`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/reader/tests.rs#L809-L815)).

This compression is inside the file. It is unrelated to any HTTP `Content-Encoding`; see [Compression](../transport.md#compression).

## Postcard encoding

Section payloads other than CONTENT (raw bytes) and UNHASHED (JSON) are postcard-encoded serde values ([`mod.rs#L100-L104`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/reader/mod.rs#L100-L104)). Postcard is an external crate, version 1.1.3 ([`Cargo.lock#L2938-L2939`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.lock#L2938-L2939)), used without its default features ([`Cargo.toml#L66`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.toml#L66)). Its wire format is specified in [postcard's wire-format.md at the published commit](https://github.com/jamesmunns/postcard/blob/718aa6a6850456017c19eeff67303c633f875736/spec/src/wire-format.md). Postcard writes no type tags, field names or field counts, so a Go decoder must know the exact Rust type, field order and variant order of every payload. The payload pages give those types; this section gives the encoding rules they rely on.

| Construct | Encoding | Shown in Atomic by |

| map | Varint pair count, then key and value for each pair. | Not shown in Atomic's tests. |

Serde attributes change these rules. These are the ones that matter for change payloads:

- **`#[serde(with = ...)]` replaces the encoding.** `ChangeSignature.signature: [u8; 64]` and `signed_hash: [u8; 32]` are serialized through helpers that write a slice ([`section.rs#L514-L520`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/section.rs#L514-L520), [`section.rs#L558-L586`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/section.rs#L558-L586)). They are therefore length-prefixed byte sequences (`40` + 64 bytes, `20` + 32 bytes), not fixed arrays. On decode, any other length is an error.
- **Custom `Serialize` impls can branch on the format.** `Hash` writes a base32 string in human-readable formats such as JSON, and its raw 32 bytes in postcard ([`hash.rs#L198-L210`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/hash.rs#L198-L210)). Both forms are documented once, in [Binary hash form](../types.md#binary-hash-form) and [Base32 hash text](../types.md#base32-hash-text).
- **Names and discriminants are never written.** `#[serde(rename_all = ...)]` renames variants, as on `Encoding` ([`encoding.rs#L43-L45`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/encoding.rs#L43-L45)), and postcard writes the variant index, not the name, so the attribute does not change the bytes. `#[repr(u8)]` and explicit discriminants such as `Regular = 0` on `InodeKind` ([`attribute.rs#L6-L16`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/attribute.rs#L6-L16)) are likewise ignored: the declaration index is written, as the enum row above says.
- **`#[serde(default)]` does nothing in postcard.** Postcard decodes a struct as a tuple of exactly as many fields as the struct declares ([`Cargo.lock#L2938-L2939`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.lock#L2938-L2939); external: [deserializer.rs#L503-L513](https://github.com/jamesmunns/postcard/blob/718aa6a6850456017c19eeff67303c633f875736/source/postcard/src/de/deserializer.rs#L503-L513)). Missing trailing bytes are a decode error, not a defaulted field. This is why older payload layouts need explicit compatibility decoders ([`compatibility.rs#L1-L5`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/compatibility.rs#L1-L5)). Some comments in the code suggest otherwise; see [Open questions](#open-questions).
- **Trailing bytes are ignored.** `postcard::from_bytes` returns once the value is decoded and does not check for leftover input (external: [mod.rs#L12-L19](https://github.com/jamesmunns/postcard/blob/718aa6a6850456017c19eeff67303c633f875736/source/postcard/src/de/mod.rs#L12-L19)). Atomic decodes payloads with `postcard::from_bytes` ([`mod.rs#L162-L164`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/reader/mod.rs#L162-L164), [`change.rs#L727-L728`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L727-L728)), so a payload with bytes after the value is accepted. The SPAN section is the exception: its payload must re-encode to the identical bytes ([`change.rs#L714-L722`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L714-L722)).
- **Overlong varints are accepted.** Postcard's varint decoder reads until a byte without the high bit and only rejects values that overflow the type (external: [deserializer.rs#L66-L82](https://github.com/jamesmunns/postcard/blob/718aa6a6850456017c19eeff67303c633f875736/source/postcard/src/de/deserializer.rs#L66-L82)). A writer should always emit the minimal encoding, because the bytes are hashed.

## Change hash

The change hash is the identity of a change: the 32-byte value Atomic registers the change under and content-addresses it by ([`options.rs#L199-L205`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/options.rs#L199-L205), [`change.rs#L542-L546`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L542-L546)). Its text form is documented in [Base32 hash text](../types.md#base32-hash-text), and its uses on the wire in [Change hashes and the V3 file](../types.md#change-hashes-and-the-v3-file).

**Function.** The hash is BLAKE3 in its default hashing mode: no key, no derive-key context, and a 32-byte output. The writer and the reader both start from `blake3::Hasher::new()` ([`state_machine.rs#L190-L194`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/state_machine.rs#L190-L194), [`mod.rs#L408-L409`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/reader/mod.rs#L408-L409)). BLAKE3 is the external `blake3` crate, version 1.8.7 ([`Cargo.lock#L656-L657`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.lock#L656-L657)); the algorithm is defined by the [reference implementation at that release](https://github.com/BLAKE3-team/BLAKE3/blob/f3149ec5bb5449af877ba20377a11008ff499fa2/reference_impl/reference_impl.rs).

**Input.** The hash input is these bytes, concatenated in file order, exactly as they appear on disk:

1. The hash dedup table: all `hash_table_entries × 32` bytes ([`state_machine.rs#L270-L278`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/state_machine.rs#L270-L278), [`mod.rs#L422-L425`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/reader/mod.rs#L422-L425)).
2. For each section except SIGNATURE and UNHASHED, its frame bytes (5 bytes, or 45 for CONTENT) followed by its compressed payload bytes ([`helpers.rs#L113-L117`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/helpers.rs#L113-L117), [`sections.rs#L153-L155`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/sections.rs#L153-L155), [`sections.rs#L125-L129`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/reader/sections.rs#L125-L129)).

These bytes are not hashed:

- The 64-byte file header, including `version`, the flags and the counts ([`state_machine.rs#L220-L246`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/state_machine.rs#L220-L246)).
- The SIGNATURE and UNHASHED sections: their frames and their payloads ([`section.rs#L173-L195`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/section.rs#L173-L195)). Tests show that adding an UNHASHED section, or signing a change, leaves its hash unchanged ([`tests.rs#L605-L638`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/tests.rs#L605-L638), [`tests_signing.rs#L28-L35`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/tests_signing.rs#L28-L35)).
- The trailer.

The hash is taken over the uncompressed hash table and the *compressed* section bytes. It is not taken over decompressed payloads.

```text
h := blake3 (default mode)
h.write(file[64 : 64 + 32*hash_table_entries])        // the table
for each section, in file order:
    if type == 0x04 (SIGNATURE) or type == 0xF0 (UNHASHED): skip
    h.write(frame bytes)        // 5 bytes, or 45 for CONTENT (0x20)
    h.write(compressed payload) // compressed_len bytes
trailer (last 32 bytes of the file) must equal h.sum()
```

A reader skipping a section still has to feed it to the hasher; `skip_section` does so ([`sections.rs#L194-L202`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/reader/sections.rs#L194-L202)).

**Trailer.** The trailer is the 32-byte hash output, written raw after the last section ([`state_machine.rs#L523-L530`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/state_machine.rs#L523-L530)). `verify` reads it and fails with `HashMismatch` if it differs from the computed hash ([`sections.rs#L264-L282`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/reader/sections.rs#L264-L282)).

**The table's slot 0 is not the change hash.** The doc comments say index 0 holds "the change's own hash" ([`header.rs#L200-L204`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/header.rs#L200-L204)). It cannot: the hash covers the table, so a writer cannot know the hash before it writes the table. `Change::serialize` puts a placeholder of 32 zero bytes in slot 0 ([`change.rs#L391-L394`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L391-L394)), and every full-file fixture has zeros there ([`atomic_0_19_1_file_add.hex#L3`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/fixtures/atomic_0_19_1_file_add.hex#L3), [`span_opaque_v2_reference.hex#L1-L2`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/fixtures/span_opaque_v2_reference.hex#L1-L2), [`cb_fmt1_legacy_v1_object.hex#L1`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/fixtures/cb_fmt1_legacy_v1_object.hex#L1)). The change hash appears in the file only as the trailer, and in the SIGNATURE payload's `signed_hash` when the change is signed. See [HashIndex](#hashindex) for what index 0 means in payloads.

<a id="identity-comes-from-the-original-bytes"></a>**Identity comes from the original bytes.** The hash depends on postcard output, zstd output, FastCDC chunk boundaries and table order, so decoding a change and encoding it again can produce a different hash. Atomic therefore treats the received bytes as authoritative:

- `VerifiedChange::from_bytes` binds the identity to the original bytes. A test shows a file with non-FastCDC chunk boundaries keeps its original hash while a re-encoding gets a different one ([`verified.rs#L19-L34`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/verified.rs#L19-L34), [`verified.rs#L197-L229`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/verified.rs#L197-L229)).
- Re-encoding a change recorded by atomic 0.19.1 with the current writer gives it a different hash ([`legacy_history_span_insert_tests.rs#L23-L29`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/repository/tests/legacy_history_span_insert_tests.rs#L23-L29)).
- Importing a received change verifies the trailer, compares the result with the expected hash, and stores the exact bytes ([`changes.rs#L209-L223`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/repository/changes.rs#L209-L223), [`changes.rs#L254`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/repository/changes.rs#L254), [`changes.rs#L273-L275`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/repository/changes.rs#L273-L275)).
- The daemon's push can upload re-encoded bytes. When a change has no file on disk, it loads the change and uploads the output of `Change::serialize`, still under the original hash as the object's key ([`services_sync_remote.rs#L388-L398`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L388-L398), [`services_sync_remote.rs#L688-L695`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L688-L695)). `Change::serialize` writes version 2 or 3, never 1 ([`builder.rs#L135-L137`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/builder.rs#L135-L137), [`change.rs#L456-L459`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L456-L459)), so for a version 1 change the uploaded bytes always have a different hash from their key. For any other change they keep the key's hash only if `Change::serialize` reproduces the original bytes exactly. A receiver that checks identity, as Atomic's own pull does ([`changes.rs#L214-L223`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/repository/changes.rs#L214-L223)), refuses such an object. What the server does with it is unknown ([Open questions](#open-questions)).

A Go client should do the same. Treat the trailer, once verified, as the change's identity, and never re-encode a change to compute or check its hash. Because the hash is defined over the bytes actually written, a Go writer produces a valid change even if its zstd output differs from libzstd's. It gets the same hash as the Rust writer for the same change only if it reproduces every byte.

## Signing

A V3 file can carry one Ed25519 signature, in the optional SIGNATURE section (`0x04`), which is announced by flag bit 3 (`HAS_SIGNATURE`) ([`section.rs#L64-L74`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/section.rs#L64-L74), [`header.rs#L56-L57`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/header.rs#L56-L57)). The writer places it after DEPS and PROVENANCE and before GRAPH ([`change.rs#L481-L490`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L481-L490), [`state_machine.rs#L459-L485`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/state_machine.rs#L459-L485)). Nothing else in the file is signed.

- **Not hashed.** The SIGNATURE section is outside the change hash, so signing or re-signing a change never changes its identity ([`section.rs#L69-L73`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/section.rs#L69-L73), [`tests_signing.rs#L28-L35`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/tests_signing.rs#L28-L35)).
- **What is signed.** The signed message is the ASCII bytes `atomic.change.signature.v1`, then one `00` byte, then the 32-byte change hash ([`signing.rs#L21-L25`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/signing.rs#L21-L25), [`signing.rs#L104-L111`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/signing.rs#L104-L111)). The signature is a plain Ed25519 signature over that message, made with a 32-byte seed ([`signing.rs#L36-L49`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/signing.rs#L36-L49)). Ed25519 comes from the external `ed25519-dalek` crate, version 3.0.0 ([`Cargo.lock#L1326-L1327`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.lock#L1326-L1327)). The algorithm is [RFC 8032](https://www.rfc-editor.org/rfc/rfc8032) PureEdDSA. The doc comments say the signature is "over the content hash"; the domain prefix is part of the message.
- **Payload.** The payload is a postcard `ChangeSignature` ([`section.rs#L508-L527`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/section.rs#L508-L527)); its fields, their encodings and a decoded example are on [ChangeSignature](sections.md#changesignature). A signature verifies only when `signed_hash` equals the change hash, that is the trailer ([`signing.rs#L84-L91`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/signing.rs#L84-L91)). In the 0.19.1 fixture, the bytes after the `20` length prefix are the same 32 bytes as the trailer ([`atomic_0_19_1_file_add.hex#L13-L14`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/fixtures/atomic_0_19_1_file_add.hex#L13-L14), [`atomic_0_19_1_file_add.hex#L23-L24`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/fixtures/atomic_0_19_1_file_add.hex#L23-L24)).
- **How a signature is made.** `Change::sign_with` computes the change's hash by serializing the change, signs it, and attaches the signature ([`change.rs#L850-L869`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L850-L869)).
- **Verification is separate from reading.** `Change::deserialize` decodes the SIGNATURE payload but does not verify it ([`change.rs#L744-L750`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L744-L750)). `verify_change_signature` requires method `ed25519` and `signed_hash` equal to the verified change hash, then checks the signature against a public key the caller supplies ([`signing.rs#L71-L102`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/signing.rs#L71-L102)). The embedded DID is a discovery hint, never the key to trust ([`signing.rs#L8-L16`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/signing.rs#L8-L16)).

## Content chunking

A change's content blob (the bytes that its graph operations index into) is stored as zero or more CONTENT sections. Concatenating their decompressed payloads in file order rebuilds the blob ([`change.rs#L731-L734`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L731-L734)). The reader derives `contents_hash` as BLAKE3 of the rebuilt blob ([`change.rs#L814-L815`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L814-L815)).

**How the Rust writer splits content.** `Change::serialize` chunks the blob with `ChunkingOptions::default()` ([`change.rs#L419-L424`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L419-L424)):

| Content length | Chunks |
|---|---|
| 0 | none; `contents_chunks` is 0 ([`chunking.rs#L482-L484`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/chunking.rs#L482-L484)) |
| 1 to 16384 bytes | one chunk covering everything ([`chunking.rs#L486-L494`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/chunking.rs#L486-L494)) |
| more than 16384 bytes | FastCDC with minimum 16384, average 65536 and maximum 262144 bytes ([`chunking.rs#L164-L176`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/chunking.rs#L164-L176), [`chunking.rs#L496-L501`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/chunking.rs#L496-L501)) |

FastCDC is the external `fastcdc` crate, version 3.2.1 ([`Cargo.lock#L1429-L1430`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.lock#L1429-L1430)), using its `v2020` chunker ([`chunking.rs#L496-L501`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/chunking.rs#L496-L501)). That constructor uses normalization level 1 and gear seed 0 (external: [v2020/mod.rs#L454-L469](https://github.com/nlfiedler/fastcdc-rs/blob/e0d8753b39b273d20e33ef57a5cf68052ff8fac4/src/v2020/mod.rs#L454-L469)). Chunks are numbered from 0 in order, and each chunk's hash is BLAKE3 of its uncompressed bytes ([`chunking.rs#L503-L514`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/chunking.rs#L503-L514)).

**Chunk metadata.** Each CONTENT section's frame is a [ContentChunkHeader](#contentchunkheader). It carries `chunk_index`, `chunk_hash` (BLAKE3 of the uncompressed chunk), `uncompressed_len` and `compressed_len`. The writer computes the hash over the uncompressed data and compresses each chunk separately ([`sections.rs#L134-L147`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/sections.rs#L134-L147)). No other table or index of chunks exists in the file.

**What readers check.** The Rust reader exposes the chunk metadata but does not check it: it does not compare `chunk_hash` or `uncompressed_len` with the decompressed payload, and it does not check that `chunk_index` counts up from 0 ([`sections.rs#L131-L143`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/reader/sections.rs#L131-L143), [`change.rs#L731-L734`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L731-L734)). The frames are still covered by the change hash.

**What this means for writers.** Chunk boundaries do not affect what a reader rebuilds, but they do affect the change hash, because every 45-byte frame is hashed. Any split is valid: a test writes `hello` as the two chunks `he` and `llo`, and the file verifies under its own hash ([`verified.rs#L197-L229`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/verified.rs#L197-L229)). A Go writer that needs only valid files may chunk however it likes. To reproduce the Rust writer's hash, it must reproduce FastCDC 2020's cut points with these parameters, as well as libzstd's compressed bytes.

The layer-selective reader helpers refuse version 3 files ([`sections.rs#L395-L409`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/reader/sections.rs#L395-L409)). |

The version field is not hashed, but changing it does not let one change pass as another. A test rewrites a version 3 file's field to 2 and checks that the file no longer decodes ([`span_patch.rs#L342-L345`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/span_patch.rs#L342-L345)). The version decides how the HEADER payload and the section manifest are read, so a Go reader must branch on it as the table describes.

Version 1 files also differ in payload shapes. Some postcard payload structs changed shape while the header version stayed at 1 ([`compatibility.rs#L1-L5`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/compatibility.rs#L1-L5)). The reader retries a PROVENANCE payload in the July 2026 layout when the current layout fails ([`mod.rs#L176-L186`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/reader/mod.rs#L176-L186)). Those layouts are in [Historical layouts](sections.md#historical-layouts).

**Files that are not V3.** If the first four bytes are not `ATOM`, `Change::deserialize` reads them as a little-endian `u32`. A value of 1 or 2 is reported as the legacy pre-V3 bincode format ("must be re-recorded"); anything else is `InvalidMagic` ([`change.rs#L578-L595`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L578-L595)). There is no migration from those older formats.

**Forward compatibility.** Unknown flag bits (4 to 31) are kept and ignored. No reader rejects them, and they add no sections ([`header.rs#L305-L307`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/header.rs#L305-L307), [`header.rs#L34-L39`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/header.rs#L34-L39), [`header.rs#L95-L101`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/header.rs#L95-L101), [`header.rs#L372-L390`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/header.rs#L372-L390)). The 28 reserved bytes are read but never checked ([`header.rs#L228-L232`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/header.rs#L228-L232), [`header.rs#L317-L318`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/header.rs#L317-L318)). A new section type would break every existing reader ([Section order and multiplicity](#section-order-and-multiplicity)), so the doc comment's advice to bump `version` for breaking changes is the only extension path ([`header.rs#L34-L39`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/header.rs#L34-L39)).

## Reader validation

`Change::deserialize` is the full reader. It performs these checks, in this order, and stops at the first failure. Errors are [FormatError](#formaterror) values, or `ChangeError::Invalid` with the message shown.

1. Read 4 bytes. If they are not `ATOM`, fail with the legacy-format message or `InvalidMagic` ([`change.rs#L578-L595`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L578-L595)).
2. Parse the 64-byte header. Fail with `InvalidMagic` or `UnsupportedVersion` as described in [Versioning](#versioning) ([`header.rs#L287-L303`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/header.rs#L287-L303)).
3. Validate the header ([`header.rs#L399-L425`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/header.rs#L399-L425)):
   - `hash_table_entries` greater than 65534 fails with `InvalidHeader`.
   - `HAS_SEMANTIC` set with `semantic_section_count` 0 fails with `InvalidHeader`.
   - `semantic_section_count` greater than 0 without `HAS_SEMANTIC` fails with `InvalidHeader`.
   - No other flag is compared with a count at this step; step 9 does that for version 2 and 3 files.
4. Read `hash_table_entries × 32` bytes ([`hash_table.rs#L624-L638`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/hash_table.rs#L624-L638)). A duplicate entry fails with `InvalidHeader` "duplicate hash in dedup table at index N" ([`hash_table.rs#L222-L230`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/hash_table.rs#L222-L230)).
5. Compute the expected number of sections ([`mod.rs#L427-L428`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/reader/mod.rs#L427-L428)). For each section ([`sections.rs#L22-L136`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/reader/sections.rs#L22-L136)):
   - Read the type byte. An unknown byte fails with `InvalidSectionType`.
   - Read the rest of the frame: 4 more bytes, or 44 for `0x20`.
   - Read `compressed_len` bytes of payload.
   - Feed the frame and payload to the hasher if the section is hashed.
   - Decompress.

   An end of file exactly where a section should start ends the loop without an error ([`sections.rs#L32-L41`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/reader/sections.rs#L32-L41)). The trailer read in step 8 then fails. An end of file inside a frame or payload is `FormatError::Io` with kind `UnexpectedEof`.
6. In version 2 and 3 files, check the order ("canonical V2 section ordering") and reject duplicates ("duplicate V2 HEADER section", "duplicate V2 DEPS section", "duplicate V2 PROVENANCE section", "duplicate V2 UNHASHED section"). SPAN must appear only in version 3, only once, and in canonical form ("unexpected or duplicate SPAN section", "noncanonical SPAN section") ([`change.rs#L631-L743`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L631-L743)).
7. Decode each payload. A DEPS index must resolve to a non-zero hash ([`change.rs#L662-L680`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L662-L680), [`envelope.rs#L110-L123`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/envelope.rs#L110-L123)). Payload failures are `Postcard`, `HashIndexOutOfBounds`, `InvalidChangeMetadata`, `InvalidGraphOp`, a JSON error for UNHASHED, or `ChangeError::Invalid` "failed to deserialize ... section" ([`change.rs#L681-L750`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L681-L750)).
8. Read the 32-byte trailer and compare it with the computed hash. A difference fails with `HashMismatch` ([`change.rs#L754-L756`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L754-L756)).
9. In version 2 and 3 files, check that the sections read match the header ("V2 section manifest does not match the file header") ([`change.rs#L758-L782`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L758-L782)). The check compares the HEADER, DEPS, PROVENANCE, GRAPH, SEMANTIC, CONTENT, UNHASHED and SPAN counts ([`change.rs#L769-L776`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L769-L776)). It does not compare the SIGNATURE count, which cannot differ anyway, because the reader frames exactly the header's total and every other count is compared ([`header.rs#L372-L390`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/header.rs#L372-L390)). A header that promises more sections than the file holds usually fails earlier, in step 5 or 8, because the reader takes the trailer for a section. Then run `validate_v2` on the decoded change ([`change.rs#L838-L840`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L838-L840)). `Change::validate_v2` runs the `HashedChange` rules, compares `contents_hash` with BLAKE3 of the rebuilt blob (always equal on read, because the reader derives it), and for a version 3 file runs `SpanPatch::validate_content_ranges` ([`change.rs#L324-L338`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L324-L338), [`change.rs#L814-L815`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L814-L815); [SPAN section](sections.md#span-section)). The `HashedChange` rules require the dependency hashes to be non-zero and in strictly increasing byte order, among others ([`change.rs#L1151-L1207`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L1151-L1207), [`classification.rs#L298-L311`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/classification.rs#L298-L311)).

`Change::deserialize` stops after the trailer and does not look at any bytes that follow. `VerifiedChange::from_bytes` additionally fails a buffer with bytes after the trailer ("trailing bytes after verified change") ([`verified.rs#L21-L28`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/verified.rs#L21-L28)). A Go reader that receives a whole file should apply the stricter rule.

The low-level `ChangeReader` performs only steps 2 to 5 and 8 ([`mod.rs#L408-L443`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/reader/mod.rs#L408-L443), [`sections.rs#L113-L136`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/reader/sections.rs#L113-L136), [`sections.rs#L264-L282`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/reader/sections.rs#L264-L282)). It checks no order, duplicates or manifest.

## Writer rules

To write a file that Atomic's strict reader accepts:

1. Write `version` 2, or 3 if and only if the change has a span section ([`state_machine.rs#L232-L239`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/state_machine.rs#L232-L239), [`state_machine.rs#L517-L521`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/state_machine.rs#L517-L521)). Set the counts and flags to exactly the sections you write ([Reader validation](#reader-validation) step 9). Set `HAS_SEMANTIC` exactly when `semantic_section_count` is greater than 0 ([`builder.rs#L119-L133`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/builder.rs#L119-L133)). Write zeros in `reserved`. Atomic writers leave `total_uncompressed` as 0 ([FileHeader](#fileheader)).
2. Build the table:
   - Slot 0 holds 32 zero bytes ([`change.rs#L391-L394`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L391-L394)).
   - Every other slot holds a distinct non-zero hash: a reader refuses a repeated entry, so with zeros in slot 0 no other slot can be zero ([`hash_table.rs#L217-L233`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/hash_table.rs#L217-L233)). The Rust writer adds only hashes that a payload refers to ([`change.rs#L396-L411`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L396-L411)).
   - Use no more than 65534 slots ([`hash_table.rs#L267-L280`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/hash_table.rs#L267-L280)).

   The Rust writer inserts the dependencies first, then `extra_known`, then `supersedes`, then the causal-frontier roots, then every hash referenced by graph operations, skipping hashes already present ([`change.rs#L396-L411`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L396-L411)). Table order is hashed, so it is part of the identity, but readers accept any order: they check only for duplicates ([`hash_table.rs#L217-L233`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/hash_table.rs#L217-L233)).
3. Write DEPS indices that are neither 0 nor `0xFFFF` and are strictly increasing ([`state_machine.rs#L378-L393`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/state_machine.rs#L378-L393)). Inserting the sorted dependencies first, as the Rust writer does, gives indices 1, 2, 3, and so on.
4. Write the sections in [order](#section-order-and-multiplicity). Write each of HEADER, DEPS, PROVENANCE, SIGNATURE, SPAN and UNHASHED at most once. SIGNATURE goes after DEPS and PROVENANCE and before GRAPH ([`state_machine.rs#L459-L485`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/state_machine.rs#L459-L485)). UNHASHED is last ([`sections.rs#L193-L226`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/sections.rs#L193-L226)).
5. Compress each payload separately with zstd. Atomic uses level 3 ([Compression](#compression)).
6. For CONTENT, number the chunks from 0 and set `chunk_hash` to BLAKE3 of the uncompressed chunk ([`sections.rs#L123-L147`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/sections.rs#L123-L147)). Concatenated, the chunks must equal the content blob your graph operations index.
7. Hash as described in [Change hash](#change-hash), and append the 32-byte result.

A Go writer can check its output against `span_opaque_v2_reference.hex`. The Rust writer produces that file byte for byte from a known change ([`span_patch.rs#L454-L464`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/span_patch.rs#L454-L464)). Matching it requires the same HEADER payload bytes and libzstd 1.5.7's level-3 output for three tiny inputs, which are stored as raw blocks. Hand-building raw-block frames like these reproduces the file without libzstd; see the [worked example](#worked-example-a-version-2-file). A raw block holds at most 131072 bytes, so a larger payload needs several blocks in its frame; the worked example gives the rule.

### HashDedupTable

The table follows the header immediately. It is `hash_table_entries` raw 32-byte hashes in index order, with no count prefix, no framing and no compression ([`hash_table.rs#L34-L38`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/hash_table.rs#L34-L38), [`hash_table.rs#L584-L589`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/hash_table.rs#L584-L589)). The entry at byte offset `64 + 32*i` is index `i`. Every entry is fed to the change hash ([Change hash](#change-hash)).

| Offset in the file | Size | Field | Type | Meaning |
|---|---|---|---|---|
| `64 + 32*i`, for `i` from 0 to `hash_table_entries − 1` | 32 | entry `i` | `[u8; 32]`, raw bytes with no byte order to apply | The hash that [HashIndex](#hashindex) `i` names. Each entry is copied as it is, with no prefix or framing ([`hash_table.rs#L584-L589`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/hash_table.rs#L584-L589), [`hash_table.rs#L624-L638`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/hash_table.rs#L624-L638)); see [Binary hash form](../types.md#binary-hash-form). |

The reader reads the 64-byte header, then exactly `hash_table_entries` entries, then the sections, so the first section starts at offset `64 + 32*hash_table_entries` ([`mod.rs#L412-L419`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/reader/mod.rs#L412-L419)).

- **Entries are unique.** A reader fails with `InvalidHeader` if two entries are equal ([`hash_table.rs#L217-L233`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/hash_table.rs#L217-L233), [`hash_table.rs#L814-L824`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/hash_table.rs#L814-L824)). Since slot 0 is all zeros in Atomic files, no other slot can be zero.
- **Capacity.** The table holds at most 65534 entries (`MAX_HASH_TABLE_ENTRIES = u16::MAX - 1`), so the highest index is 65533 (`0xFFFD`), and `0xFFFF` can never be a slot ([`error.rs#L54-L60`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/error.rs#L54-L60)). A reader fails a larger count with `InvalidHeader` at header validation, or with `HashTableFull` ([`hash_table.rs#L624-L627`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/hash_table.rs#L624-L627)).
- **Slot 0.** Atomic writers put 32 zero bytes in slot 0, not the change hash ([Change hash](#change-hash)).

### HashIndex

A `u16` index into the table, used inside postcard payloads and therefore encoded as a varint: 1 byte up to 127, 3 bytes at most ([`hash_index.rs#L33-L39`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/hash_index.rs#L33-L39)). This section is the one place this reference defines what each value means; the payload pages link here.

Indices appear in the HEADER payload (`supersedes`, `causal_frontier`, `extra_known`), the DEPS payload, and three kinds of GRAPH field: a position's or a vertex's `change` and an edge's `introduced_by` ([ChangeHeaderV2](sections.md#changeheaderv2), [DEPS section](sections.md#deps-section), [What an index means](graph.md#what-an-index-means)). SPAN payloads name changes by full hash, and SEMANTIC payloads by node ID, so neither uses the table ([ExternalSpan](sections.md#externalspan), [Node IDs in semantic identities](graph.md#node-ids-in-semantic-identities)).

| Value | Constant | In GRAPH payloads | In HEADER and DEPS payloads |
|---|---|---|---|
| `0xFFFF` | `HASH_INDEX_NONE` ([`hash_index.rs#L41-L48`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/hash_index.rs#L41-L48)) | **This change**: the change the file holds. The compactor writes `None` (the change being recorded) as `0xFFFF` and reads `0xFFFF` back as `None` ([`compactor.rs#L249-L279`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/compact/compactor.rs#L249-L279)). | `0` | `HASH_INDEX_SELF` ([`hash_index.rs#L50-L55`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/hash_index.rs#L50-L55)) | An ordinary index: the hash in slot 0. | `1` to `hash_table_entries − 1` | | The change whose hash is in slot `i` ([`compactor.rs#L273-L279`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/compact/compactor.rs#L273-L279)). | The hash in slot `i`, refused if it is the zero hash ([`envelope.rs#L110-L123`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/envelope.rs#L110-L123)). |

Because the table holds at most 65534 entries, the highest index that can name a slot is `0xFFFD` ([HashDedupTable](#hashdeduptable)).

**Before compaction.** In memory, a graph operation names a change as an `Option<Hash>`: `None` is the change being recorded, `Some(Hash::NONE)` is the virtual ROOT, and `Some(h)` is change `h` ([`helpers.rs#L10-L16`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/record/workflow/globalize/helpers.rs#L10-L16), [`position.rs#L70-L89`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/apply/position.rs#L70-L89)). The compactor maps `None` to `0xFFFF` and looks every `Some` hash up in the table, so ROOT lands at index 0 only because the writer put the zero hash there ([`compactor.rs#L249-L266`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/compact/compactor.rs#L249-L266)). A test pins the mapping: with the writer's zero placeholder in slot 0, the change being built compacts to `0xFFFF`, ROOT to 0 and another change to 1, and each expands back to what it was ([`tests.rs#L507-L530`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/compact/tests.rs#L507-L530)).

**Resolve index 0 through the table.** Index 0 means whatever 32 bytes the file stores in slot 0, not ROOT as such. `HashDedupTable::new` puts whatever hash it is given in slot 0 ([`hash_table.rs#L161-L169`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/hash_table.rs#L161-L169)), and a test that seeds slot 0 with a non-zero hash ([`tests.rs#L42-L50`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/compact/tests.rs#L42-L50)) expands index 0 to that hash ([`tests.rs#L544-L554`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/compact/tests.rs#L544-L554)).

**The names and doc comments say the opposite.** The comments on `HashIndex`, on the two constants, on the table module and on the `change` fields of `CompactPosition` and `CompactGraphNode` describe index 0 as "this change" and `0xFFFF` as "no hash" or root ([`hash_index.rs#L20-L25`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/hash_index.rs#L20-L25), [`hash_index.rs#L41-L55`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/hash_index.rs#L41-L55), [`hash_table.rs#L42-L46`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/hash_table.rs#L42-L46), [`hash_index.rs#L117-L123`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/hash_index.rs#L117-L123), [`types.rs#L29-L34`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/compact/types.rs#L29-L34)). The helper methods follow the comments: `is_root` tests for `0xFFFF`, `is_self_ref` tests for 0, and the `Display` impls print them as `ROOT` and `SELF` ([`hash_index.rs#L219-L250`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/hash_index.rs#L219-L250), [`types.rs#L70-L104`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/compact/types.rs#L70-L104)). The compactor, which is what writes and reads files, does not use them, and its own comment says meaning must be recovered through the table, not from the constant names ([`compactor.rs#L249-L279`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/compact/compactor.rs#L249-L279)). ### SectionType

The header counts give 2 + 1 = 3 sections ([`header.rs#L372-L390`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/header.rs#L372-L390)). The hash input is bytes 64 to 242: the 32-byte table, then the HEADER, DEPS and CONTENT frames with their payloads, 179 bytes in all. BLAKE3 of those bytes is `cf90221730dcd4c8f3088b9b00001c317c251a0f66536aabd8a75dd902fcef8e`, which is the trailer. In base32 that is `Z6ICEFZQ3TKMR4YIRONQAAA4GF6CKGQPMZJWVK6YU5O5SAX456HA`, the value the test asserts ([`span_patch.rs#L459-L463`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/span_patch.rs#L459-L463)). All three payloads are raw zstd blocks. A Go writer can therefore reproduce this file exactly by building raw-block frames (magic, `00`, `58`, a 3-byte little-endian block header `(len << 3) | 1`, then the bytes), with no compressor.

That recipe works only for a payload of at most 131072 bytes. A zstd block's content may be at most `Block_Maximum_Size` bytes, the smaller of the window size and 128 KiB (external: [RFC 8878 §3.1.1.2](https://www.rfc-editor.org/rfc/rfc8878#section-3.1.1.2)), and the window descriptor `58` gives a 2 MiB window ([RFC 8878 §3.1.1.1.2](https://www.rfc-editor.org/rfc/rfc8878#section-3.1.1.1.2)). A bigger payload, such as a CONTENT chunk of up to 262144 bytes ([`chunking.rs#L164-L176`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/chunking.rs#L164-L176)), must be split over several raw blocks in one frame: block header `len << 3` on each block but the last, and `(len << 3) | 1` on the last. Any such split is valid. libzstd 1.5.7 cuts its input into blocks of at most `ZSTD_BLOCKSIZE_MAX`, 131072 bytes (external: [zstd.h#L147-L148](https://github.com/facebook/zstd/blob/v1.5.7/lib/zstd.h#L147-L148)), and ends a frame with an empty raw last block, `01 00 00`, when no block it wrote was marked last ([zstd_compress.c#L5361-L5369](https://github.com/facebook/zstd/blob/v1.5.7/lib/compress/zstd_compress.c#L5361-L5369)). A writer that wants libzstd's exact bytes for a large payload must reproduce those boundaries; this reference does not document libzstd's choices beyond that ([Open questions](#open-questions)).

## Open questions

- **Meaning of index 0 and `0xFFFF`.** This is the one place this reference lists the disagreement. The doc comments, constant names and helper methods say index 0 (`HASH_INDEX_SELF`) is this change and `0xFFFF` (`HASH_INDEX_NONE`) is "no hash" or root ([`hash_index.rs#L20-L25`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/hash_index.rs#L20-L25), [`hash_table.rs#L42-L46`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/hash_table.rs#L42-L46)). The compactor that writes and reads GRAPH payloads does the reverse: `0xFFFF` is this change, and index 0 is slot 0's zero hash, the virtual root ([`compactor.rs#L249-L279`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/compact/compactor.rs#L249-L279)). [HashIndex](#hashindex), [What an index means](graph.md#what-an-index-means) and the [HEADER and DEPS rules](sections.md#hash-indices) all document the code. Whether the server, or any other producer, applies the documented meaning anywhere is unknown.
- **Slot 0 contents.** The docs say slot 0 holds the change's own hash ([`header.rs#L200-L204`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/header.rs#L200-L204), [`hash_table.rs#L141-L149`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/hash_table.rs#L141-L149)). Production writers store zeros ([`change.rs#L391-L394`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L391-L394)). No reader checks slot 0. Whether a server refuses a file with a non-zero slot 0 is unknown.
- **Is SIGNATURE hashed?** The doc comment on `write_signature` calls SIGNATURE "a hashed section" whose bytes the trailer covers ([`state_machine.rs#L436-L447`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/state_machine.rs#L436-L447)). The code excludes it ([`section.rs#L193-L195`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/section.rs#L193-L195)), and a test confirms signing does not change the hash ([`tests_signing.rs#L28-L35`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/tests_signing.rs#L28-L35)). This page follows the code.
- **Hash coverage docs.** The `Trailer` doc lists the compressed sections as the hash input. It does not say the 5- and 45-byte frames are included, and it omits SPAN and SIGNATURE ([`builder.rs#L165-L179`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/builder.rs#L165-L179)). The types module doc's `ContentChunkHeader` diagram omits `uncompressed_len` ([`mod.rs#L62-L66`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/mod.rs#L62-L66)); the 45-byte layout above follows the code.
- **"No backward compatibility."** The module doc says there is no version detection and no dual code path ([`mod.rs#L97-L102`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/mod.rs#L97-L102)). The code reads versions 1, 2 and 3 with different rules ([Versioning](#versioning)).
- **Table capacity wording.** The doc says the table supports indices 0 through `0xFFFE` ([`hash_index.rs#L27-L31`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/hash_index.rs#L27-L31)). With at most 65534 entries, the highest usable index is `0xFFFD` ([`error.rs#L60`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/error.rs#L60)).
- **`serde(default)` in postcard payloads.** Some code comments say compatibility fields are appended with `serde(default)` ([`mod.rs#L229-L231`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/provenance_graph/mod.rs#L229-L231)). Postcard 1.1.3 always reads every declared field, so an older payload without the appended field fails to decode instead of taking the default ([Postcard encoding](#postcard-encoding)). The change payload types that carry the attribute are listed on [Serde attributes](sections.md#encoding-rules) and [LineOps](graph.md#lineops).
- **Chunk metadata and delta transfer.** The section doc says content chunks enable delta transfer, where only missing chunks are sent ([`section.rs#L85-L91`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/section.rs#L85-L91)). Nothing in the container code checks `chunk_hash`, `chunk_index` or `uncompressed_len` on read. The client can fetch a change's chunk list with [`get_chunk_manifest`](../endpoints/project.md#get_chunk_manifest), but no request it makes uploads or downloads a single chunk ([Delta transfer negotiation](../transport.md#delta-transfer-negotiation)). Whether a server checks chunk hashes is unknown.
- **Server-side checks.** The server is not in the source. Whether atomic.storage verifies the trailer, applies the strict version 2 rules, accepts version 1 uploads, refuses trailing bytes, re-encodes a received change (which would change its identity), or accepts a re-encoded `Change` object whose bytes do not hash to its key ([Identity comes from the original bytes](#identity-comes-from-the-original-bytes)) is unknown.
- **zstd input limits.** The Rust reader accepts whatever `zstd::decode_all` accepts, including several concatenated frames ([`sections.rs#L131-L136`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/reader/sections.rs#L131-L136); [Compression](#compression)). Whether a server accepts several frames in one payload, and what window size it tolerates, is not in the source.
- **libzstd block boundaries.** Reproducing libzstd's exact bytes for a payload above 131072 bytes needs libzstd's block-splitting and its choice between raw and compressed blocks. Beyond the block size limit and the empty last block ([Worked example](#worked-example-a-version-2-file)), this reference does not document them; they are libzstd internals, not part of the format.
- **Unused errors.** `SectionTruncated` and `UnexpectedEof` are declared ([`error.rs#L232-L248`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/error.rs#L232-L248)) but never raised. Truncation surfaces as `Io`.
