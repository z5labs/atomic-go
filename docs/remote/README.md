# Atomic remote protocol

This reference describes the HTTP protocol that the Atomic client speaks to a hosted Atomic server, and the V3 change-file format that carries changes over it, as implemented by atomicdotdev/atomic at commit [`a6c3e359456e83cf5a967a2e8265f11e0ba45d80`](https://github.com/atomicdotdev/atomic/commit/a6c3e359456e83cf5a967a2e8265f11e0ba45d80). That commit is the tip of atomicdotdev/atomic's `dev` branch as of 2026-11-24, and it is the same commit that the [Atomic RPC API reference](../rpc/README.md) describes. Every citation in these pages is a permalink pinned to that commit, so moving the reference to a newer commit means re-checking every citation against the new source, not only updating the links.

The server, `atomic-api` and `atomic-storage`, is not in that repository. The workspace's crates are the client, its libraries and its tools ([`Cargo.toml#L3-L19`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.toml#L3-L19)), and atomic-remote describes itself as the client side of the protocol that `atomic-api` servers serve ([`lib.rs#L1-L4`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/lib.rs#L1-L4)). These pages therefore document the protocol as the client speaks it: what the client sends, what it accepts and what it does with the answer. Where a source comment and the code disagree, a page describes the code and lists the disagreement under its "Open questions". Anything that only the server decides is listed there too, rather than guessed.

## Overview

### What a client talks to

**Two HTTP clients.** atomic-remote holds two HTTP clients, each with its own defaults; see [Two clients](transport.md#two-clients). `HttpRemote` speaks the *project protocol* to one project's URL ([`mod.rs#L143-L153`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/mod.rs#L143-L153)). `StorageClient` speaks the *atomic-storage management API*: create, read, update and delete on workspaces, projects and other management resources, with bearer authentication, JSON bodies and a response envelope. The push, pull and clone exchanges do not use it ([`storage.rs#L1-L8`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L1-L8)); the one exception is the signer-key lookup after a pull, described below. The atomic-teams crate sends its org, member, team, grant and domain requests through `StorageClient` ([`lib.rs#L1-L6`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-teams/src/lib.rs#L1-L6)), and `atomic identity register` sends one more management request with a plain reqwest client ([`register.rs#L183-L196`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/identity/register.rs#L183-L196)). The project protocol is documented on [endpoints/project.md](endpoints/project.md) and the management API on [endpoints/storage.md](endpoints/storage.md).

**The `/code` sync exchange.** A project's remote URL is `{org_base_url}/workspaces/{workspace}/projects/{project}/code` ([`create.rs#L159-L164`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/project/create.rs#L159-L164)). At this commit push, pull and clone move every object and ref through that one URL, in a binary format: a push `POST`s a [SyncPack](endpoints/project.md#syncpack) of objects and ref compare-and-swaps, and a pull or clone `GET`s with a [SyncWants](endpoints/project.md#syncwants) body naming the views it wants and the objects it already holds, and gets a SyncPack back ([`sync.rs#L1-L24`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/sync.rs#L1-L24), [`code_sync.rs#L42-L55`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/code_sync.rs#L42-L55), [`code_sync.rs#L79-L92`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/code_sync.rs#L79-L92)). The request header `Atomic-Protocol: sync/1` selects this exchange; atomic-objects documents that without it the same URL answers with JSON project information, which only the server can confirm ([`sync.rs#L44-L52`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/sync.rs#L44-L52)). Three kinds of side request surround the exchange: the project-identity read and bind on `?project-identity=1` ([`identity.rs#L1-L12`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/identity.rs#L1-L12)), the view inventory `GET {project}/refs/views` on a path beside `/code` ([`bare.rs#L17-L32`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/bare.rs#L17-L32)), and signer-key discovery, a management-API lookup sent to the remote's origin after a pull ([`signer_refresh.rs#L8-L33`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/signer_refresh.rs#L8-L33), [`services_sync_remote.rs#L1580-L1584`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1580-L1584)). [flows.md](flows.md) gives each flow as its ordered requests.

**The older query-string requests.** `HttpRemote` still implements the per-operation requests that select an operation with a query parameter, such as `GET ?view={view}&changelist={from}` and `POST ?insert={hash}&view={view}` ([`queries.rs#L84`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/queries.rs#L84), [`upload.rs#L43`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/upload.rs#L43)); the crate's documentation lists them as the protocol `atomic-api` serves ([`lib.rs#L64-L75`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/lib.rs#L64-L75)). The CLI and the daemon call only one of them, `download_change`, from the git-binding closure fetch ([`transport.rs#L630-L644`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/git/transport.rs#L630-L644)); the [endpoint table](#endpoints) marks the rest as unused. The `bare` module records that push, pull and clone moved to the single `/code` protocol ([`bare.rs#L1-L7`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/bare.rs#L1-L7)). Whether servers still answer the query-string requests is an [open question](#open-questions).

**Which code sends the requests.** `atomic push` and `atomic pull` inside a repository send their requests from libatomic's `PushChanges` and `PullChanges` handlers. Each command hands its work to the service layer first, and runs its own body only when no service opens ([`command.rs#L1139-L1147`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/push/command.rs#L1139-L1147), [`command.rs#L1032-L1038`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/pull/command.rs#L1032-L1038), [`rpc.rs#L5366-L5371`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/rpc.rs#L5366-L5371)), which happens outside a repository ([`mod.rs#L123-L126`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/service/mod.rs#L123-L126)) and inside a remote sandbox ([`mod.rs#L146-L153`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/service/mod.rs#L146-L153)). The commands' own bodies call `HttpRemote` directly; the [endpoint table](#endpoints) lists those calls too. The service layer runs the handler in process by default, or in the `atomicd` daemon when `ATOMIC_SERVICE=reactor` or `ATOMIC_RPC=1` is set ([`mod.rs#L82-L91`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/service/mod.rs#L82-L91), [`mod.rs#L1810-L1828`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/service/mod.rs#L1810-L1828)). Each handler builds an `HttpRemote` for the remote URL ([`services_sync_remote.rs#L500-L505`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L500-L505), [`services_sync_remote.rs#L1189-L1192`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1189-L1192)). `atomic clone` calls atomic-remote itself ([`command.rs#L1037`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L1037)). See [Which code sends the requests](flows.md#which-code-sends-the-requests).

### What this documentation does not cover

- **The server's internals.** The server is not in the source. The pages say what the client expects of it, and say whose claim each such statement is: a client comment, or a test server such as libatomic's sync test peer ([`local_sync_test.rs#L170-L206`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/tests/local_sync_test.rs#L170-L206)).
- **The recording algorithm.** [graph.md](change-format/graph.md) documents the bytes of a change's edits, not how a client decides which edits to record.
- **The local daemon's gRPC API.** That is the [Atomic RPC API](../rpc/README.md). Push and pull do not travel over it to the remote: the daemon's handlers are themselves HTTP clients of the remote ([`services_sync_remote.rs#L500-L505`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L500-L505)).
- **Requests to services that are not Atomic servers.** The release check of `atomic update` goes to the GitHub API ([`update.rs#L265-L280`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/update.rs#L265-L280)), and atomic-repository's AI features call AI providers ([`mod.rs#L104-L129`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/ai/mod.rs#L104-L129)). See [Out of scope](endpoints/storage.md#out-of-scope).

### The V3 change format in brief

A change travels between a client and a server as one V3 change file. A push uploads the exact bytes on disk, and re-serializes the change only when no file exists ([`services_sync_remote.rs#L375-L399`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L375-L399)); inside a SyncPack each file is one [ObjectRecord](endpoints/project.md#objectrecord) of family `Change` ([`services_sync_remote.rs#L688-L695`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L688-L695)).

- **Layout.** A file is a 64-byte header that starts with the magic `ATOM` ([`error.rs#L38-L42`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/error.rs#L38-L42), [`header.rs#L235-L237`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/header.rs#L235-L237)), a table of 32-byte hashes, a sequence of sections, and a 32-byte trailer that holds the change hash, written in that order ([`state_machine.rs#L241`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/state_machine.rs#L241), [`state_machine.rs#L267-L278`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/state_machine.rs#L267-L278), [`state_machine.rs#L523-L529`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/state_machine.rs#L523-L529), [`builder.rs#L181-L188`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/builder.rs#L181-L188)). Each section is a 5-byte frame, or a 45-byte frame for CONTENT, followed by its zstd-compressed payload ([`section.rs#L303-L305`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/section.rs#L303-L305), [`section.rs#L392-L394`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/section.rs#L392-L394)). The fixed-size structures are little-endian ([`header.rs#L164-L165`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/header.rs#L164-L165), [`header.rs#L294`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/header.rs#L294), [`section.rs#L320`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/section.rs#L320), [`section.rs#L415-L418`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/section.rs#L415-L418)). See [File layout](change-format/container.md#file-layout).
- **Sections.** The type byte names the section: HEADER `0x01`, DEPS `0x02`, PROVENANCE `0x03`, SIGNATURE `0x04`, GRAPH `0x10`, SPAN `0x11`, CONTENT `0x20`, SEMANTIC `0x30` and UNHASHED `0xF0` ([`section.rs#L144-L156`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/section.rs#L144-L156)). Payloads are postcard 1.1.3 ([`Cargo.lock#L2938-L2939`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.lock#L2938-L2939), [`helpers.rs#L98-L103`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/helpers.rs#L98-L103)), except that a CONTENT chunk is the raw content bytes ([`sections.rs#L134-L139`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/sections.rs#L134-L139)) and UNHASHED is JSON ([`change.rs#L536-L540`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L536-L540)). Writers compress every payload with zstd, at level 3 by default ([`options.rs#L7-L12`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/options.rs#L7-L12)). The payloads are on [sections.md](change-format/sections.md) and [graph.md](change-format/graph.md); the postcard rules are on [Postcard encoding](change-format/container.md#postcard-encoding).
- **Change hash.** The change hash is BLAKE3 in its default mode, in the writer and in the reader ([`state_machine.rs#L190-L194`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/state_machine.rs#L190-L194), [`mod.rs#L408-L409`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/reader/mod.rs#L408-L409)). It covers the hash-table bytes ([`state_machine.rs#L274-L275`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/state_machine.rs#L274-L275)) and, for every section except SIGNATURE and UNHASHED, the frame bytes and the compressed payload ([`helpers.rs#L113-L117`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/helpers.rs#L113-L117), [`section.rs#L193-L195`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/section.rs#L193-L195)). The file header is not hashed: the writer writes it without feeding the hasher ([`state_machine.rs#L241`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/state_machine.rs#L241), [`builder.rs#L177-L179`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/builder.rs#L177-L179)). Because compressed bytes are hashed, re-encoding a change can change its identity, so Atomic verifies a received file and stores its exact bytes ([`changes.rs#L209-L223`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/repository/changes.rs#L209-L223), [`changes.rs#L254`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/repository/changes.rs#L254), [`changes.rs#L273-L275`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/repository/changes.rs#L273-L275)). See [Change hash](change-format/container.md#change-hash).
- **Versioning.** The header's `version` field is 1 (legacy, read only), 2 (what writers emit) or 3 (a change with one SPAN section); any other value fails with `UnsupportedVersion` ([`error.rs#L44-L52`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/error.rs#L44-L52), [`header.rs#L294-L303`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/header.rs#L294-L303)). "V3" names the format family, not that field. See [Versioning](change-format/container.md#versioning).
- **Signing.** The optional SIGNATURE section carries an Ed25519 signature over `atomic.change.signature.v1`, a `0x00` byte and the 32-byte change hash ([`signing.rs#L21-L25`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/signing.rs#L21-L25), [`signing.rs#L104-L111`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/signing.rs#L104-L111)). See [Signing](change-format/container.md#signing) and [ChangeSignature](change-format/sections.md#changesignature).
- **Identifiers.** Every 32-byte identifier that travels as text is written the same way: RFC 4648 base32 in upper case without padding, 52 characters for 32 bytes. Change hashes, Merkle states and SetIds are written by atomic-core's `Base32` trait ([`mod.rs#L45-L52`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/mod.rs#L45-L52), [`hash.rs#L51`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/hash.rs#L51), [`hash.rs#L259-L287`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/hash.rs#L259-L287), [`hash.rs#L478-L480`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/hash.rs#L478-L480)), and public keys, identity ids and delegation ids by the external `data-encoding` crate's `BASE32_NOPAD` ([`keypair.rs#L51-L54`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/keypair.rs#L51-L54), [`identity.rs#L71-L74`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/identity.rs#L71-L74), [`delegation.rs#L607-L610`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L607-L610); data-encoding 2.11.1, [`Cargo.lock#L1174-L1175`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.lock#L1174-L1175)). Decoding follows two rules. atomic-core's decoder, for change hashes, Merkle states and SetIds, accepts lower case and ignores the four unused low bits of the last character ([`hash.rs#L289-L322`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/hash.rs#L289-L322), [`set_id.rs#L344-L376`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/set_id.rs#L344-L376)). `BASE32_NOPAD`, which decodes public keys, identity ids (and so `did:atomic` DIDs) and delegation ids, refuses lower case and non-zero trailing bits ([`keypair.rs#L92-L108`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/keypair.rs#L92-L108), [`identity.rs#L76-L92`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/identity.rs#L76-L92), [`identity.rs#L112-L118`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/identity.rs#L112-L118), [`delegation.rs#L612-L619`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L612-L619); external: [`lib.rs#L2254-L2264`](https://github.com/ia0/data-encoding/blob/834737d9c3dc957ce1b653959e3f35061dd77ade/lib/src/lib.rs#L2254-L2264), [`lib.rs#L1898-L1908`](https://github.com/ia0/data-encoding/blob/834737d9c3dc957ce1b653959e3f35061dd77ade/lib/src/lib.rs#L1898-L1908)), and project ids go through a strict decoder of their own with the same rule ([`project_id.rs#L14-L30`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/kg/project_id.rs#L14-L30)). A Go client should write only the canonical upper-case form. Their text and binary forms are on [Identifiers and encodings](types.md#identifiers-and-encodings), and the key encodings on [Keys and key encodings](auth.md#keys-and-key-encodings).

## How a client talks to a hosted server

**Server URLs.** The client addresses each org, the tenant, of a multi-tenant server on its own host: the org base URL keeps the configured server URL's scheme, host and port, puts `{org}.` in front of the host and drops any path, while for a single-tenant server it is the configured URL unchanged, less a trailing `/` ([`lib.rs#L141-L173`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-config/src/lib.rs#L141-L173)). A project's remote URL is `{org_base_url}/workspaces/{workspace}/projects/{project}/code` ([`create.rs#L159-L164`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/project/create.rs#L159-L164), [`init.rs#L182-L187`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/project/init.rs#L182-L187)). Doc comments still show an older `/tenant/{t}/portfolio/{p}/project/{name}/code` shape ([`lib.rs#L44-L48`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/lib.rs#L44-L48)). Management requests go to the org base URL, or to the apex, the server's own host, when they span orgs ([`client.rs#L61-L68`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/client.rs#L61-L68)). See [Server URLs](transport.md#server-urls), and [Base URLs](endpoints/storage.md#base-urls) for which request uses which base.

**HTTP methods and content types.** `HttpRemote` sends only `GET` and `POST`. Its sync requests carry `Content-Type: application/vnd.atomic.sync.v1` and `Atomic-Protocol: sync/1` ([`code_sync.rs#L47-L53`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/code_sync.rs#L47-L53)), and the pull direction is a `GET` with a request body ([`code_sync.rs#L84-L91`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/code_sync.rs#L84-L91)). `StorageClient` also sends `PUT` and `DELETE` ([`storage.rs#L208-L211`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L208-L211), [`storage.rs#L224-L227`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L224-L227)). Change-file uploads are `application/octet-stream` ([`upload.rs#L46-L50`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/upload.rs#L46-L50)), and every `StorageClient` request is `application/json`, `GET` and `DELETE` included ([`storage.rs#L118`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L118)). See [Methods and content types](transport.md#methods-and-content-types) and [Default headers](transport.md#default-headers).

**Compression.** `HttpRemote` sends `Accept-Encoding: zstd, gzip, deflate` and has reqwest decode gzip and deflate ([`mod.rs#L71-L72`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/mod.rs#L71-L72), [`mod.rs#L210-L213`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/mod.rs#L210-L213), [`mod.rs#L231-L232`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/mod.rs#L231-L232)), but no crate enables reqwest's zstd decoder ([`Cargo.toml#L103`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.toml#L103), [`Cargo.toml#L21`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/Cargo.toml#L21), [`Cargo.toml#L77`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/Cargo.toml#L77), [`Cargo.toml#L64`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/Cargo.toml#L64), [`Cargo.lock#L887-L895`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.lock#L887-L895)). No request body is HTTP-compressed. The sync bodies are compressed by Atomic itself: postcard-serialized, then zstd-compressed at level 3 ([`sync.rs#L58-L60`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/sync.rs#L58-L60), [`sync.rs#L299-L307`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/sync.rs#L299-L307)). Change files travel as their raw bytes ([`upload.rs#L46-L50`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/upload.rs#L46-L50)), already compressed section by section inside the file ([`helpers.rs#L101-L103`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/helpers.rs#L101-L103)). See [Compression](transport.md#compression).

**Streaming and chunked transfer.** One request body is streamed: `upload_change_streamed` sends a file from disk with `Content-Length` set to its size ([`upload.rs#L437-L471`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/upload.rs#L437-L471)). It is the only request with a stream body, and no code sets `Transfer-Encoding` ([`upload.rs#L460-L461`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/upload.rs#L460-L461)); every other body is an in-memory buffer ([`upload.rs#L46-L50`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/upload.rs#L46-L50), [`code_sync.rs#L44-L52`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/code_sync.rs#L44-L52)). Every response is read whole before it is used ([`queries.rs#L46-L49`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/queries.rs#L46-L49)), and `download_change_to_file` also buffers the whole body, although its documentation says it avoids that ([`download.rs#L18-L22`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/download.rs#L18-L22), [`download.rs#L44-L51`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/download.rs#L44-L51)). The streaming module documents a have/need exchange of content chunks ([`negotiation.rs#L18-L38`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/streaming/negotiation.rs#L18-L38)), but no request sends a have list or transfers a single chunk; the only chunk-related request is the chunk-manifest `GET` ([`download.rs#L171-L180`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/download.rs#L171-L180)). See [Streaming](transport.md#streaming), and [Content chunking](change-format/container.md#content-chunking) for chunks inside a change file.

**Version negotiation.** There is no version handshake. A server may send `X-Atomic-Min-Version`; when the running client is older, the client prints a warning to standard error and carries on, and the request neither fails nor changes ([`version.rs#L45-L65`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/version.rs#L45-L65)). Both clients check it on every response except those of `list_view_refs`, `fetch_project_identity` and `bind_project_identity` ([`queries.rs#L40`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/queries.rs#L40), [`storage.rs#L246`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L246), [`bare.rs#L34-L40`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/bare.rs#L34-L40), [`identity.rs#L133-L139`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/identity.rs#L133-L139)); the registration request does not check it either ([`register.rs#L198-L209`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/identity/register.rs#L198-L209)). A `sync_pull` whose answer does not decode also puts that header's value in a `VersionMismatch` error ([`code_sync.rs#L94-L108`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/code_sync.rs#L94-L108)). The only version the client sends is the `sync/1` value of `Atomic-Protocol`, whose suffix is to be bumped on any wire-breaking change ([`sync.rs#L49-L52`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/sync.rs#L49-L52)). The crate's `PROTOCOL_VERSION` constant is never sent ([`lib.rs#L172-L175`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/lib.rs#L172-L175)). See [Version negotiation](transport.md#version-negotiation).

**Authentication.** There is no login endpoint and no token cache: the client signs a short-lived EdDSA JWT itself, with the identity's Ed25519 key, and sends it as `Authorization: Bearer` ([`mod.rs#L1-L9`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L1-L9), [`token.rs#L3-L6`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L3-L6)). A token is valid for 5 minutes ([`token.rs#L56-L58`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L56-L58)), and its audience is the apex server URL, which push, pull and clone derive from the project URL ([`token.rs#L82-L86`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L82-L86), [`mod.rs#L414-L425`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L414-L425)). An agent identity also sends the delegation certificate it acts under in an `Atomic-Delegation` header ([`mod.rs#L430-L439`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L430-L439)); atomic-canonical's documentation says the server trusts it because the delegator's key is already registered ([`delegation.rs#L266-L277`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L266-L277)). An identity is an Ed25519 key with two DID forms, `did:atomic` (a fingerprint of the key) and `did:key` (the key itself) ([`identity.rs#L48-L52`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/identity.rs#L48-L52), [`keypair.rs#L56-L62`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/keypair.rs#L56-L62)). A human identity becomes known to a server through a signed `POST {server_url}/register` that carries no `Authorization` header ([`register.rs#L160-L196`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/identity/register.rs#L160-L196)). The client signs no request method, path or body: the token's claims are the subject key, the issue and expiry times, a token ID, the audience and, for an agent, the actor and the delegation ([`token.rs#L72-L95`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L72-L95)). See [auth.md](auth.md): [What exists](auth.md#what-exists), [Tokens](auth.md#tokens), [Delegation](auth.md#delegation), [Request headers](auth.md#request-headers) and [Registration](auth.md#registration); the registration endpoint itself is [`execute`](endpoints/storage.md#execute).

**Errors.** Every failed atomic-remote request becomes one `RemoteError` value ([`error.rs#L9-L17`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/error.rs#L9-L17)); its kinds are listed under [RemoteError](errors.md#remoteerror), and credential failures before a request under [AuthError](auth.md#autherror). On the project protocol the client reads an error body as plain text. On most requests `401` and `403` become `AuthenticationFailed`, `404` a result specific to the method, and any other status `HttpError` ([`queries.rs#L44-L66`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/queries.rs#L44-L66)); some requests give another status a meaning of its own, such as `409` on a sync push, which becomes `ProtocolError` ([`code_sync.rs#L61-L63`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/code_sync.rs#L61-L63)), and the view inventory has no case for `401` or `403` ([`bare.rs#L60-L64`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/bare.rs#L60-L64)). Each method's mapping is under [Project-protocol failures](errors.md#project-protocol-failures). On the management API it takes the message from a JSON [ApiResponse](endpoints/storage.md#apiresponse) or [ApiError](endpoints/storage.md#apierror) body and produces `HttpError` for every error status ([`storage.rs#L280-L305`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L280-L305)). When a push or pull runs in the daemon's handlers, a failure reaches the CLI as a gRPC `INVALID_ARGUMENT` status whose message is `atomic:REMOTE: ` followed by a JSON object with `stage`, `variant`, `url` and `message` ([`services_sync_remote.rs#L51-L66`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L51-L66), [`state.rs#L432-L452`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/state.rs#L432-L452)); the CLI strips that prefix before it parses the JSON ([`rpc.rs#L5288-L5293`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/rpc.rs#L5288-L5293)). See [Error responses](errors.md#error-responses) and [How errors reach the user](errors.md#how-errors-reach-the-user).

**Push, pull and clone.** A push reads the remote's refs with a `refs_only` sync pull of the view chain, plans each view, and stops there on a conflict or a dry run ([`services_sync_remote.rs#L508-L525`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L508-L525), [`services_sync_remote.rs#L619-L648`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L619-L648)). It then offers the project identity, sends every object and ref move in one `POST`, and re-reads the refs to check that each pushed change is listed ([`services_sync_remote.rs#L842-L902`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L842-L902)). A pull sends one sync pull that lists every change hash the repository holds as `haves` ([`services_sync_remote.rs#L1162-L1209`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1162-L1209)). A clone asks for one view, or every view, with no `haves`, and then reads the project identity ([`command.rs#L1028-L1037`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L1028-L1037), [`command.rs#L1052`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L1052)). [flows.md](flows.md) gives each sequence and how conflicts and partial failures are reported: [Push](flows.md#push), [Pull](flows.md#pull) and [Clone](flows.md#clone).

## Endpoints

The table has one row for each of the 83 HTTP requests the client sends to an Atomic server: 27 on a project URL ([endpoints/project.md](endpoints/project.md)), 25 through `StorageClient`'s own methods, 30 that atomic-teams sends through `StorageClient`, and the registration request ([endpoints/storage.md](endpoints/storage.md)). A row is a place in the code that builds a request, so a method that only delegates to another, `upload_change_file`, shares the row of the request it sends ([`upload.rs#L522-L529`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/upload.rs#L522-L529)). Seven requests to services that are not Atomic servers are excluded, because they are not part of this protocol: the GitHub API release check of `atomic update` ([`update.rs#L277-L278`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/update.rs#L277-L278)) and six calls to Anthropic, OpenAI and Voyage AI from atomic-repository's AI features ([`mod.rs#L207`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/ai/mod.rs#L207), [`mod.rs#L242`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/ai/mod.rs#L242), [`mod.rs#L331`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/ai/mod.rs#L331), [`mod.rs#L394`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/ai/mod.rs#L394), [`tools.rs#L237`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/ai/tools.rs#L237), [`tools.rs#L348`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/ai/tools.rs#L348)); see [Out of scope](endpoints/storage.md#out-of-scope).

The path placeholders are those of the endpoint pages: `{base}` is the project's `/code` URL and `{project}` that URL without `/code` ([How a request is addressed](endpoints/project.md#how-a-request-is-addressed)), and `{org_base}`, `{apex}` and `{origin}` are the management API's bases ([Base URLs](endpoints/storage.md#base-urls)). "Called at" cites where the client builds the request. "Used by" names the push, pull or clone step, or the other command, that calls the method at this commit, citing the call; a request whose method has no caller outside tests is "not used by any CLI flow at this commit". "The CLI's own push body" and "the CLI's own pull body" are the command bodies that run only when no service opens; see [Which code sends the requests](#what-a-client-talks-to).

## Open questions

These questions cut across pages or affect every client. Each page's own list follows.

- **What the server does.** The server is not in the source, so every statement about it comes from a client comment or from a test server. libatomic's sync test peer, for example, refuses a ref move with `409` "ref CAS refused" and a missing view snapshot with `400` ([`local_sync_test.rs#L176-L189`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/tests/local_sync_test.rs#L176-L189)). Those are a test's choices, not the server's contract. Each page lists what it could not confirm.
- **Whether the query-string requests are still served.** `HttpRemote` implements them ([`lib.rs#L64-L75`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/lib.rs#L64-L75)), but push, pull and clone moved to `/code` ([`bare.rs#L1-L7`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/bare.rs#L1-L7)), and only `download_change` has a caller outside tests. See [Which methods have callers](endpoints/project.md#which-methods-have-callers) and [Retired per-object sequences](flows.md#retired-per-object-sequences).
- **Unescaped query values.** The client puts view names, hashes and states into query strings without escaping them itself ([`queries.rs#L30`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/queries.rs#L30), [`upload.rs#L43`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/upload.rs#L43)). reqwest's URL parser then removes tabs and line breaks, percent-encodes only space, `"`, `'`, `<`, `>`, the other control bytes and non-ASCII bytes, and ends the query at a `#`; `%`, `+`, `&` and `=` are sent raw ([Building request URLs](transport.md#building-request-urls)). How the server decodes `%`, `+`, `&`, `=` and `#`, and which characters a view name may contain on the server, is not in the source. See [Building request URLs](transport.md#building-request-urls) and [View names](types.md#view-names).
- **A `GET` with a body.** The pull direction of the sync exchange sends its `SyncWants` as the body of a `GET` ([`code_sync.rs#L84-L91`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/code_sync.rs#L84-L91)). Whether the server accepts the exchange any other way, and how proxies in front of it treat such a body, is not in the source. See [Methods and content types](transport.md#methods-and-content-types).
- **zstd in `Accept-Encoding`.** `HttpRemote` advertises zstd but cannot decode it ([`mod.rs#L71-L72`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/mod.rs#L71-L72), [`Cargo.toml#L21`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/Cargo.toml#L21)). Whether a server ever answers with `Content-Encoding: zstd` is the server's choice. See [Compression](transport.md#compression).
- **Version policy.** The client only warns on `X-Atomic-Min-Version` ([`version.rs#L45-L65`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/version.rs#L45-L65)). Which responses carry it, whether a server refuses old clients outright, and how it rejects an unknown `Atomic-Protocol` value ([`sync.rs#L49-L52`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/sync.rs#L49-L52)) are not in the source. See [Version negotiation](transport.md#version-negotiation).
- **What the server checks in a token.** Which claims the server verifies, how much clock skew it allows and whether it tracks `jti` are not in the source. The token's comments say a fresh token is minted per request ([`token.rs#L3-L6`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L3-L6)), but `attach_identity` mints one and stores it in the configuration's extra headers ([`mod.rs#L425-L428`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L425-L428)), which become default headers on every request of that client ([`mod.rs#L215-L223`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/mod.rs#L215-L223)). The apex used as the audience drops the first host label whenever the host has a dot ([`mod.rs#L642-L647`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L642-L647)), so on a single-tenant host it differs from the org base URL ([`lib.rs#L154-L158`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-config/src/lib.rs#L154-L158)). See [What the server is expected to check](auth.md#what-the-server-is-expected-to-check), [Apex host](transport.md#apex-host) and [Open questions](auth.md#open-questions).
- **Error bodies, statuses and codes.** On the project protocol the client shows an error body as text ([`queries.rs#L58-L65`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/queries.rs#L58-L65)), and recognises missing dependencies only from English words in it ([`upload.rs#L73`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/upload.rs#L73)). On the management API it drops the error `code` on an error status ([`storage.rs#L282-L292`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L282-L292)), and keeps it only when a `2xx` body says `success: false` ([`storage.rs#L268-L271`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L268-L271)). Which statuses, bodies and codes the server sends is not in the source. See [Error bodies](errors.md#error-bodies) and [Error mapping](endpoints/storage.md#error-mapping).
- **Object keys in a sync pack.** `ObjectRecord.key` is documented as the lowercase-hex BLAKE3 of the bytes, which the receiver verifies ([`sync.rs#L129-L138`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/sync.rs#L129-L138)), but a push keys each change file by its base32 change hash ([`services_sync_remote.rs#L688-L695`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L688-L695)), and the change hash is not the BLAKE3 of the file ([`pack.rs#L289-L294`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/git_binding/pack.rs#L289-L294); see [Change hashes and the V3 file](types.md#change-hashes-and-the-v3-file)). `Attest` and `Provenance` objects are keyed by the base32 of the BLAKE3 of their bytes, the same digest that `verify_key` compares in hex, and `Tag` objects by a content hash of the decoded record ([Which identifier is which](types.md#which-identifier-is-which), [TagRecord](endpoints/project.md#tagrecord)). Which rule the server applies to each object family is not in the source. See [ObjectRecord](endpoints/project.md#objectrecord).
- **Ref moves and partial packs.** atomic-objects says the server moves a ref only if `expect_old` is current and an ancestor of the new target ([`sync.rs#L155-L159`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/sync.rs#L155-L159)); the test peer checks only equality ([`local_sync_test.rs#L176-L179`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/tests/local_sync_test.rs#L176-L179)). Whether the server stores the rest of a pack when it refuses one ref move is not in the source. See [Conflicts and rejections](flows.md#conflicts-and-rejections) and [Partial failure and repeats](flows.md#partial-failure-and-repeats).
- **A draft view's `own_changes`.** The ViewSnapshot comment says a draft's `own_changes` holds only the draft's own changes ([`view_snapshot.rs#L70-L73`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/view_snapshot.rs#L70-L73)). A push fills it from the view manifest's change log ([`services_sync_remote.rs#L346-L349`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L346-L349)), which for a draft includes the prefix inherited from its parent ([`manifest.rs#L10-L14`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/manifest.rs#L10-L14)). What the server and other producers write is not in the source. See [ViewSnapshot](endpoints/project.md#viewsnapshot).
- **Signer discovery sends a DID to the key lookup.** After a pull, signer discovery passes each unresolved signer's DID to `resolve_identity_by_public_key` ([`signer_refresh.rs#L26-L33`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/signer_refresh.rs#L26-L33)), which builds `/identities/by-key/{public_key}` ([`storage.rs#L538-L551`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L538-L551)); the [`/identities/by-did/`](endpoints/storage.md#resolve_identity_by_did) lookup has no caller. Whether the server's by-key lookup accepts a DID is not in the source. See [`resolve_identity_by_public_key`](endpoints/storage.md#resolve_identity_by_public_key).
- **Hash index 0 and `0xFFFF`.** The `HashIndex` comments say index 0 is the change itself and `0xFFFF` means no hash ([`hash_index.rs#L20-L25`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/hash_index.rs#L20-L25)). The writer does the reverse: it maps the change being recorded to `0xFFFF` ([`compactor.rs#L249-L266`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/compact/compactor.rs#L249-L266)) and puts 32 zero bytes, the root, at index 0 ([`change.rs#L391-L394`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L391-L394)). The pages follow the code; whether other writers do is not known. See [HashIndex](change-format/container.md#hashindex) and [What an index means](change-format/graph.md#what-an-index-means).
- **SIGNATURE and the change hash.** `write_signature`'s comment calls SIGNATURE a hashed section ([`state_machine.rs#L438-L441`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/state_machine.rs#L438-L441)), but `is_hashed` leaves it out of the change hash ([`section.rs#L193-L195`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/section.rs#L193-L195)). The pages follow the code. See [Signing](change-format/container.md#signing) and [Change hash coverage](change-format/sections.md#change-hash-coverage).
- **Missing fields in postcard payloads.** Some comments say a `#[serde(default)]` field lets older payloads that lack it decode ([`ops.rs#L590-L591`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/ops.rs#L590-L591)), but postcard encodes a struct by position, and another comment says that `serde(default)` therefore cannot recover a field whose position changed ([`compatibility.rs#L3-L5`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/compatibility.rs#L3-L5)). Whether payloads without such fields exist is not known. See [Postcard encoding](change-format/container.md#postcard-encoding).
- **What the server does with change files.** Whether a server verifies the trailer, accepts schema version 1 uploads, or re-encodes a received change, which would change its identity, is not in the source. What it returns for a layer-selective download is not either; the client's documentation says only that the result "may be a subset" ([`download.rs#L105-L108`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/download.rs#L105-L108)). See [Open questions](change-format/container.md#open-questions) and [Layer selection](transport.md#layer-selection).
- **Chunk-level transfer.** The streaming module documents a have/need exchange of content chunks ([`negotiation.rs#L18-L38`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/streaming/negotiation.rs#L18-L38)), but the client has no request for it. Whether servers implement one is not in the source. See [Delta transfer negotiation](transport.md#delta-transfer-negotiation).
