# Push, pull and clone

This page describes `atomic push`, `atomic pull` and `atomic clone` as the ordered HTTP requests they send to a hosted Atomic server, at commit [`a6c3e359456e83cf5a967a2e8265f11e0ba45d80`](https://github.com/atomicdotdev/atomic/commit/a6c3e359456e83cf5a967a2e8265f11e0ba45d80). All three move objects and refs through one endpoint per project, the remote's `/code` URL, in a binary sync format: a push `POST`s a pack of objects and ref moves, and a pull or clone `GET`s with a list of wanted views and held objects ([`sync.rs#L1-L29`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/sync.rs#L1-L29)). A few side requests surround that exchange: the project-identity binding, the view inventory and signer-key discovery. The server is not in the source, so anything only the server decides is listed under [Open questions](#open-questions).

## Which code sends the requests

| Command | Code that sends the HTTP requests | Evidence |
|---|---|---|
| `atomic push` inside a repository | libatomic's `PushChanges` handler, which the CLI calls | [`rpc.rs#L5366-L5404`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/rpc.rs#L5366-L5404) |
| `atomic pull` inside a repository | libatomic's `PullChanges` handler, which the CLI calls | [`rpc.rs#L5652-L5686`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/rpc.rs#L5652-L5686) |
| `atomic clone` | The CLI's own clone body, calling atomic-remote directly | [`command.rs#L1436-L1450`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L1436-L1450) |

`Push::run` calls `rpc::push` first and runs its own body only when that returns `false` ([`command.rs#L1139-L1147`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/push/command.rs#L1139-L1147)). `rpc::push` returns `false` only when `Service::open` returns `None` ([`rpc.rs#L5369-L5371`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/rpc.rs#L5369-L5371)). `Service::open` returns `None` outside a repository and inside a remote sandbox ([`mod.rs#L123-L128`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/service/mod.rs#L123-L128), [`mod.rs#L147-L154`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/service/mod.rs#L147-L154)). Pull is wired the same way ([`command.rs#L1032-L1038`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/pull/command.rs#L1032-L1038); [`rpc.rs#L5652-L5656`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/rpc.rs#L5652-L5656)). So inside an ordinary repository the CLI's own push and pull bodies do not run at this commit. They are still in the source and send nearly the same requests; [CLI-local push body](#cli-local-push-body) and [CLI-local pull body](#cli-local-pull-body) list the differences.

The service layer chooses where the handler runs. By default it runs in the CLI process; with `ATOMIC_SERVICE=reactor` or `ATOMIC_RPC=1` the CLI sends the RPC to the `atomicd` daemon over its socket ([`mod.rs#L82-L91`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/service/mod.rs#L82-L91), [`mod.rs#L161-L165`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/service/mod.rs#L161-L165), [`mod.rs#L190-L197`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/service/mod.rs#L190-L197)). In process, `Service::push_changes` and `Service::pull_changes` call `SyncImpl` directly ([`mod.rs#L1810-L1848`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/service/mod.rs#L1810-L1848)), and `SyncImpl` hands both to `services_sync_remote.rs` ([`services_sync.rs#L34-L45`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync.rs#L34-L45)). The HTTP requests are the same either way. libatomic's in-process `LocalService` routes the same two RPCs to the same handlers after resolving credentials itself ([`local.rs#L174-L217`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/local.rs#L174-L217)). For the RPC side see [PushChanges](../rpc/services/sync.md#pushchanges) and [PullChanges](../rpc/services/sync.md#pullchanges).

atomic-remote also exports `SyncEngine`, a changelist-dichotomy engine ([`lib.rs#L162`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/lib.rs#L162)). No push, pull or clone code uses it; it is described under [Changelist dichotomy](#changelist-dichotomy) for completeness.

## Push

### Push sequence

This is the sequence `atomic push` runs at this commit: the `PushChanges` handler, called by the CLI.

```text
CLI                              PushChanges handler                         server (/code)
 |  ListRemotes (in process)
 |  check_push_credentials (local)
 |  attach_identity (local)
 |--- PushChangesRequest -------->|
 |                                |  build view chain root -> leaf (local)
 |                                |--- 1. GET  /code  SyncWants{refs: chain, refs_only: true} --->|
 |                                |<-- 200 SyncPack{refs, View objects} -------------------------|
 |                                |  plan each view; stop on conflict or dry run
 |                                |  build one SyncPack; stop if empty
 |                                |--- 2. POST /code?project-identity=1  (local identity only) --->|
 |                                |<-- 200/201 | 404/405/501 | 409 -----------------------------|
 |                                |--- 2b. GET /code?project-identity=1  (after a 409 only) ----->|
 |                                |--- 3. POST /code  SyncPack{objects, refs} ------------------->|
 |                                |<-- 200/201 {"stored","refs_moved"} | 409 | 401/403 ---------|
 |                                |--- 4. GET  /code  SyncWants{refs: chain, refs_only: true} --->|
 |                                |<-- 200 SyncPack{refs, View objects} -------------------------|
 |<-- PushChangesResponse --------|
```

### Before the first request

1. The CLI resolves the remote through the in-process `ListRemotes` RPC, not over HTTP. An empty name selects the default remote, then `origin`; a name containing `://` is used as the URL ([`rpc.rs#L5243-L5263`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/rpc.rs#L5243-L5263)).
2. The CLI runs [`check_push_credentials`](auth.md#check_push_credentials), which fails when no usable identity or signing key resolves ([`rpc.rs#L5380`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/rpc.rs#L5380); [`mod.rs#L556-L586`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L556-L586)). libatomic's in-process `LocalService`, which resolves credentials itself before calling the same handler, behaves the same way: its sync test shows a push naming a missing identity failing with zero requests reaching the peer ([`local.rs#L174-L185`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/local.rs#L174-L185); [`local_sync_test.rs#L342-L350`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/tests/local_sync_test.rs#L342-L350)).
3. The CLI mints the auth headers with [`attach_identity`](auth.md#attach_identity) and sends them, with the resolved URL, in `PushChangesRequest` ([`rpc.rs#L5268-L5279`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/rpc.rs#L5268-L5279), [`rpc.rs#L5381-L5400`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/rpc.rs#L5381-L5400)).
4. The handler holds the repository's exclusive gate for the whole push, network I/O included ([`services_sync_remote.rs#L433-L434`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L433-L434)).
5. The local leaf view is `from_view`, else the `.atomic/current_view` marker, else `dev`. Its name on the remote is `to_view`, else the local name ([`services_sync_remote.rs#L484-L490`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L484-L490); [`state.rs#L77-L85`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/state.rs#L77-L85)).
6. The handler builds the ancestor chain root to leaf by following each view's parent, and fails on a cycle ([`services_sync_remote.rs#L157-L181`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L157-L181), [`services_sync_remote.rs#L492-L499`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L492-L499)). Only the leaf is renamed on the remote; ancestors keep their names ([`services_sync_remote.rs#L509-L518`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L509-L518)).
7. The HTTP client gets the timeout, the `insecure` flag and every auth header ([`services_sync_remote.rs#L143-L155`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L143-L155), [`services_sync_remote.rs#L501-L506`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L501-L506)).

### Request 1: ref advertisement

The handler sends `sync_pull` with `SyncWants::advertise(remote_names)`: `refs` is the chain's remote names root to leaf, `haves` is empty and `refs_only` is `true` ([`services_sync_remote.rs#L508-L525`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L508-L525); [`sync.rs#L237-L245`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/sync.rs#L237-L245)). atomic-objects documents the answer as the refs and view-snapshot objects of those views and their ancestor chains, with no change bodies or sidecars ([`sync.rs#L217-L224`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/sync.rs#L217-L224)).

The handler reads the answer like this ([`services_sync_remote.rs#L190-L217`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L190-L217)):

- Each `View` object is decoded as a [ViewSnapshot](endpoints/project.md#viewsnapshot); objects that do not decode are skipped.
- Each ref's `new_target` is kept as that view's compare-and-swap base.
- When the ref's snapshot is in the pack, it is rendered as manifest text, parsed and verified. Verification recomputes the merkle fold of the change list and compares it with the declared state ([`services_sync_remote.rs#L221-L244`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L221-L244); [`manifest.rs#L132-L142`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/manifest.rs#L132-L142)). A failure ends the push with stage `advertise`.
- When the ref's snapshot is not in the pack, the view has no known remote manifest but keeps its `new_target` as the base ([`services_sync_remote.rs#L201-L211`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L201-L211)).

A dry run sends this request too, then returns the plan ([`services_sync_remote.rs#L629-L648`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L629-L648)).

### Planning what to send

The handler compares each local view manifest with the remote one, root to leaf ([`services_sync_remote.rs#L541-L613`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L541-L613)). The local manifest is `Repository::view_manifest`, the view's change log as stored locally, renamed to the remote name for the leaf ([`services_sync_remote.rs#L548-L551`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L548-L551); [`views.rs#L892-L917`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/repository/views.rs#L892-L917)).

|---|---|---|
| Absent | Store the whole local log and declare the view. | [`services_sync_remote.rs#L307-L314`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L307-L314) |
| Scope differs | Identity-mismatch conflict. | [`services_sync_remote.rs#L315-L321`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L315-L321) |

- A view with nothing to store and nothing to declare is a no-op ([`services_sync_remote.rs#L255-L258`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L255-L258)).

So a change that is in more than one view's log, and in no advertised manifest of those views or their ancestors, goes into the pack once per view, as separate `Change` records with the same key ([`services_sync_remote.rs#L687-L698`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L687-L698)). The CLI-local body does the same: its comment says hashes "stored for an earlier view in this push" are skipped ([`command.rs#L623-L627`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/push/command.rs#L623-L627)), but its code adds only remote manifests to the set ([`command.rs#L659-L662`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/push/command.rs#L659-L662), [`command.rs#L684-L688`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/push/command.rs#L684-L688)). A Go client that wants one copy per change must deduplicate across the chain itself.
- The first conflict stops planning. The handler returns it in the response's `conflict` field and sends no further requests ([`services_sync_remote.rs#L556-L573`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L556-L573), [`services_sync_remote.rs#L619-L627`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L619-L627)).

### Diverged views

When the local and remote logs of a view each hold changes the other lacks, the plan stores the local-only changes and declares, because `declare` is true whenever the local set is not a subset of the remote set ([`services_sync_remote.rs#L330-L343`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L330-L343)). The snapshot minted for that declare lists the local log only, and its `prev` is the target the remote advertised ([`services_sync_remote.rs#L348-L373`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L348-L373), [`services_sync_remote.rs#L699-L715`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L699-L715)). So the ref move is a fast-forward in the `prev` chain, and the new snapshot leaves out the changes only the remote has.

The client relies on the server to merge those back in. Two CLI comments say so: "The server performs the local∪remote set union when publishing refs" ([`command.rs#L598-L601`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/push/command.rs#L598-L601)) and "Otherwise the server unions the proposal with its current set" ([`helpers.rs#L245-L247`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/push/helpers.rs#L245-L247)). That is the client's account of the server. Request 4 checks only that the re-read list contains every local change ([`services_sync_remote.rs#L885-L901`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L885-L901)), so it passes whether the server unions the sets or replaces the remote list with the pushed one. If the server replaces it, the view loses its remote-only changes. Which one it does is an [open question](#open-questions).

### Building the pack

The handler builds one [SyncPack](endpoints/project.md#syncpack) for the whole push, from a read-only repository handle ([`services_sync_remote.rs#L650-L662`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L650-L662)). Objects go in this order:

| Order | Object | `family` | `key` | `bytes` | Included when | Source |
|---|---|---|---|---|---|---|
| 1 | Change file | `Change` | Change hash, base32 | The change file as stored on disk, or the change re-serialized when the file is missing | For each non-no-op view, its changes to store, in log order | [`services_sync_remote.rs#L675-L698`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L675-L698); [`services_sync_remote.rs#L377-L399`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L377-L399) |
| 2 | View snapshot | `View` | Lowercase hex Blake3 of the snapshot's canonical JSON | The snapshot's canonical JSON | One per non-no-op view, after that view's changes | [`services_sync_remote.rs#L699-L710`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L699-L710); [`view_snapshot.rs#L106-L117`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/view_snapshot.rs#L106-L117) |
| 3 | Attestation | `Attest` | Attestation hash, base32 | `Attestation::serialize` output | It covers a stored change, and every change it covers is in the union of the chain's logs | [`services_sync_remote.rs#L663-L668`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L663-L668), [`services_sync_remote.rs#L722-L758`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L722-L758) |
| 4 | Provenance graph | `Provenance` | Provenance hash, base32 | `ProvenanceGraph::serialize` output | It explains a stored change, and every change it explains is in that union | [`services_sync_remote.rs#L759-L795`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L759-L795) |
| 5 | Tag | `Tag` | Tag content hash, base32 | `serialize_tag` output, a postcard [TagRecord](endpoints/project.md#tagrecord) | Every tag of the local leaf view, on every push. The record is sent as stored, so its `view` is the local view name even with `to_view`; see below. | [`services_sync_remote.rs#L796-L814`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L796-L814) |

A pushed tag keeps its local `view`. The handler lists the tags with `list_tags_for_view(&local_view)` and serializes each record unchanged; nothing rewrites its `view` ([`services_sync_remote.rs#L799-L808`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L799-L808)). The comment above that code says the tags are "declared under the possibly-renamed remote view name" ([`services_sync_remote.rs#L796-L797`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L796-L797)), but the code does not do this. `view` is part of the tag content hash ([`tag.rs#L100-L101`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/pristine/traits/tag.rs#L100-L101)), so the object key is computed from the local name too. The pack carries no ref for a tag; how the server ties a `Tag` object to a view when the names differ is an [open question](#open-questions).

Attestations and provenance graphs are deduplicated by hash ([`services_sync_remote.rs#L725-L733`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L725-L733), [`services_sync_remote.rs#L761-L770`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L761-L770)). The change-file bytes are the V3 format; see [File layout](change-format/container.md#file-layout).

Each non-no-op view also adds one [RefRecord](endpoints/project.md#refrecord), root to leaf: `name` is the view's remote name, `expect_old` is the target from request 1 (or none when the view was not advertised), and `new_target` is the new snapshot's key ([`services_sync_remote.rs#L699-L716`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L699-L716)).

The client mints each snapshot from the local manifest ([`services_sync_remote.rs#L346-L373`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L346-L373)):

| Snapshot field | Value |
|---|---|
| `scope` | `"draft"` for a draft view, else `"shared"` |
| `parent_view` | The manifest's parent view name, or none |
| `prev` | The advertised target from request 1 as a one-element list, or an empty list |
| `own_changes` | The manifest's change hashes in base32, in log order |
| `own_set_id` | The order-invariant `SetId` fold of those hashes, base32 |
| `merkle_state` | The manifest's merkle state in base32, or none for an empty log |

The CLI's copy of this function says the fold matches the server's own `from_manifest` bridge, so client and server mint byte-identical objects with identical keys ([`command.rs#L84-L88`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/push/command.rs#L84-L88)). The encodings are under [Merkle state](types.md#merkle-state) and [SetId](types.md#setid). The clone test builds a one-change shared root `dev` snapshot by the same rules ([`clone_sidecar_integration_test.rs#L85-L100`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/tests/it/clone_sidecar_integration_test.rs#L85-L100)).

The snapshot key is the hex Blake3 of `serde_json::to_vec` of the snapshot ([`view_snapshot.rs#L106-L117`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/view_snapshot.rs#L106-L117)), so a Go client must reproduce serde_json's bytes exactly. The byte layout, the serde_json version and where Go's `encoding/json` differs are under [ViewSnapshot](endpoints/project.md#viewsnapshot).

The whole pack is built in memory and sent as one body ([`services_sync_remote.rs#L662`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L662), [`services_sync_remote.rs#L864`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L864)). The CLI marks streaming large changes as a follow-up ([`command.rs#L780-L783`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/push/command.rs#L780-L783)). atomic-remote's chunk-manifest and layer types ([`mod.rs#L1-L19`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/streaming/mod.rs#L1-L19)) are not used by push, pull or clone.

When the pack is empty, the push ends here with no further requests ([`services_sync_remote.rs#L842`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L842)). The pack is empty only when every view is a no-op and the leaf view has no tags, because no-op views add nothing and tags are added on every push ([`services_sync_remote.rs#L670-L674`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L670-L674), [`services_sync_remote.rs#L796-L814`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L796-L814)).

### Requests 2 and 2b: project-identity bind

The handler binds only when the pack is not empty and the repository has a [project identity](auth.md#project-identity) ([`services_sync_remote.rs#L842-L863`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L842-L863)).

- Request 2 is `POST {remote_url}?project-identity=1` with `Content-Type: application/json`; the body is the local identity document ([`identity.rs#L169-L180`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/identity.rs#L169-L180); [`identity_transport.rs#L257-L264`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/identity_transport.rs#L257-L264)).
- `200` or `201` means bound, and `404`, `405` or `501` means the server predates the endpoint; the push continues in both cases ([`identity.rs#L181-L194`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/identity.rs#L181-L194); [`identity_transport.rs#L278-L279`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/identity_transport.rs#L278-L279)).
- On `409`, the client reads the body as `{"code", "message"}` (or nested under `"error"`), then sends request 2b, `GET {remote_url}?project-identity=1`, to name the remote binding. The push is then refused ([`identity.rs#L57-L73`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/identity.rs#L57-L73), [`identity.rs#L183-L191`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/identity.rs#L183-L191); [`identity_transport.rs#L280-L283`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/identity_transport.rs#L280-L283)).
- `401`, `403` and every other status fail the bind ([`identity.rs#L195-L202`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/identity.rs#L195-L202)).
- The handler turns any bind failure into gRPC `FAILED_PRECONDITION` before request 3 ([`services_sync_remote.rs#L858-L861`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L858-L861)).

### Request 3: send the pack

The handler sends `sync_push` with the encoded pack ([`services_sync_remote.rs#L864-L867`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L864-L867); [`code_sync.rs#L42-L55`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/code_sync.rs#L42-L55)).

### Partial failure and repeats

- Every object and every ref move travels in one `POST` ([`services_sync_remote.rs#L864`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L864)). Whether the server applies a pack all or nothing is not in the source.
- When request 3 fails, the handler returns at once. It does not re-read the advertisement to learn what landed ([`services_sync_remote.rs#L864-L867`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L864-L867)).
- When request 4 fails, request 3 has already returned `200` or `201`, so the pack was accepted; the handler still returns an error with stage `verify` ([`services_sync_remote.rs#L864-L875`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L864-L875)). The error does not say which refs moved, and the client learns nothing more. A repeat push plans again from a fresh advertisement (request 1), so it sends only what the remote still lacks.
- The bind in request 2 is sent before the pack. A push that then fails at request 3 may already have bound the remote to the local identity: the module comment says an unbound remote adopts the identity it is offered, which is the client's account of the server ([`services_sync_remote.rs#L842-L867`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L842-L867); [`identity_transport.rs#L14-L16`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/identity_transport.rs#L14-L16)).
- The handler opens the local repository read-only for planning and packing ([`services_sync_remote.rs#L537`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L537), [`services_sync_remote.rs#L657`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L657)), and otherwise only reads the project identity ([`services_sync_remote.rs#L850-L855`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L850-L855)). A failed push leaves no local trace.
- A repeat push plans again from a fresh advertisement, so changes the remote already lists are not sent again. A test repeats a push and sees no second upload ([`local_sync_test.rs#L370-L376`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/tests/local_sync_test.rs#L370-L376)). A leaf view with a tag is the exception: tags go into every pack, so requests 2 to 4 run on every repeat ([`services_sync_remote.rs#L796-L814`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L796-L814), [`services_sync_remote.rs#L842`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L842)).
- The CLI describes storing as content-addressed and idempotent ([`command.rs#L203-L206`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/push/command.rs#L203-L206)). That is the client's expectation of the server.

### Push end state

- Each declared view is advertised by the remote with a change list that contains every change of the local manifest. The client does not check that the ref points at the snapshot it minted ([`services_sync_remote.rs#L876-L902`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L876-L902)).
- `pushed_changes` in the response is the number of `Change` records in the pack, counting a change once for each view that stored it ([`services_sync_remote.rs#L696`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L696), [`services_sync_remote.rs#L916-L917`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L916-L917); see [Planning what to send](#planning-what-to-send)).

## Pull

### Pull sequence

This is the sequence `atomic pull` runs at this commit: the `PullChanges` handler, called by the CLI.

```text
CLI                              PullChanges handler                         server
 |  ListRemotes (in process)
 |  attach_identity (local)
 |--- PullChangesRequest -------->|
 |                                |  haves = every change hash in the local graph
 |                                |--- 1. GET /code  SyncWants{refs: [view], haves, refs_only: dry_run} --->|
 |                                |<-- 200 SyncPack{refs, View, Change, Attest, Provenance, Tag} ---------|
 |                                |--- 2. GET /code?project-identity=1 ----------------------------------->|
 |                                |  dry run: return
 |                                |  save changes; download-only: sidecars, then 3, return
 |                                |  reconcile views root -> leaf; import sidecars
 |                                |--- 3. GET {origin}/identities/by-key/{did}  (per unresolved signer) -->|
 |                                |--- 4. GET {project}/refs/views  (only if changes were replayed) ----->|
 |                                |  materialize working copy; save tags
 |<-- PullChangesResponse --------|
```

### Before the first request

1. The CLI resolves the remote through `ListRemotes` and mints the auth headers with `attach_identity`. It runs no credential check, so a pull without an identity goes unauthenticated ([`rpc.rs#L5657-L5682`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/rpc.rs#L5657-L5682)). libatomic's sync test pulls through `LocalService` with a missing identity from a peer that allows it ([`local_sync_test.rs#L461-L472`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/tests/local_sync_test.rs#L461-L472)).
2. The handler holds the repository's exclusive gate ([`services_sync_remote.rs#L1105-L1106`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1105-L1106)).
3. The remote view is `from_view`, else the current view. The local view is `to_view`, else the remote view's name ([`services_sync_remote.rs#L1156-L1160`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1156-L1160)).
4. `haves` is every change hash registered in the local graph, in base32, not only the target view's ([`services_sync_remote.rs#L1162-L1187`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1162-L1187)). The CLI explains this keeps the server from resending shared-view changes when a draft's own log is empty ([`command.rs#L539-L543`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/pull/command.rs#L539-L543)).
5. The handler prepares a signer-discovery client only when the auth headers include `Authorization: Bearer` ([`services_sync_remote.rs#L1189-L1191`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1189-L1191); [`signer_refresh.rs#L8-L21`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/signer_refresh.rs#L8-L21)).

### Request 1: sync pull

The handler sends `sync_pull` with `refs` set to the remote view, the graph-wide `haves`, and `refs_only` set to the dry-run flag ([`services_sync_remote.rs#L1197-L1209`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1197-L1209)). atomic-objects documents the answer as the objects the client is missing plus the current ref targets ([`sync.rs#L21-L24`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/sync.rs#L21-L24)). The CLI expects the requested view's snapshot and every ancestor's ([`command.rs#L566-L568`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/pull/command.rs#L566-L568)). libatomic's test peer returns the refs of the requested views and their ancestors, plus every stored object whose key is not in `haves`, of any family, or only `View` objects when `refs_only` is set ([`local_sync_test.rs#L125-L169`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/tests/local_sync_test.rs#L125-L169)).

The handler rebuilds the view chain from the pack ([`services_sync_remote.rs#L929-L968`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L929-L968)):

1. For every ref, it finds the `View` object with that key, decodes it and parses its manifest text ([`services_sync_remote.rs#L972-L997`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L972-L997)). Pull parses but does not verify the merkle fold, unlike push and clone.
2. It folds the change list into a `SetId` and warns when that differs from the snapshot's `own_set_id` ([`services_sync_remote.rs#L998-L1007`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L998-L1007)).
3. It walks from the requested view up through each parent, then reverses to root-to-leaf order ([`services_sync_remote.rs#L943-L967`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L943-L967)).

Any failure in that walk (the view is missing, an ancestor is missing, a cycle, a manifest that does not parse) is reported as stage `fetch-missing`, `Remote view '<name>' does not exist` ([`services_sync_remote.rs#L1210-L1221`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1210-L1221)). The leaf is then renamed to the local view name; ancestors keep their names ([`services_sync_remote.rs#L1255-L1258`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1255-L1258)).

### Request 2: project identity

The handler sends `GET {remote_url}?project-identity=1` on every pull, dry runs and download-only pulls included, because it runs before either of those returns ([`services_sync_remote.rs#L1222-L1254`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1222-L1254), [`services_sync_remote.rs#L1306-L1307`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1306-L1307)).

- A bound identity is applied locally. A local repository with no identity, or with one minted as an upgrade placeholder, adopts it; a local identity that was created or already adopted and differs is kept and reported as a warning ([`project_identity.rs#L160-L195`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/repository/project_identity.rs#L160-L195); [`identity_transport.rs#L10-L13`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/identity_transport.rs#L10-L13); [`services_sync_remote.rs#L1239-L1247`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1239-L1247)).
- An unbound project, a server that predates the endpoint (`200` without `bound`, `404`, `405`, `501`), and transport errors change nothing and never fail the pull ([`identity.rs#L139-L156`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/identity.rs#L139-L156); [`identity_transport.rs#L98-L114`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/identity_transport.rs#L98-L114)).

### Saving changes

- Every `Change` object in the pack is treated as missing; the list comes from the pack's own keys, and a key that does not parse as a base32 hash is skipped without a warning ([`services_sync_remote.rs#L1266-L1276`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1266-L1276)).
- A dry run returns here, after requests 1 and 2 ([`services_sync_remote.rs#L1306-L1358`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1306-L1358)).
- Each change is deserialized and its hash recomputed. A mismatch refuses that change ([`services_sync_remote.rs#L1012-L1016`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1012-L1016); [`changes.rs#L214-L223`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/repository/changes.rs#L214-L223)). See [Change hash](change-format/container.md#change-hash).
- A change that fails to save is counted in `changes_failed` and the pull continues ([`services_sync_remote.rs#L1402-L1412`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1402-L1412)). The handler looks each body up again by the re-encoded hash, and aborts the pull with stage `download`, variant `change_not_found` when that lookup fails, which can happen only when re-encoding a parsed key does not give back the key ([`services_sync_remote.rs#L1371-L1380`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1371-L1380), [`services_sync_remote.rs#L1415-L1423`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1415-L1423)).
- A download-only pull imports the attestations and provenance graphs, runs signer discovery (request 3), and returns without changing any view ([`services_sync_remote.rs#L1438-L1513`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1438-L1513)).

### Reconciling and sidecars

- The handler reconciles each manifest into the local views, root to leaf. Errors are collected into `apply_errors` and do not fail the RPC ([`services_sync_remote.rs#L1515-L1547`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1515-L1547)).
- Provenance graphs and attestations are imported after reconciling, because their dependency edges need the covered changes registered ([`services_sync_remote.rs#L1549-L1578`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1549-L1578)). Each is hash-checked against its key, and one already present is not counted again ([`services_sync_remote.rs#L1031-L1060`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1031-L1060)).

### Request 3: signer discovery

This step runs only when the pull carried a bearer token ([`services_sync_remote.rs#L1580-L1585`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1580-L1585)).

- For every `did:atomic:` signer of a local attestation with no cached key ([`kg_attestation.rs#L35-L50`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/repository/kg_attestation.rs#L35-L50)), the client sends `GET {origin}/identities/by-key/{did}` ([`signer_refresh.rs#L26-L34`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/signer_refresh.rs#L26-L34); [`storage.rs#L546-L551`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L546-L551)).
- `{origin}` is the remote URL's scheme, host and port; the project path is dropped ([`signer_refresh.rs#L19`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/signer_refresh.rs#L19)).
- The request carries the same bearer token, `Atomic-Delegation` when present, `Content-Type: application/json`, and `User-Agent: atomic/<version>` ([`signer_refresh.rs#L18-L20`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/signer_refresh.rs#L18-L20); [`storage.rs#L98-L124`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L98-L124)).
- Each lookup has a 10-second timeout. A failure is skipped, and a returned key is cached only when it matches the DID ([`signer_refresh.rs#L30-L47`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/signer_refresh.rs#L30-L47)).
- A local repository error in this step fails the pull after the changes are saved and the views reconciled ([`services_sync_remote.rs#L1580-L1585`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1580-L1585)).

### Request 4: view inventory

This step runs only when reconciling replayed at least one change ([`services_sync_remote.rs#L1524-L1530`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1524-L1530), [`services_sync_remote.rs#L1588-L1592`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1588-L1592)).

- The client sends `GET {project_url}/refs/views` ([`bare.rs#L31-L39`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/bare.rs#L31-L39)) and reads its rows as [RemoteViewInfo](types.md#remoteviewinfo) ([`bare.rs#L46-L58`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/bare.rs#L46-L58)).
- It compares the remote view's `set_id` with the local view's set-id. A mismatch is a warning; a failed request or a missing `set_id` skips the check ([`services_sync_remote.rs#L1592-L1630`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1592-L1630)).

### Materializing and tags

These steps are local and send no requests.

- The working copy is materialized only when the local view is the workspace's current view ([`services_sync_remote.rs#L1632-L1657`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1632-L1657)).
- Each `Tag` object in the pack is saved unless the local view already has a tag with that name ([`services_sync_remote.rs#L1691-L1730`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1691-L1730)). The bytes are decoded as a [TagRecord](endpoints/project.md#tagrecord) and the key is not checked. The name check uses the local view name, but the record is saved under its own `view` field ([`tags.rs#L98-L101`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/repository/tags.rs#L98-L101)).

### Divergence and conflicts

- A pull sends only `GET` requests and proposes no ref move, so it has no compare-and-swap for the server to refuse.
- Local changes missing from the remote list are reported in `local_only` ([`services_sync_remote.rs#L1278-L1304`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1278-L1304)).
- A local view that cannot take a remote manifest is reported in `apply_errors` ([`services_sync_remote.rs#L1532-L1535`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1532-L1535)).
- A remote project identity that differs from an established local one is a warning ([`services_sync_remote.rs#L1241-L1245`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1241-L1245)).

### Partial failure and repeats

- When request 1 fails, nothing is saved; the error has stage `fetch` ([`services_sync_remote.rs#L1206-L1209`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1206-L1209)).
- The identity from request 2 is applied before any change is saved, so even a dry run or a pull that fails later can adopt it ([`services_sync_remote.rs#L1224-L1238`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1224-L1238)).
- Changes saved before a later failure stay saved. The next pull lists them in `haves`, so the server need not send them again ([`services_sync_remote.rs#L1177-L1182`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1177-L1182)).

### Pull end state

- The local graph holds every change from the pack that saved without error ([`services_sync_remote.rs#L1380-L1413`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1380-L1413)).
- The chain's views are reconciled under their remote names, the leaf under the local view name; the response's `updated_views` lists them ([`services_sync_remote.rs#L1765-L1773`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1765-L1773)).
- The client sent no write request to the server.

## Clone

### Which clone path runs

`Clone::run` calls the CLI's clone body directly; there is no service layer ([`command.rs#L1436-L1450`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L1436-L1450)). A `--git` clone, or a URL ending in `.git`, starting with `git@` or `ssh://`, or naming a local Git repository, takes the Git bootstrap instead and sends none of the requests below ([`command.rs#L949-L957`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L949-L957); [`bootstrap.rs#L67-L85`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/git/bootstrap.rs#L67-L85)).

### Clone sequence

```text
CLI (atomic clone)                                                      server
 |  create target directory, init empty repository (local)
 |  attach_identity from the URL only (local)
 |--- 1. GET /code  SyncWants{refs: [view] or [], haves: [], refs_only: false} --->|
 |<-- 200 SyncPack{refs, View, Change, Attest, Provenance, Tag} -----------------|
 |--- 2. GET /code?project-identity=1 ------------------------------------------->|
 |  view absent: create empty view, set origin, done
 |  save chain's changes; download-only: sidecars, set origin, done
 |  apply manifests root -> leaf, materialize, set origin
 |--- 3. GET /code  SyncWants{refs: [], haves: [], refs_only: true}  (no --all-views) --->|
 |  import sidecars
 |--- 4. GET {project}/refs/views  (no apply errors) ---------------------------->|
```

### Before the first request

- The client creates the target directory under a cleanup guard and initializes an empty repository ([`command.rs#L978-L996`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L978-L996)). The guard deletes the directory when the clone returns early ([`helpers.rs#L296-L303`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/helpers.rs#L296-L303)).
- The auth headers come from the clone URL alone: no `--identity` and no remote registry ([`command.rs#L336-L343`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L336-L343)).

### Request 1: fetch

- By default the client asks for one view, `dev` unless `--view` names another, with empty `haves` and `refs_only` false ([`command.rs#L1024-L1036`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L1024-L1036); [`command.rs#L75`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L75)).
- With `--all-views` it sends `SyncWants::all(vec![])`; empty `refs` asks for every view ([`command.rs#L1028-L1029`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L1028-L1029); [`sync.rs#L206-L235`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/sync.rs#L206-L235)).
- A failure ends the clone and the guard removes the directory ([`command.rs#L1037-L1043`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L1037-L1043)).

### Request 2: project identity

The client sends `GET {remote_url}?project-identity=1` and applies it with the same adoption rules as pull, before the local knowledge graph is built ([`command.rs#L1047-L1065`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L1047-L1065); [`identity_transport.rs#L84-L93`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/identity_transport.rs#L84-L93)). The clone test's server answers every path not ending in `/code` with `404`, and the clone still succeeds ([`clone_sidecar_integration_test.rs#L155-L159`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/tests/it/clone_sidecar_integration_test.rs#L155-L159), [`clone_sidecar_integration_test.rs#L211-L216`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/tests/it/clone_sidecar_integration_test.rs#L211-L216)).

### Reading the chain and saving changes

- The client reads the requested view's snapshot from the pack, then each parent's, and applies them root to leaf ([`command.rs#L567-L614`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L567-L614)). Each manifest is parsed and verified, and a set-id disagreement is a warning ([`command.rs#L457-L491`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L457-L491)).
- A parent that the pack lacks, or a parent loop, is an error ([`command.rs#L584-L606`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L584-L606)).
- When the requested view is not in the pack, the client creates it empty, records the remote as `origin`, and finishes without further requests ([`command.rs#L1079-L1117`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L1079-L1117)).
- The client saves the union of the chain's changes that it does not already hold, taking each body from the pack ([`command.rs#L1138-L1151`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L1138-L1151)). A missing body aborts the clone ([`command.rs#L672-L684`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L672-L684)).
- A body that is in the pack but fails to save, for example on a hash mismatch, does not stop the clone. It is counted as a failure and the loop carries on with the next change ([`command.rs#L647-L670`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L647-L670); [`changes.rs#L214-L223`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/repository/changes.rs#L214-L223)). The clone then goes on to apply the manifests; see [Partial failure and clone end state](#partial-failure-and-clone-end-state).
- `--download-only` imports the sidecars, records `origin`, and finishes ([`command.rs#L1153-L1196`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L1153-L1196)).

### Applying

- The client applies each manifest root to leaf, switches to the requested view and materializes the working copy ([`command.rs#L1198-L1266`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L1198-L1266)).
- It records the clone URL as the default remote `origin` ([`command.rs#L1268-L1281`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L1268-L1281)).

### Request 3: other views

- With `--all-views`, the other views come from the pack of request 1; no request is sent ([`command.rs#L812-L823`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L812-L823), [`command.rs#L1288-L1305`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L1288-L1305)).
- Otherwise, and only when nothing failed to apply ([`command.rs#L1287-L1308`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L1287-L1308)), the client sends `sync_pull` with `SyncWants::advertise(vec![])` (all refs, `refs_only` true) only to list the other view names in a hint. Failure is ignored ([`command.rs#L916-L942`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L916-L942)).

### Request 4: view inventory

After importing the sidecars ([`command.rs#L1311-L1318`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L1311-L1318)), and only when nothing failed to apply, the client sends `GET {project_url}/refs/views`. It compares each applied view's `set_id` with the local set-id, warns on a mismatch, and skips the check when the request fails ([`command.rs#L1320-L1326`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L1320-L1326), [`command.rs#L500-L543`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L500-L543)).

### Partial failure and clone end state

- An error before the end removes the target directory, except with `--into-existing`, which installs no guard ([`command.rs#L978-L988`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L978-L988)).
- A change that failed to save, or an apply error, keeps the partial clone and returns the error "clone completed with errors" ([`command.rs#L1370-L1395`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L1370-L1395)).
- With `--download-only`, a change that failed to save does not fail the clone: that branch returns success before the failure check ([`command.rs#L1153-L1196`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L1153-L1196)).
- On success the new repository holds the requested view and its ancestors with their scopes and parents, the requested view is current, and `origin` is the default remote ([`command.rs#L1198-L1281`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L1198-L1281)). A clone sends no write requests.

## Changelist dichotomy

`SyncEngine` in `atomic-remote/src/sync.rs` finds where a cached copy of a remote view's history diverged from the remote, by binary search on merkle states ([`sync.rs#L1-L31`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/sync.rs#L1-L31)). At this commit nothing outside atomic-remote calls it; the crate only re-exports it ([`lib.rs#L162`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/lib.rs#L162)). The flows above do not use the changelist endpoints at all.

`compute_delta(view, local_hashes)` sends these requests ([`sync.rs#L635-L725`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/sync.rs#L635-L725)):

1. `GET {remote_url}?view={view}&state=` ([`get_state`](endpoints/project.md#get_state)). When the answer carries a `SetId` equal to the fold of `local_hashes`, the views are in sync and no more requests are sent ([`sync.rs#L640-L656`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/sync.rs#L640-L656), [`sync.rs#L478-L486`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/sync.rs#L478-L486)).
2. With an empty cache: `GET {remote_url}?view={view}&changelist=0` ([`get_changelist`](endpoints/project.md#get_changelist)). Every entry whose hash is not in `local_hashes` is to download, and the cache is seeded ([`sync.rs#L659-L661`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/sync.rs#L659-L661), [`sync.rs#L731-L768`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/sync.rs#L731-L768)).
3. With a cache: `get_state` again. A merkle equal to the cached last state puts the divergence after the cache; an empty view puts it at 0 ([`sync.rs#L534-L550`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/sync.rs#L534-L550)).
4. Otherwise a binary search over the cached positions. Each probe sends `GET {remote_url}?view={view}&changelist={mid}` and compares the entry at `mid` with the cache; a cache gap counts as a mismatch with no request ([`sync.rs#L552-L611`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/sync.rs#L552-L611)).
5. `GET {remote_url}?view={view}&changelist={divergence}`. Remote entries missing locally are to download; cached entries the remote no longer lists are remote unrecords; the cache is replaced from the divergence point on ([`sync.rs#L680-L714`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/sync.rs#L680-L714)).

`compute_pull_delta` sends one more `get_state` before all of that ([`sync.rs#L776-L784`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/sync.rs#L776-L784)). `compute_push_delta` sends no upload itself: it lists for upload each local `Node` ([client-only types](types.md#client-only-types)) not in the remote's post-divergence set ([`sync.rs#L794-L801`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/sync.rs#L794-L801), [`sync.rs#L350-L361`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/sync.rs#L350-L361)); `Node` equality includes the merkle state, not only the hash ([`types.rs#L88-L100`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L88-L100)). The cache, `RemoteState`, is an in-memory struct ([`sync.rs#L98-L125`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/sync.rs#L98-L125)). The view name goes into both URLs without encoding ([`queries.rs#L29-L30`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/queries.rs#L29-L30), [`queries.rs#L79-L84`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/queries.rs#L79-L84)).

The doc comment says each probe is a `?state=` request; the code sends a `?changelist=` request from `mid` ([`sync.rs#L509-L511`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/sync.rs#L509-L511), [`sync.rs#L573-L576`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/sync.rs#L573-L576)).

## Open questions

- **Pack atomicity.** The client sends every object and ref move in one `POST` ([`services_sync_remote.rs#L864`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L864)). Whether the server stores all of it or none of it when one ref move is refused is not in the source. The test peer checks every ref before storing anything ([`local_sync_test.rs#L176-L200`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/tests/local_sync_test.rs#L176-L200)), but that is a test model.
- **Ref-move rule.** atomic-objects says a ref moves only if `expect_old` is the current target and an ancestor of `new_target` in the `prev` chain ([`sync.rs#L155-L159`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/sync.rs#L155-L159)). The test peer checks only that `expect_old` equals the current target ([`local_sync_test.rs#L176-L179`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/tests/local_sync_test.rs#L176-L179)). Which rule the server enforces is not confirmed.
- **Diverged push.** For a view where each side holds changes the other lacks, the pushed snapshot's `own_changes` is the local log only ([Diverged views](#diverged-views)). The CLI's comments say the server unions the proposal with its current set ([`command.rs#L598-L601`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/push/command.rs#L598-L601), [`helpers.rs#L245-L247`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/push/helpers.rs#L245-L247)). Whether the server unions `own_changes` with the view's current set, or replaces the set with the pushed list, is not in the source; request 4 cannot tell the two apart.
- **Tags under a renamed view.** A pushed `Tag` object's record names the local view, even when `to_view` renames the leaf on the remote ([Building the pack](#building-the-pack)), and the pack carries no ref for a tag. How the server ties a `Tag` object to a view, and what it does when the record's `view` is not a view it holds, is not in the source.
- **Object keys.** The producers key `View` objects by lowercase-hex Blake3 and every other family by a base32 Atomic hash, which is not what `ObjectRecord`'s comment says; the per-family keys are on [ObjectRecord](endpoints/project.md#objectrecord), and the open question is kept once, under [Open questions](endpoints/project.md#open-questions) on project.md.
- **Ancestors in a full pull.** `SyncWants` documents ancestor chains only for `refs_only` ([`sync.rs#L217-L222`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/sync.rs#L217-L222)). Pull and clone fail when an ancestor's ref or snapshot is missing ([`services_sync_remote.rs#L955-L962`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L955-L962); [`command.rs#L598-L606`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L598-L606)). The test peer always includes ancestors ([`local_sync_test.rs#L129-L156`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/tests/local_sync_test.rs#L129-L156)). That the server does the same for a full pull is assumed, not confirmed.
- **What `haves` filters.** Pull sends only change hashes in `haves` ([`services_sync_remote.rs#L1177-L1182`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1177-L1182)). Whether the server then resends every attestation, provenance graph, tag and view snapshot on each pull is server behaviour. The client tolerates resends: sidecars already present are not counted again and existing tags are skipped ([`services_sync_remote.rs#L1037-L1049`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1037-L1049), [`services_sync_remote.rs#L1708-L1710`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1708-L1710)).
- **Object order inside a pack.** The client orders each view's changes before its snapshot, views root to leaf, then attestations, provenance graphs and tags ([`services_sync_remote.rs#L670-L814`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L670-L814)). Whether the server depends on any of this order is not stated.
- **Prefix rule and `--force`.** The push module documents a fast-forward rule (the remote log must be a prefix of the local log) and a `--force` override ([`mod.rs#L33-L34`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/push/mod.rs#L33-L34); [`command.rs#L194-L201`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/push/command.rs#L194-L201)). The planner compares sets, ignores `force`, and never reports divergence ([`helpers.rs#L198-L252`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/push/helpers.rs#L198-L252); [`services_sync_remote.rs#L303-L344`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L303-L344)). This page documents the code.
- **Draft change lists.** Push copies each view's stored log into the snapshot's `own_changes` unchanged ([ViewSnapshot](endpoints/project.md#viewsnapshot)). Source comments disagree on whether a draft's log, and so its `own_changes`, includes the inherited prefix; that open question is kept once, under [Open questions](endpoints/project.md#open-questions) on project.md.
- **Signer lookup endpoint.** Pull's signer discovery sends a `did:atomic:` DID to the by-key lookup, whose argument is documented as a base32 public key ([`resolve_identity_by_public_key`](endpoints/storage.md#resolve_identity_by_public_key)). What the server accepts there is kept once, under [Open questions](endpoints/storage.md#open-questions) on storage.md.
- **Response content type.** The client does not check the `Content-Type` of a sync response ([`code_sync.rs#L97-L108`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/code_sync.rs#L97-L108)). libatomic's test peer sends `application/vnd.atomic.sync.v1` ([`local_sync_test.rs#L164-L167`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/tests/local_sync_test.rs#L164-L167)) and the clone test server sends `application/octet-stream` ([`clone_sidecar_integration_test.rs#L160-L163`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/tests/it/clone_sidecar_integration_test.rs#L160-L163)). What the server sends is not in the source.
- **Unauthenticated push.** The CLI checks credentials first because, it says, the server answers a push without credentials with an ambiguous `404` that masks private projects ([`command.rs#L566-L572`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/push/command.rs#L566-L572)). That is the client's account of the server.
- **Unknown view on pull.** The client treats a requested view missing from the pack as nonexistent ([`services_sync_remote.rs#L1210-L1221`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1210-L1221)). Whether the server answers `200` with no ref or an error status is not in the source.
