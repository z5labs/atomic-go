# Transport

This page describes how the Atomic client talks HTTP to a hosted Atomic server such as atomic.storage: the URLs it builds, the headers it sends, how bodies are compressed, what is and is not streamed, and how versions are negotiated. The client is the `atomic-remote` crate at commit [`a6c3e359456e83cf5a967a2e8265f11e0ba45d80`](https://github.com/atomicdotdev/atomic/commit/a6c3e359456e83cf5a967a2e8265f11e0ba45d80); the crate describes itself as the client side of the remote protocol that `atomic-api` servers serve ([`lib.rs#L1-L4`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/lib.rs#L1-L4)). The server is not in the source. Everything here is the protocol as the client speaks it, and what only the server decides is listed under [Open questions](#open-questions).

Request-by-request detail is in [endpoints/project.md](endpoints/project.md) and [endpoints/storage.md](endpoints/storage.md). How failures are reported is in [errors.md](errors.md), and credentials are in [auth.md](auth.md).

## Two clients

atomic-remote contains two HTTP clients, each with its own reqwest client and its own defaults.

| Client | Talks to | Source |
|---|---|---|
| `HttpRemote` | The project protocol on a project URL: push, pull, clone and view queries. | [`mod.rs#L143-L160`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/mod.rs#L143-L160) |
| `StorageClient` | The atomic-storage management API: workspaces, projects, identities and delegations. The push, pull and clone exchanges do not use it; the one exception is the signer-key lookup after a pull ([Management API base](#management-api-base)). | [`storage.rs#L1-L8`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L1-L8) |

## Server URLs

### Project URL

A project's remote URL is the endpoint of the project protocol. `atomic project create`, `atomic project init` and `atomic project show` build it the same way, from the org base URL of the management client, the workspace slug and the project slug ([`create.rs#L159-L164`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/project/create.rs#L159-L164), [`init.rs#L182-L187`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/project/init.rs#L182-L187), [`rpc.rs#L7350-L7355`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/rpc.rs#L7350-L7355), [`show.rs#L98-L103`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/project/show.rs#L98-L103)):

```text
{org_base_url}/workspaces/{workspace}/projects/{project}/code
```

For example, `https://alice.atomic.storage/workspaces/my-ws/projects/my-app/code` ([`init.rs#L33-L35`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/project/init.rs#L33-L35)). `atomic project init` saves this URL as the repository's `origin` remote, through the service layer's `ManageRemotes` when a service opens and directly otherwise ([`rpc.rs#L7365-L7370`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/rpc.rs#L7365-L7370), [`init.rs#L189-L190`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/project/init.rs#L189-L190)).

The URL ending in `/code` is the one endpoint through which every object and ref of a project moves. A request header selects the binary sync protocol on it; atomic-objects documents that without that header the server answers the same URL with JSON project information ([`sync.rs#L4-L12`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/sync.rs#L4-L12)), which only the server can confirm. See [The sync protocol header](#the-sync-protocol-header).

Doc comments, the crate README and unit tests also show an older path shape, `/tenant/{t}/portfolio/{p}/project/{name}/code` ([`lib.rs#L46-L48`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/lib.rs#L46-L48), [`mod.rs#L149-L153`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/mod.rs#L149-L153), [`README.md#L23-L25`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/README.md?plain=1#L23-L25), [`tests.rs#L97-L102`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/tests.rs#L97-L102)). The URL builders above produce only the `/workspaces/…/projects/…/code` shape, and an integration test clones from that shape ([`clone_sidecar_integration_test.rs#L201-L209`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/tests/it/clone_sidecar_integration_test.rs#L201-L209)). `HttpRemote` itself accepts any URL that parses; it does not check the path ([`mod.rs#L204-L205`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/mod.rs#L204-L205)).

### Org host

The client addresses each org (tenant) of a multi-tenant server on its own host, named by putting the org slug in front of the server's host. `ServerConfig::org_base_url` keeps the scheme, host and port of the configured server URL, adds `{org}.` to the host, and drops any path ([`lib.rs#L141-L173`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-config/src/lib.rs#L141-L173)). The configuration's documentation describes a single-tenant server as one that serves one org at its bare host ([`lib.rs#L125-L132`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-config/src/lib.rs#L125-L132)). The client marks a server single-tenant when the registration response has `mode` set to `single` ([`register.rs#L464-L474`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/identity/register.rs#L464-L474)), and for such a server the configured URL is returned unchanged except for a trailing `/` ([`lib.rs#L154-L158`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-config/src/lib.rs#L154-L158)).

### Apex host

The apex is the server without the org label. The client computes it in two different ways, and the two are documented only here.

**Management apex: the profile URL as configured.** The CLI's apex management clients use the server profile's `url` exactly as configured, with no derivation ([`client.rs#L91-L94`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/client.rs#L91-L94), [`client.rs#L136-L149`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/client.rs#L136-L149)). Management calls that span orgs, such as listing the orgs a user belongs to, go there rather than to an org host ([`client.rs#L61-L68`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/client.rs#L61-L68)); which other endpoints do is on [Base URLs](endpoints/storage.md#base-urls). Both management builders, the org-scoped one included, mint their token for this URL ([`client.rs#L98-L100`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/client.rs#L98-L100), [`client.rs#L223-L224`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/client.rs#L223-L224)).

**Token apex: derived from the project URL.** Push, pull, clone, `view list --remote` and `repo identity adopt` mint their token through `attach_identity` ([`command.rs#L411`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/push/command.rs#L411), [`command.rs#L419`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/pull/command.rs#L419), [`command.rs#L342`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L342), [`list.rs#L474`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/view/list.rs#L474), [`repo.rs#L121`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/repo.rs#L121)); when push and pull run through the service layer, the CLI runs it and hands the resulting headers to the handler ([`rpc.rs#L5265-L5279`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/rpc.rs#L5265-L5279), [`rpc.rs#L5381`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/rpc.rs#L5381), [`rpc.rs#L5664`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/rpc.rs#L5664)). `attach_identity` mints the token for an apex derived from the project URL: the scheme, the host with everything up to and including its first `.` removed when it contains one, and the port if the URL has one; the path is dropped ([`mod.rs#L414-L422`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L414-L422), [`mod.rs#L637-L653`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L637-L653)). The same derived URL is the server a delegated identity's stored certificate must be scoped to ([`mod.rs#L458-L463`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L458-L463)). See [Tokens](auth.md#tokens) and [Choosing a certificate](auth.md#choosing-a-certificate).

The two agree for a multi-tenant server, whose project URLs sit on `{org}.{server host}` ([Org host](#org-host)), and can differ when the project URL's host has no org label, as on a single-tenant server; see [Open questions](#open-questions). The derivation's tests:

### Sibling resources

The `bare` module describes the remaining read-only REST resources next to `/code` under the project path, of which the client uses one ([`bare.rs#L1-L7`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/bare.rs#L1-L7)). `resource_url` builds their URLs from the project URL: it removes one trailing `/`, then a trailing `/code`, then appends the resource path ([`bare.rs#L17-L26`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/bare.rs#L17-L26)). So `https://h/workspaces/w/projects/p/code` plus `refs/views` gives `https://h/workspaces/w/projects/p/refs/views`, and a project URL without `/code` gets the path appended directly ([`bare.rs#L73-L93`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/bare.rs#L73-L93)). The only caller is `list_view_refs`, which reads `GET …/refs/views` ([`bare.rs#L28-L32`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/bare.rs#L28-L32)). Its documentation names `atomic view list --remote` as its user, but pull's set-id check and clone call it too ([`list.rs#L480-L481`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/view/list.rs#L480-L481), [`services_sync_remote.rs#L1592`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1592), [`command.rs#L506`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L506)); see [`list_view_refs`](endpoints/project.md#list_view_refs).

### Management API base

`StorageClient` takes a base URL, trims trailing `/` characters from it, and forms each request URL as the base URL followed by the path, such as `/workspaces` ([`storage.rs#L128-L132`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L128-L132), [`storage.rs#L150-L151`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L150-L151)). The CLI passes the org base URL for org-scoped commands ([`client.rs#L212-L228`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/client.rs#L212-L228)) and the apex for apex-scoped ones ([`client.rs#L91-L104`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/client.rs#L91-L104)). Signer-key discovery instead derives the base URL from a project URL's origin (scheme, host and port) and reuses the bearer token already attached for that remote ([`signer_refresh.rs#L8-L20`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/signer_refresh.rs#L8-L20)). See [Base URLs](endpoints/storage.md#base-urls).

### Choosing a remote URL

Named remotes are stored in the repository's `.atomic/config.toml` under `[remotes]` ([`remote.rs#L9-L19`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/remote.rs#L9-L19)). The only check on a URL is that it contains `://` ([`remote.rs#L218-L220`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/remote.rs#L218-L220), [`remote.rs#L480-L486`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/remote.rs#L480-L486), [`remote.rs#L547-L553`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/remote.rs#L547-L553)). `atomic clone` connects to the URL exactly as given and saves it as `origin` ([`command.rs#L1018`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L1018), [`command.rs#L1096`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L1096)). The daemon's push handler uses the request's `remote_url` if set, else a remote name that contains `://` as the URL, else the named remote's stored URL ([`services_sync_remote.rs#L445-L465`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L445-L465)). None of these paths rewrites the URL before `HttpRemote` parses it.

### Base URL and repository name

`HttpRemote::with_config` parses the URL with the `url` crate and keeps the result as the base URL for every request ([`mod.rs#L204-L205`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/mod.rs#L204-L205), [`mod.rs#L241-L245`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/mod.rs#L241-L245)). A URL that does not parse fails construction ([`tests.rs#L166-L170`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/tests.rs#L166-L170)); see [errors.md](errors.md#error-kinds). The `url` crate (external, version 2.5.8, [`Cargo.lock#L4976-L4977`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.lock#L4976-L4977)) implements the [WHATWG URL Standard](https://url.spec.whatwg.org/), so the base URL is used in its normalised serialisation; for example a bare `https://host` serialises with a trailing `/`.

The client also infers a repository name from the path: the segment before the first `code` or `.atomic` segment, otherwise the last segment that is neither, with a `.git` suffix removed ([`mod.rs#L263-L292`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/mod.rs#L263-L292)). Both `https://api.example.com/tenant/t/portfolio/p/project/myrepo/code` and `…/myrepo/.atomic` give `myrepo`, and `https://example.com/myrepo.git` gives `myrepo` ([`tests.rs#L97-L121`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/tests.rs#L97-L121)). The name is exposed only through `repo_name()` ([`mod.rs#L253-L256`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/mod.rs#L253-L256)) and does not change any request.

## HTTP mechanics

### Building request URLs

A project-protocol query is the base URL's serialisation followed by `?` and the query, built with string formatting. View names, hashes and states go into the query as they are, without percent-encoding, for example `{base}?view={view}&state=` and `{base}?insert={hash}&view={view}` ([`queries.rs#L30`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/queries.rs#L30), [`upload.rs#L43`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/upload.rs#L43)). The sync requests go to the base URL itself ([`code_sync.rs#L43`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/code_sync.rs#L43), [`code_sync.rs#L80`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/code_sync.rs#L80)), and the project-identity requests to the base URL plus `?project-identity=1` ([`identity.rs#L132`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/identity.rs#L132)). On the wire the request target is the path and query, as a test that records the request line shows: `GET /workspaces/w/projects/p/code?project-identity=1` ([`project_identity_transport.rs#L77-L81`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/tests/project_identity_transport.rs#L77-L81)). The full list of query forms is in [endpoints/project.md](endpoints/project.md).

Because the query is appended, a base URL that already has a query string or fragment produces a malformed request. A Go client should build these URLs the same way, from a base URL without a query, and should not escape the values differently from the Rust client; see [Open questions](#open-questions).

`StorageClient` percent-encodes some values with the `urlencoding` crate, such as the email in `/identities/resolve?email=` and a delegation ID in a path ([`storage.rs#L415-L418`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L415-L418), [`storage.rs#L490-L492`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L490-L492)), and inserts others unescaped, such as workspace slugs ([`storage.rs#L325-L327`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L325-L327)). [endpoints/storage.md](endpoints/storage.md) gives each path.

### TLS

The only TLS setting is `danger_accept_invalid_certs`, which disables certificate verification and defaults to off ([`mod.rs#L87-L88`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/mod.rs#L87-L88), [`mod.rs#L123-L130`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/mod.rs#L123-L130), [`mod.rs#L229`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/mod.rs#L229)). The CLI sets it with `-k`/`--insecure` ([`command.rs#L210-L214`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/push/command.rs#L210-L214), [`command.rs#L237-L242`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/pull/command.rs#L237-L242), [`command.rs#L148-L153`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L148-L153)), and the daemon from the request's `insecure` field ([`services_sync_remote.rs#L148-L150`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L148-L150)). `StorageClient` has no such option ([`storage.rs#L122-L126`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L122-L126)). No custom root certificates or client certificates are configured on either client. In Go, the equivalent of `danger_accept_invalid_certs` is `tls.Config.InsecureSkipVerify`.

### Redirects, proxies and HTTP version

Neither client sets a redirect policy, a proxy or an HTTP version ([`mod.rs#L226-L233`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/mod.rs#L226-L233), [`storage.rs#L122-L126`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L122-L126)), so reqwest's defaults apply (external; reqwest 0.12.28, [`Cargo.lock#L3677-L3678`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.lock#L3677-L3678)):

- Redirects are followed, up to 10 hops ([`reqwest::redirect`](https://docs.rs/reqwest/0.12.28/reqwest/redirect/index.html)). On a redirect to a different host or port reqwest removes `Authorization`, `Cookie`, `Proxy-Authorization` and `WWW-Authenticate`, and keeps every other header, including `Atomic-Delegation` ([`redirect.rs`](https://docs.rs/crate/reqwest/0.12.28/source/src/redirect.rs) `remove_sensitive_headers`).
- reqwest's default features, which the workspace leaves on ([`Cargo.toml#L103`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.toml#L103)), include `system-proxy` and `http2` ([reqwest 0.12.28 features](https://docs.rs/crate/reqwest/0.12.28/features)): proxies come from the environment and the operating system, and HTTP/2 is used when the server offers it.
- A URL with userinfo, such as `http://bob@alice.localhost:8080/…`, which the client accepts as a way to choose an identity ([`mod.rs#L11-L14`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L11-L14)), makes reqwest add `Authorization: Basic …` built from the userinfo to each request ([`request.rs`](https://docs.rs/crate/reqwest/0.12.28/source/src/async_impl/request.rs) `extract_authority`). That per-request header takes the place of the default `Authorization: Bearer` header; see [Open questions](#open-questions).

### Retries

The client does not retry. Each method sends its request once and returns the first error ([`queries.rs#L33-L38`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/queries.rs#L33-L38)). `RemoteError::is_retryable()` reports `ConnectionFailed` and `Timeout` as retryable ([`error.rs#L336-L342`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/error.rs#L336-L342)), but no code in the workspace outside atomic-remote's own tests calls it. A Go client may retry idempotent reads; it must not assume a retried upload is a no-op unless the endpoint says so (for example, `store_change` is documented as idempotent, [`upload.rs#L91-L98`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/upload.rs#L91-L98)).

### Reading responses

Every response body is read whole into memory, with `.text()`, `.bytes()` or `.json()` ([`queries.rs#L46-L49`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/queries.rs#L46-L49), [`queries.rs#L190-L193`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/queries.rs#L190-L193), [`code_sync.rs#L59`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/code_sync.rs#L59), [`code_sync.rs#L99-L102`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/code_sync.rs#L99-L102), [`identity.rs#L141-L143`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/identity.rs#L141-L143)). An error body is read as text, and a body that cannot be read becomes an empty message ([`queries.rs#L58-L65`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/queries.rs#L58-L65)). reqwest's `.text()` decodes with the charset named in the response's `Content-Type` and falls back to UTF-8 (external; [`Response::text`](https://docs.rs/reqwest/0.12.28/reqwest/struct.Response.html#method.text)), so a server should send text as UTF-8. Status handling per request is in [Error responses](errors.md#error-responses).

## Compression

**Responses.** `HttpRemote` sends `Accept-Encoding: zstd, gzip, deflate` and turns on reqwest's automatic gzip and deflate decoding ([`mod.rs#L71-L72`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/mod.rs#L71-L72), [`mod.rs#L210-L213`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/mod.rs#L210-L213), [`mod.rs#L231-L232`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/mod.rs#L231-L232)), with reqwest's `gzip` and `deflate` features enabled for the crate ([`Cargo.toml#L21`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/Cargo.toml#L21)). No crate enables reqwest's `zstd` feature ([`Cargo.toml#L103`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.toml#L103), [`Cargo.toml#L77`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/Cargo.toml#L77), [`Cargo.toml#L64`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/Cargo.toml#L64)), and the only decompression codec crate in the lock file depends on `flate2` alone ([`Cargo.lock#L887-L895`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.lock#L887-L895)). reqwest disables zstd decoding unless its own `zstd` feature is on (external; [`client.rs`](https://docs.rs/crate/reqwest/0.12.28/source/src/async_impl/client.rs), where the decompression layer is built with `.no_zstd()`). So the Rust client advertises zstd but cannot decode it: a response with `Content-Encoding: zstd` reaches its parsers still compressed. A Go client should either advertise only the encodings it decodes or decode zstd itself; see [Open questions](#open-questions).

Because `HttpRemote` sets `Accept-Encoding` itself, reqwest does not replace it; reqwest's decompression layer fills the header only when it is absent (external; [tower-http 0.6.11](https://docs.rs/crate/tower-http/0.6.11/source/src/decompression/service.rs), [`Cargo.lock#L4668-L4669`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.lock#L4668-L4669)). `StorageClient` sets no `Accept-Encoding`, so its requests carry the one reqwest generates for gzip and deflate, `gzip,deflate`, and its responses are decoded the same way (external; [tower-http `compression_utils.rs`](https://docs.rs/crate/tower-http/0.6.11/source/src/compression_utils.rs) `to_header_value`; reqwest enables gzip and deflate decoding by default when the features are on, [`ClientBuilder::gzip`](https://docs.rs/reqwest/0.12.28/reqwest/struct.ClientBuilder.html#method.gzip)).

**Requests.** No request body is HTTP-compressed. The client never sets `Content-Encoding` (see the request headers above), and reqwest does not compress request bodies (external; [`ClientBuilder::gzip`](https://docs.rs/reqwest/0.12.28/reqwest/struct.ClientBuilder.html#method.gzip): "The request body is **not** automatically compressed").

**Application-level compression.** The sync bodies on `/code` are compressed by Atomic itself, not by HTTP. A `SyncPack` or `SyncWants` is serialised with postcard and the result is compressed as one zstd frame at level 3; the compressed bytes are the HTTP body ([`sync.rs#L31-L37`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/sync.rs#L31-L37), [`sync.rs#L58-L60`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/sync.rs#L58-L60), [`sync.rs#L299-L307`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/sync.rs#L299-L307)). Decoding inflates at most 2 GiB and refuses a larger body ([`sync.rs#L62-L65`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/sync.rs#L62-L65), [`sync.rs#L316-L341`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/sync.rs#L316-L341)). A test confirms the body is smaller than the raw postcard bytes for repetitive input ([`sync.rs#L421-L441`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/sync.rs#L421-L441)), and garbage that is not a zstd frame fails to decode ([`sync.rs#L460-L463`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/sync.rs#L460-L463)). The zstd frame format is external, the [Zstandard format, RFC 8878](https://www.rfc-editor.org/rfc/rfc8878), produced by the `zstd` crate 0.14.3 ([`Cargo.lock#L5652-L5653`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.lock#L5652-L5653)); postcard is pinned at 1.1.3 ([`Cargo.lock#L2938-L2939`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.lock#L2938-L2939)). The structure inside is described under [SyncPack](endpoints/project.md#syncpack), [SyncWants](endpoints/project.md#syncwants) and [Postcard encoding](change-format/container.md#postcard-encoding).

Change files are uploaded as their raw bytes with `Content-Type: application/octet-stream`, and downloaded as raw bytes ([`upload.rs#L46-L50`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/upload.rs#L46-L50), [`queries.rs#L189-L196`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/queries.rs#L189-L196)). The client adds no compression of its own around them. Their per-section zstd compression is part of the file, not of HTTP; see [the container's compression](change-format/container.md#compression).

## Streaming

The `streaming` module describes itself as the protocol for streaming V3 change files over HTTP without buffering whole bodies ([`mod.rs#L1-L19`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/streaming/mod.rs#L1-L19)). At this commit only one request body is actually streamed, and no response is.

**Streamed: one upload.** `upload_change_streamed` opens a change file, wraps it in a byte stream as the request body, and sets `Content-Length` to the file size and `Content-Type` to `application/octet-stream` ([`upload.rs#L437-L471`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/upload.rs#L437-L471)). Its URL and status handling are those of `upload_change`, `{base}?insert={hash}&view={view}` ([`upload.rs#L443`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/upload.rs#L443), [`upload.rs#L476-L503`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/upload.rs#L476-L503)). `upload_change_file` is a wrapper around it ([`upload.rs#L522-L529`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/upload.rs#L522-L529)). Because the length is set, the body has a fixed length rather than an unknown one. It is the only stream body in the client, and no code sets `Transfer-Encoding` ([`upload.rs#L460-L461`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/upload.rs#L460-L461)). On the wire this request is identical to `upload_change` with the same bytes, so a Go client can send either an in-memory buffer or an `io.Reader` with `ContentLength` set.

**Not streamed:**

- **Responses.** Every method reads the response body whole before using it ([Reading responses](#reading-responses)).
- **`download_change_to_file`.** Its documentation says it avoids holding the whole change in memory ([`download.rs#L18-L22`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/download.rs#L18-L22)), but the code reads the whole body into memory, creates the parent directory, and then writes the file ([`download.rs#L47-L72`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/download.rs#L47-L72)).
- **Push, pull and clone.** `sync_push` encodes the whole pack in memory and sends it as one body; `sync_pull` reads the whole response and then decodes it ([`code_sync.rs#L44-L52`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/code_sync.rs#L44-L52), [`code_sync.rs#L99-L103`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/code_sync.rs#L99-L103)).
- **Content chunks.** No request uploads or downloads an individual chunk; see [Delta transfer negotiation](#delta-transfer-negotiation).

### Chunk manifests

`get_chunk_manifest` requests `{base}?change={hash}&manifest` ([`download.rs#L171-L172`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/download.rs#L171-L172)). The manifest lists the content chunks of a change with their blake3 hashes and sizes, and is documented as the starting point for delta transfer ([`download.rs#L155-L170`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/download.rs#L155-L170)). The client handles the response as follows ([`download.rs#L185-L235`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/download.rs#L185-L235)):

| Response | Result |
|---|---|
| `200`, `Content-Type` contains `json` | The body is parsed as a [ChunkManifest](endpoints/project.md#chunkmanifest); a parse failure is a protocol error. |
| `200`, any other `Content-Type` | No manifest. The client takes it that the server ignored `&manifest` and returned the change itself. |
| `400` | No manifest; treated as "likely unsupported". |
| `404` | `ChangeNotFound`. |
| `401`, `403` | `AuthenticationFailed`. |
| anything else | `HttpError`. |

The JSON shape, from the type's documentation ([`layers.rs#L232-L243`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/streaming/layers.rs#L232-L243)):

```json
{
  "entries": [
    {"index": 0, "hash": "aabb...", "compressed_size": 32000, "uncompressed_size": 65536},
    {"index": 1, "hash": "ccdd...", "compressed_size": 28000, "uncompressed_size": 65536}
  ]
}
```

Each entry is a [ChunkManifestEntry](types.md#chunkmanifestentry): `hash` is 64 lowercase hex characters, the blake3 hash of the uncompressed chunk ([`types.rs#L104-L121`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/streaming/types.rs#L104-L121), [`types.rs#L168-L205`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/streaming/types.rs#L168-L205)). How a change file is cut into chunks is part of the file format; see [Content chunking](change-format/container.md#content-chunking). Outside atomic-remote, only a CLI test fixture calls `get_chunk_manifest` ([`helpers_c5.rs#L365`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/tests/fixtures/helpers_c5.rs#L365)).

### Delta transfer negotiation

`ChunkNegotiation` is documented as a "have" exchange: one side sends a manifest, the other the chunk hashes it already holds, and only the rest is transferred ([`negotiation.rs#L18-L38`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/streaming/negotiation.rs#L18-L38)). In the code it is a local computation only. `ChunkNegotiation::compute` takes a manifest and a list of hashes, keeps manifest entries whose hash is not in the list, in manifest order, and sums compressed sizes for the kept and skipped entries ([`negotiation.rs#L80-L120`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/streaming/negotiation.rs#L80-L120)). No `HttpRemote` method sends a have list, receives a need list, or transfers a single chunk: the only chunk-related request is the manifest `GET` above ([`download.rs#L155-L172`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/download.rs#L155-L172)). `StreamingPushOptions` and `StreamingPullOptions`, whose defaults turn delta transfer on for push and off for pull ([`negotiation.rs#L228-L236`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/streaming/negotiation.rs#L228-L236), [`negotiation.rs#L335-L344`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/streaming/negotiation.rs#L335-L344)), are not taken by any `HttpRemote` method; outside the streaming module the crate only re-exports them ([`lib.rs#L164-L168`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/lib.rs#L164-L168)). A Go client has no chunk-level transfer to implement at this commit; push and pull move whole objects through `/code`, and the `/code` exchange has its own have/want negotiation of whole objects ([`sync.rs#L26-L29`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/sync.rs#L26-L29), [`sync.rs#L206-L225`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/sync.rs#L206-L225)). See [flows.md](flows.md#push).

### Progress

`TransferProgress` (events: started, section complete, chunk complete, finished) and `TransferStats` (a summary of sections, chunks and bytes) are in-process types for progress output ([`progress.rs#L15-L67`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/streaming/progress.rs#L15-L67), [`progress.rs#L118-L159`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/streaming/progress.rs#L118-L159)). They have no wire form, and no `HttpRemote` method produces them.

## Version negotiation

The client has no version handshake. Two mechanisms carry version information: a response header that triggers an upgrade warning, and a request header that names the sync wire format.

### `X-Atomic-Min-Version`

The server may send `X-Atomic-Min-Version` on a response to state the oldest CLI version it supports ([`version.rs#L1-L5`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/version.rs#L1-L5)). The client looks it up as `x-atomic-min-version` ([`version.rs#L37-L43`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/version.rs#L37-L43), [`version.rs#L50-L51`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/version.rs#L50-L51)); header names are case-insensitive, so any spelling matches.

**When it is read.** `HttpRemote` checks it on every response from the query, download, upload and sync methods, right after the response arrives and before the status is looked at, so error responses are checked too ([`queries.rs#L40-L44`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/queries.rs#L40-L44), [`upload.rs#L55-L58`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/upload.rs#L55-L58), [`code_sync.rs#L56-L57`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/code_sync.rs#L56-L57)). `StorageClient` checks it on every response ([`storage.rs#L231`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L231), [`storage.rs#L246`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L246)). `fetch_project_identity`, `bind_project_identity` and `list_view_refs` do not check it ([`identity.rs#L133-L139`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/identity.rs#L133-L139), [`identity.rs#L173-L181`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/identity.rs#L173-L181), [`bare.rs#L34-L40`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/bare.rs#L34-L40)).

**What the client does.** If the running version is older than the header's value, the client prints this line to standard error and carries on; the request neither fails nor changes ([`version.rs#L45-L65`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/version.rs#L45-L65)):

```text
warning: this server requires Atomic CLI >= {min} (you have {current}). Run 'atomic update' to upgrade.
```

An absent header, a value that cannot be read as a string, or a version that does not parse produces no warning ([`version.rs#L45-L49`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/version.rs#L45-L49), [`version.rs#L53-L56`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/version.rs#L53-L56)). The running version is the crate version ([`lib.rs#L177-L178`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/lib.rs#L177-L178)), which is 0.22.1 at this commit ([`Cargo.toml#L22`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.toml#L22)). In addition, `sync_pull` keeps the header's raw value and, if the returned pack fails to decode, puts it in a `VersionMismatch` error ([`code_sync.rs#L94-L108`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/code_sync.rs#L94-L108)); see [Error kinds](errors.md#error-kinds).

**How versions compare.** `needs_upgrade(current, required)` returns true only when both versions parse and `current < required` ([`version.rs#L9-L31`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/version.rs#L9-L31)). Parsing trims whitespace, splits on `.` into at most four parts, and reads the first three as unsigned 32-bit integers ([`version.rs#L19-L25`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/version.rs#L19-L25)). A missing minor or patch part counts as 0. Anything after the third dot is ignored. If any of the first three parts present fails to parse, including an empty part, a `v` prefix or a pre-release suffix such as `3-rc1`, the version does not parse. The triples compare major first, then minor, then patch. The tests:

### The sync protocol header

The request header `Atomic-Protocol: sync/1` selects the binary sync exchange on `…/code`; without it, according to atomic-objects, the endpoint gives its default JSON project-info or browse response ([`sync.rs#L44-L52`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/sync.rs#L44-L52)). The value's suffix is to be bumped on any wire-breaking change, "so an old server rejects (and an old client is told to upgrade via `X-Atomic-Min-Version`)" ([`sync.rs#L49-L52`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/sync.rs#L49-L52)). The client only ever sends `sync/1` ([`code_sync.rs#L50`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/code_sync.rs#L50), [`code_sync.rs#L87`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/code_sync.rs#L87)). How a server rejects an unknown value is not in the source. A test shows the JSON an older server returns for `GET …/code` without the header: `{"workspace": "w", "project": "p", "stack": "dev"}` ([`project_identity_transport.rs#L93-L104`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/tests/project_identity_transport.rs#L93-L104)).

### No other negotiation

The crate declares `PROTOCOL_VERSION = 1`, "used for compatibility checking with remote servers" ([`lib.rs#L172-L175`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/lib.rs#L172-L175)), but no code sends or compares it. Apart from `User-Agent`, the client sends no version information. There is no capability request.

## Open questions

- **zstd response encoding.** `HttpRemote` advertises `zstd` in `Accept-Encoding` ([`mod.rs#L71-L72`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/mod.rs#L71-L72)) but its reqwest build cannot decode it ([`Cargo.toml#L21`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/Cargo.toml#L21), [`Cargo.lock#L887-L895`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.lock#L887-L895)). Whether the server ever answers with `Content-Encoding: zstd` is decided by the server. If it did, today's CLI would hand compressed bytes to its parsers. A Go client should either decode zstd or not advertise it.
- **Escaping in query values.** The client inserts view names, hashes and states into the query without percent-encoding ([`queries.rs#L30`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/queries.rs#L30)). How the server decodes `%xx` and `+`, and whether view names may contain characters such as `&`, `#`, `=`, `+` or spaces, is not in the source. Change hashes are base32 (`A-Z2-7`) and need no escaping ([`upload.rs#L22-L23`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/upload.rs#L22-L23)).
- **A `GET` with a body.** `sync_pull` sends its `SyncWants` in the body of a `GET` ([`code_sync.rs#L84-L90`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/code_sync.rs#L84-L90)). Whether the server also accepts the same exchange some other way, and how proxies in front of a hosted server treat it, is not in the source.
- **Unknown sync protocol versions.** The source says an old server rejects a newer `Atomic-Protocol` value ([`sync.rs#L49-L52`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/sync.rs#L49-L52)), but not with which status or body.
- **`X-Atomic-Min-Version`.** Which responses carry the header, and whether the server ever refuses an old client outright rather than only advertising a minimum, is decided by the server. The client only warns ([`version.rs#L45-L65`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/version.rs#L45-L65)).
- **Chunk-level transfer.** The streaming module documents a have/need negotiation and per-chunk transfer ([`negotiation.rs#L18-L38`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/streaming/negotiation.rs#L18-L38)), but the client has no request for either. Whether the server implements such endpoints is not in the source.
- **Layer-selective responses.** What the server returns for `?layers=` is kept once, under [Open questions](endpoints/project.md#open-questions) on project.md.
- **`download_change_to_file` buffering.** Its documentation and its code disagree; this page documents the code ([Streaming](#streaming)), and the disagreement is kept once, under [Open questions](endpoints/project.md#open-questions) on project.md.
- **`?provenance-list` on older servers.** Its documentation and its status handling disagree; the question is kept once, under [Open questions](endpoints/project.md#open-questions) on project.md.
- **The legacy `tenant/portfolio/project` path.** Examples still use `/tenant/{t}/portfolio/{p}/project/{name}/code` ([`README.md#L23-L25`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/README.md?plain=1#L23-L25)), and a harness script uses a third shape, `${SERVER_URL}/${ORG_NAME}/${WORKSPACE_NAME}/${PROJECT_NAME}/code` ([`47_project_identity_transport.sh#L41`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/tests/harness/47_project_identity_transport.sh#L41)), while the URL builders produce only `/workspaces/{w}/projects/{p}/code` ([Project URL](#project-url)). Whether current servers still serve the other shapes is not in the source.
- **Apex derivation for hosts without an org label.** The token apex drops the first host label whenever the host has a dot ([`mod.rs#L642-L647`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L642-L647)), while the management apex is the configured URL unchanged ([Apex host](#apex-host)). So a single-tenant project URL on `storage.acme.com`, which the org base URL keeps as it is ([`lib.rs#L154-L158`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-config/src/lib.rs#L154-L158)), would give push, pull and clone the token audience `https://acme.com` while management tokens name `https://storage.acme.com`. By the same rule a project URL on `atomic.storage` itself would give `https://storage`, and an IPv4 host such as `127.0.0.1` would give `0.0.1`. The tests cover only org hosts and a bare `localhost` ([`mod.rs#L682-L704`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L682-L704)). A delegated identity's stored certificate scoped to the configured server would also fail to match the derived URL when it is selected ([`delegation.rs#L123-L132`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/delegation.rs#L123-L132)). Whether this is intended, and which audience the server expects, is not in the source. See [Audience](auth.md#audience).
- **URL userinfo and `Authorization`.** The client resolves an identity from URL userinfo ([Choosing an identity](auth.md#choosing-an-identity)) and attaches a bearer token as a default header ([`mod.rs#L11-L14`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L11-L14), [`mod.rs#L428`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L428)). Nothing removes the userinfo before `HttpRemote` parses the URL ([Choosing a remote URL](#choosing-a-remote-url)), and request URLs are built from the full base URL ([`identity.rs#L132`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/identity.rs#L132)). reqwest turns the userinfo into a per-request `Authorization: Basic` header (external; [`request.rs`](https://docs.rs/crate/reqwest/0.12.28/source/src/async_impl/request.rs) `extract_authority`), and a client-level default header never overwrites a header already on the request ([`client.rs`](https://docs.rs/crate/reqwest/0.12.28/source/src/async_impl/client.rs) `execute_request`). A `bob@host` URL would therefore seem to send Basic credentials in place of the bearer token. No test covers this, and whether such requests authenticate at all depends on the server. A Go client should remove userinfo from the URLs it requests.
- **Redirects.** Whether the server ever redirects is not in the source. If it redirects across hosts, reqwest drops `Authorization` but forwards `Atomic-Delegation` (external; [`redirect.rs`](https://docs.rs/crate/reqwest/0.12.28/source/src/redirect.rs)).
- **User-Agent spelling.** `HttpRemote` sends `atomic-{version}` and `StorageClient` sends `atomic/{version}` ([`mod.rs#L59`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/mod.rs#L59), [`storage.rs#L120`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L120)). The source says servers use the user agent to recognise the CLI ([`mod.rs#L55-L58`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/mod.rs#L55-L58)); which forms a server recognises, and what it does differently for a browser, is not in the source.
