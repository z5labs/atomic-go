# Authentication and identity

This page describes how the Atomic client proves who it is to a hosted Atomic server such as atomic.storage. The client signs a short-lived JWT itself, with the identity's Ed25519 private key, and sends it as `Authorization: Bearer` [`mod.rs#L1-L9`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L1-L9). There is no login endpoint and no token cache [`token.rs#L3-L6`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L3-L6). A delegated agent identity also sends a delegation certificate, signed by the human it works for, in an `Atomic-Delegation` header [`mod.rs#L458-L461`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L458-L461) [`mod.rs#L430-L439`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L430-L439).

The server is not in the source. This page documents what the client sends and how it builds each credential. What the server checks is given only where the source states it, and each such statement says whose claim it is. Gaps are listed under [Open questions](#open-questions).

## Identities and DIDs

### Keys and key encodings

Every identity is an Ed25519 key pair. A public key is 32 bytes [`keypair.rs#L27-L29`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/keypair.rs#L27-L29), a secret key is a 32-byte seed [`keypair.rs#L157-L159`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/keypair.rs#L157-L159), and a signature is 64 bytes [`keypair.rs#L188-L192`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/keypair.rs#L188-L192). The Ed25519 implementation is the external `ed25519-dalek` crate [`keypair.rs#L6`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/keypair.rs#L6), version 3.0.0 [`Cargo.lock#L1326-L1327`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.lock#L1326-L1327), which implements standard Ed25519 ([RFC 8032](https://www.rfc-editor.org/rfc/rfc8032)).

The text form of a public key is unpadded base32 [`keypair.rs#L51-L54`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/keypair.rs#L51-L54). That is `BASE32_NOPAD` from the external `data-encoding` crate, version 2.11.1 [`Cargo.lock#L1174-L1175`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.lock#L1174-L1175) ([`BASE32_NOPAD`](https://docs.rs/data-encoding/2.11.1/data_encoding/constant.BASE32_NOPAD.html)), the RFC 4648 base32 alphabet `A-Z2-7` without `=` padding ([RFC 4648 §6](https://www.rfc-editor.org/rfc/rfc4648#section-6)). A 32-byte value always encodes to 52 uppercase characters; atomic-core's strict decoder for that encoding states the length and alphabet [`project_id.rs#L10-L30`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/kg/project_id.rs#L10-L30), and the server's identity record documents its key the same way [`storage_types.rs#L129`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage_types.rs#L129). Decoding a key requires exactly 32 bytes [`keypair.rs#L92-L108`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/keypair.rs#L92-L108). In JSON, a public key is that base32 string [`keypair.rs#L123-L134`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/keypair.rs#L123-L134). `BASE32_NOPAD` decodes only the upper-case alphabet, and it refuses a last character whose unused low bits aren't zero: its specification has no case translation, and `Specification::new` turns trailing-bit checking on (external: data-encoding 2.11.1, [`lib.rs#L2254-L2264`](https://github.com/ia0/data-encoding/blob/834737d9c3dc957ce1b653959e3f35061dd77ade/lib/src/lib.rs#L2254-L2264), [`lib.rs#L1898-L1908`](https://github.com/ia0/data-encoding/blob/834737d9c3dc957ce1b653959e3f35061dd77ade/lib/src/lib.rs#L1898-L1908)). Write keys and ids in canonical upper case. This codec is not the one atomic-core uses for change and state hashes, which decodes either case; see [Base32 hash text](types.md#base32-hash-text).

The same 52-character string is the JWT `kid` and `sub` ([Tokens](#tokens)), the `public_key` of a [registration](#registration), the `publicKey` of an agent enrollment [`storage_types.rs#L560-L569`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage_types.rs#L560-L569), and the path segment of the by-key lookup [`storage.rs#L538-L551`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L538-L551).

### Identity ids

An identity's id is the BLAKE3 hash of its 32 public-key bytes [`identity.rs#L40-L59`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/identity.rs#L40-L59), written as unpadded base32 [`identity.rs#L71-L74`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/identity.rs#L71-L74). BLAKE3 comes from the external `blake3` crate, version 1.8.7 [`Cargo.lock#L656-L657`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.lock#L656-L657), whose `hash` returns 32 bytes ([`blake3::hash`](https://docs.rs/blake3/1.8.7/blake3/fn.hash.html)). See [IdentityId](#identityid).

This id is computed on the client. The server's own records use UUIDs: `IdentityInfo.id` [`storage_types.rs#L124-L128`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage_types.rs#L124-L128) and `AgentIdentityInfo.id` and `parent_identity_id` [`storage_types.rs#L145-L151`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage_types.rs#L145-L151). Don't confuse the two.

### DID forms

| Form | String | Can the key be recovered? | Source |
|---|---|---|---|
| `did:atomic` | `did:atomic:` followed by the unpadded base32 [identity id](#identity-ids), that is base32(BLAKE3(public key)) | No. It is a fingerprint | [`identity.rs#L99-L110`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/identity.rs#L99-L110) |
| `did:key` | `did:key:z` followed by base58btc(`0xED 0x01` followed by the 32 key bytes). Ed25519 keys always give the prefix `did:key:z6Mk` | Yes | [`keypair.rs#L14-L18`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/keypair.rs#L14-L18) [`keypair.rs#L56-L68`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/keypair.rs#L56-L68) [`delegation.rs#L927-L937`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L927-L937) |

- `did:atomic` is Atomic's own method. The DID is the identity id with a prefix, not a second derivation [`identity.rs#L99-L110`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/identity.rs#L99-L110). Parsing strips `did:atomic:` and decodes the rest as base32 [`identity.rs#L112-L118`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/identity.rs#L112-L118).
- `did:key` is the standard method ([did:key](https://w3c-ccg.github.io/did-method-key/)). The bytes `0xED 0x01` are the multicodec varint for `ed25519-pub`, and `z` is the multibase prefix for base58btc [`keypair.rs#L56-L68`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/keypair.rs#L56-L68). Base58btc is the external `bs58` crate, version 0.5.1 [`Cargo.lock#L678-L679`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.lock#L678-L679), with its default Bitcoin alphabet ([`bs58`](https://docs.rs/bs58/0.5.1/bs58/)). Parsing requires the `did:key:` prefix, the `z`, the two multicodec bytes and a 32-byte key [`keypair.rs#L70-L90`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/keypair.rs#L70-L90).
- A proof's verification method is the DID followed by `#key-1` [`did.rs#L44-L47`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/did.rs#L44-L47). A DID matches a key when it equals either form for that key [`did.rs#L54-L58`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/did.rs#L54-L58).
- A delegation certificate carries both forms for both parties, because a `did:atomic` alone cannot verify anything [`delegation.rs#L530-L553`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L530-L553). Proofs name the signer by `did:atomic` [`proof.rs#L170-L178`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/proof.rs#L170-L178) [`did.rs#L33-L35`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/did.rs#L33-L35). An enrolled agent's `did` field is a `did:atomic` [`storage_types.rs#L148-L149`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage_types.rs#L148-L149). So is a change signature's `signer_did` [`section.rs#L509-L512`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/section.rs#L509-L512).

### Identity types

An identity is a `user`, an `agent` or a `delegated` identity; the type serializes in snake_case [`identity.rs#L138-L162`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/identity.rs#L138-L162). See [IdentityType](#identitytype).

Only `delegated` changes what goes on the wire. `is_delegated` is true for `Delegated` alone [`identity.rs#L186-L190`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/identity.rs#L186-L190). For a delegated identity the client puts the human's key in the token's `sub`, adds `act` and `dlg` [`token.rs#L138-L159`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L138-L159), and sends a certificate [`mod.rs#L458-L461`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L458-L461). A standalone `agent` identity signs its token exactly like a user, with its own key in `sub`. The type itself is never sent: the claims have no field for it [`token.rs#L72-L95`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L72-L95).

The delegation module's model, which describes the server's side, says the human is the delegator and holds the grants on the server, the agent holds none, and what the agent may do is the intersection of the human's grants and the certificate's scope [`delegation.rs#L16-L31`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L16-L31). The client's type for an enrolled agent says an agent is never a tenant [`storage_types.rs#L138-L144`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage_types.rs#L138-L144).

Calling `delegated_by` on the identity builder forces the type to `Delegated` [`identity.rs#L481-L486`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/identity.rs#L481-L486). `atomic identity agent create` builds every agent this way, names it `<human>+<name>`, and refuses an agent as the delegator [`create.rs#L124-L162`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/identity/agent/create.rs#L124-L162).

### Registration

A human identity becomes known to a server through `atomic identity register <server-url>`. The CLI POSTs a signed JSON body to `{server_url}/register` with no `Authorization` header: the body's signature is the credential [`register.rs#L183-L196`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/identity/register.rs#L183-L196). Agent and delegated identities are refused before any request, because registering creates a tenant [`register.rs#L138-L153`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/identity/register.rs#L138-L153). The endpoint, its request body fields and its response are documented once, under [`execute`](endpoints/storage.md#execute). This section owns what is signed and how.

The client signs four lines joined by `\n`, with no trailing newline [`register.rs#L56-L57`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/identity/register.rs#L56-L57) [`register.rs#L163-L172`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/identity/register.rs#L163-L172):

```text
atomic-storage:register
{username}
{public_key_base32}
{timestamp}
```

`username` is the identity's name and `timestamp` is the current UTC time in RFC 3339 with whole seconds and a `Z` suffix, for example `2026-11-24T09:30:00Z` [`register.rs#L164-L167`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/identity/register.rs#L164-L167). The signature is Ed25519 over the UTF-8 bytes of that text, encoded as unpadded base32, not base64url [`register.rs#L170-L172`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/identity/register.rs#L170-L172). It goes in the body's `signature` field, and the body's `username`, `public_key` and `timestamp` fields carry lines 2 to 4 unchanged [`register.rs#L174-L181`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/identity/register.rs#L174-L181). The body's `email` is not part of the signed text. A unit test pins the exact bytes for one input [`register.rs#L480-L491`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/identity/register.rs#L480-L491):

```text
atomic-storage:register
alice
ABCDEF1234567890
2025-03-26T17:00:00Z
```

### Key lookup

Because `did:atomic` is a fingerprint, verifying a signed object means getting the key from somewhere else. The management client resolves a key by base32 public key or by DID. The by-DID lookup counts as a success only when the returned `publicKey` matches the DID [`storage.rs#L553-L575`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L553-L575) [`storage.rs#L585-L598`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L585-L598). See [`resolve_identity_by_public_key`](endpoints/storage.md#resolve_identity_by_public_key) and [`resolve_identity_by_did`](endpoints/storage.md#resolve_identity_by_did).

### Choosing an identity

This is client policy, not wire format. A Go client that wants the same behaviour as the Rust client picks the identity for a repository URL in this order [`mod.rs#L95-L113`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L95-L113) [`mod.rs#L185-L204`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L185-L204):

1. An explicit override (`--identity`).
2. The `ATOMIC_AGENT_IDENTITY` environment variable, when it isn't empty after trimming [`mod.rs#L102-L111`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L102-L111).
3. The username in the URL's userinfo, as in `http://bob@alice.localhost:8080/...` [`mod.rs#L188-L192`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L188-L192). See [Open questions](transport.md#open-questions) on transport.md before you send such a URL.
4. The configured server profile whose host is the longest dot-boundary suffix of the remote host. The active profile wins a tie, and the profile's agent identity is preferred over its human identity [`mod.rs#L216-L239`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L216-L239).
5. The first DNS label of the host, as in `alice` from `alice.atomic.storage`. A host with no dot gives no name [`mod.rs#L202-L203`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L202-L203) [`mod.rs#L655-L672`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L655-L672).

The name is then looked up exactly, then case-insensitively [`mod.rs#L248-L259`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L248-L259). An inferred name that matches no local identity falls back to the default identity. Only `--identity` counts as explicit; a name from `ATOMIC_AGENT_IDENTITY` is treated as inferred and can fall back [`mod.rs#L396`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L396). An explicit override never falls back [`mod.rs#L334-L354`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L334-L354); tests cover each case [`mod.rs#L832-L906`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L832-L906).

Management commands choose differently: the server profile's `identity`, else the default identity [`client.rs#L233-L260`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/client.rs#L233-L260). They never use the profile's agent identity, because only the human may enroll, renew or revoke a delegation [`mod.rs#L67-L74`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L67-L74).

### Project identity

A project identity is not an authentication identity. It is a JSON-LD `atomic:ProjectIdentity` document that names a project lineage by a random 32-byte id [`project_identity.rs#L35-L45`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/repository/project_identity.rs#L35-L45) [`project_id.rs#L32-L46`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/kg/project_id.rs#L32-L46). The client reads it and offers it on the project URL with `?project-identity=1`, using the same credentials as the rest of the project protocol [`identity.rs#L3-L14`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/identity.rs#L3-L14). See [`fetch_project_identity`](endpoints/project.md#fetch_project_identity) and [`bind_project_identity`](endpoints/project.md#bind_project_identity).

When a repository is created and a default identity exists, the document is signed. The client adds `atomic:issuer` as the object `{"@id": "<signer's did:atomic>"}`, signs the JCS bytes of the document with Ed25519, and attaches a [Proof](#proof) [`project_identity.rs#L46-L52`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/repository/project_identity.rs#L46-L52) [`project_identity.rs#L106-L127`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/repository/project_identity.rs#L106-L127). Unlike the delegation documents, it gets no `contentHash` or `attributedTo`. The stored bytes are the JCS form of the document [`project_identity.rs#L53-L59`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/repository/project_identity.rs#L53-L59). Its hash is BLAKE3 over `atomic.project-identity.v1`, a zero byte, and the JCS bytes of the document without `proof` [`project_identity.rs#L27-L33`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/repository/project_identity.rs#L27-L33).

## Tokens

### Token format

A token is a compact JWS: three unpadded base64url segments, `base64url(header).base64url(claims).base64url(signature)` [`token.rs#L8-L16`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L8-L16) [`token.rs#L178-L198`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L178-L198). The base64url encoding is `BASE64URL_NOPAD` from `data-encoding` 2.11.1 [`Cargo.lock#L1174-L1175`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.lock#L1174-L1175), the RFC 4648 URL-safe alphabet without padding ([RFC 4648 §5](https://www.rfc-editor.org/rfc/rfc4648#section-5)). The JWS and JWT shapes are external standards ([RFC 7515](https://www.rfc-editor.org/rfc/rfc7515), [RFC 7519](https://www.rfc-editor.org/rfc/rfc7519)), and `EdDSA` as a JOSE algorithm is [RFC 8037](https://www.rfc-editor.org/rfc/rfc8037).

The header is exactly `{"alg":"EdDSA","typ":"JWT","kid":"<signer's base32 public key>"}`, compact and in that order; a test pins the bytes [`token.rs#L231-L240`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L231-L240). The claims are serialized compact, in the order `sub`, `iat`, `exp`, `jti`, `aud`, `act`, `dlg`, with `act` and `dlg` left out entirely when unset [`token.rs#L72-L95`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L72-L95) [`token.rs#L178-L181`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L178-L181). JSON member order doesn't change the meaning, but the signature covers these exact bytes. See [JwtHeader](#jwtheader), [Claims](#claims) and [Actor](#actor).

The signature is Ed25519 over the ASCII bytes of `<header segment>.<claims segment>`. The 64-byte result is base64url-encoded and appended after a second `.` [`token.rs#L183-L198`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L183-L198). A test builds a token the same way and verifies it against the public key [`token.rs#L297-L358`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L297-L358).

A user's token, with illustrative values. `K` stands for the 52-character base32 key:

```json
{"alg":"EdDSA","typ":"JWT","kid":"K"}
{"sub":"K","iat":1795512600,"exp":1795512900,"jti":"0b6f3c9e-1f7a-4c2e-9a51-3d2b8e4f6a10","aud":"https://atomic.storage"}
```

A delegated agent's token. `A` is the agent's key and `H` the human's [`token.rs#L261-L295`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L261-L295):

```json
{"alg":"EdDSA","typ":"JWT","kid":"A"}
{"sub":"H","iat":1795512600,"exp":1795512900,"jti":"...","aud":"https://atomic.storage","act":{"sub":"A"},"dlg":"urn:atomic:delegation:..."}
```

### Minting a token

`get_token(server, identity)` mints a new token on every call [`token.rs#L109-L117`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L109-L117):

1. `kid` is the signer's base32 public key. For an agent, the signer is the agent [`token.rs#L123-L136`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L123-L136).
2. If the identity is delegated, the client resolves its certificate first ([Choosing a certificate](#choosing-a-certificate)). Then `sub` is the delegator's key, read from the certificate's `delegatorKey` and written as base32; `act.sub` is the agent's key; and `dlg` is the certificate's id as a URN [`token.rs#L138-L156`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L138-L156) [`delegation.rs#L239-L243`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L239-L243). Otherwise `sub` is the identity's own key and there is no `act` or `dlg` [`token.rs#L157-L159`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L157-L159).
3. `iat` is the current Unix time in seconds, `exp` is `iat` plus 300, and `jti` is a new random UUID [`token.rs#L161-L170`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L161-L170). The UUID comes from the external `uuid` crate 1.28.0 [`Cargo.lock#L5006-L5007`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.lock#L5006-L5007), whose `to_string` gives the lowercase hyphenated form ([`Uuid`](https://docs.rs/uuid/1.28.0/uuid/struct.Uuid.html)).
4. `aud` is derived from `server` ([Audience](#audience)) [`token.rs#L164`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L164).
5. The header and claims are serialized, encoded and signed as above [`token.rs#L172-L198`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L172-L198).

Minting fails when the identity store can't be opened or the secret key can't be loaded, or when a delegated identity has no usable certificate or one whose `delegatorKey` doesn't parse [`token.rs#L129-L149`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L129-L149). What callers do with that failure is covered under [`attach_identity`](#attach_identity).

### Audience

`aud` is the server URL with surrounding whitespace and every trailing slash removed, then ASCII-lowercased in full, path included [`token.rs#L201-L206`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L201-L206). So `https://Atomic.Storage/` gives `https://atomic.storage` [`token.rs#L212-L229`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L212-L229).

Which URL goes in depends on the client:

- **Project protocol.** `attach_identity` mints the token for an apex URL that it derives from the repository URL [`mod.rs#L414-L425`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L414-L425). The derivation and its test cases are on [Apex host](transport.md#apex-host); what it gives for a host without a tenant label is an [open question on transport.md](transport.md#open-questions).
- **Management API.** The token is minted for the management apex, the URL configured for the server profile ([Apex host](transport.md#apex-host)). That holds for the apex client [`client.rs#L91-L100`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/client.rs#L91-L100) and for the tenant-scoped client, whose requests go to the tenant URL but whose token names the configured server [`client.rs#L203-L224`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/client.rs#L203-L224).

The same apex URL is the server that a delegated identity's certificate must be scoped to ([Choosing a certificate](#choosing-a-certificate)) [`mod.rs#L463`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L463).

### Lifetime, clock and reuse

- A token is valid for 5 minutes [`token.rs#L56-L58`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L56-L58) [`token.rs#L360-L363`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L360-L363).
- `iat` and `exp` come from the client's clock, with no `nbf` claim [`token.rs#L161-L166`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L161-L166) [`token.rs#L72-L95`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L72-L95). The client does nothing about clock skew.
- The client keeps no cache. But it doesn't mint a token per request either. `attach_identity` mints one token and stores it as a header on the remote's configuration [`mod.rs#L425-L428`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L425-L428), and `HttpRemote` sends that header on every request it makes [`mod.rs#L215-L230`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/mod.rs#L215-L230). Every request through one remote therefore carries the same token, `jti` included. `StorageClient` takes one token in its constructor and sends it on every request [`storage.rs#L98-L125`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L98-L125).
- The source comments say a fresh token is minted per request [`token.rs#L5-L6`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L5-L6) [`mod.rs#L479-L483`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L479-L483). The code doesn't do that; see [Open questions](#open-questions).

A Go client can mint a token per request. That costs one Ed25519 signature, and it means no request carries a token older than its 5-minute lifetime.

### What the server is expected to check

The source contains no server verifier. Its comments describe one:

- The server finds the registered identity by the `kid` public key and verifies the signature against the key it has on record [`token.rs#L39-L45`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L39-L45).
- When `act` is present, the server requires `kid == act.sub`; otherwise it requires `kid == sub` [`token.rs#L30-L33`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L30-L33).
- The server decides whether a token is delegated by whether `act` and `dlg` are present, so a user's token must omit them rather than send `null` [`token.rs#L242-L259`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L242-L259).
- "A server that checks" `aud` refuses a token minted for another server [`token.rs#L82-L86`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L82-L86).
- The server verifies an agent's certificate on every request, against the delegator's registered key [`mod.rs#L430-L433`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L430-L433) [`storage.rs#L90-L97`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L90-L97).

libatomic's sync test stands in for the server, and its verifier is the most concrete statement of the checks. It requires `Authorization: Bearer`, three segments, `alg` `EdDSA`, `kid` and `sub` equal to the registered key, `aud` equal to the expected audience, `iat <= now`, `exp > now`, and a valid Ed25519 signature over `<header>.<claims>` [`local_sync_test.rs#L66-L102`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/tests/local_sync_test.rs#L66-L102). It answers 401 to every request that fails, including `?project-identity=1` reads [`local_sync_test.rs#L113-L121`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/tests/local_sync_test.rs#L113-L121). It compares both `kid` and `sub` with one registered key, so it accepts only user tokens [`local_sync_test.rs#L94-L95`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/tests/local_sync_test.rs#L94-L95).

## Delegation

### The delegation model

A delegation certificate is a signed JSON-LD document in which a human names an agent's key, what the agent may do, and when that ends [`delegation.rs#L1-L14`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L1-L14). What the agent may actually do is the intersection of the human's own grants and the certificate's scope [`delegation.rs#L16-L31`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L16-L31).

The certificate isn't registered in advance. It travels with each request in the `Atomic-Delegation` header. The header constant's doc comment says the server trusts it because it is signed by a key the server already holds: the delegator's, from registration [`delegation.rs#L266-L277`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L266-L277). Issuing or widening a grant needs no server round trip. Only withdrawing one does [`delegation.rs#L273-L276`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L273-L276).

The client can check a certificate's signature, its expiry, its scope and any revocation recorded on the same machine. It can't see a revocation issued elsewhere; the module comment says the server re-checks on every request [`delegation.rs#L13-L19`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/delegation.rs#L13-L19).

Three documents share one signing method [`delegation.rs#L9-L15`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L9-L15):

| Document `@type` | Signed by | Purpose | Type |
|---|---|---|---|
| `AgentDelegation` | the delegator (human) | the certificate: this key is the agent's, within these bounds | [AgentDelegation](#agentdelegation) |
| `AgentDelegationRequest` | the delegate (agent) | proof that the agent holds its key, before the human signs a certificate for it | [DelegationRequest](#delegationrequest) |
| `DelegationRevocation` | the delegator | withdraws a certificate | [DelegationRevocation](#delegationrevocation) |

### Signing a delegation document

All three documents are signed by `attest_value` [`delegation.rs#L129`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L129) [`delegation.rs#L399`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L399) [`delegation.rs#L477`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L477):

1. Build the document without `proof` [`delegation.rs#L104-L127`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L104-L127).
2. If `attributedTo` is missing or empty, set it to the signer's `did:atomic` [`proof.rs#L137-L150`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/proof.rs#L137-L150).
3. Set `contentHash` to `blake3:` followed by the lowercase hex BLAKE3 of the JCS bytes of the document without `proof` and `contentHash` [`proof.rs#L63-L71`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/proof.rs#L63-L71) [`proof.rs#L152-L157`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/proof.rs#L152-L157) [`hash.rs#L15-L20`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/hash.rs#L15-L20).
4. The signing input is the JCS bytes of the document without `proof`, which still includes `contentHash` [`proof.rs#L52-L61`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/proof.rs#L52-L61) [`proof.rs#L159`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/proof.rs#L159).
5. Sign it with the signer's Ed25519 key [`proof.rs#L116-L120`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/proof.rs#L116-L120).
6. Add `proof`: `@type` `DataIntegrityProof`, `cryptosuite` `eddsa-jcs-2022`, `verificationMethod` `<signer's did:atomic>#key-1`, `proofPurpose` `assertionMethod`, and `proofValue` `z` followed by base58btc of the 64 signature bytes [`proof.rs#L23-L27`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/proof.rs#L23-L27) [`proof.rs#L170-L186`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/proof.rs#L170-L186) [`proof.rs#L285-L290`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/proof.rs#L285-L290).

JCS is RFC 8785 ([RFC 8785](https://www.rfc-editor.org/rfc/rfc8785)), produced by the external `serde_json_canonicalizer` crate, version 0.3.2 [`jcs.rs#L12-L30`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/jcs.rs#L12-L30) [`jcs.rs#L122-L129`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/jcs.rs#L122-L129) [`Cargo.lock#L3965-L3966`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.lock#L3965-L3966). Object keys sort by UTF-16 code units, not UTF-8 bytes [`jcs.rs#L161-L172`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/jcs.rs#L161-L172). Timestamps in these documents are RFC 3339 UTC with whole seconds and `Z`, so the canonical bytes are stable [`delegation.rs#L604-L607`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L604-L607) [`delegation.rs#L973-L985`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L973-L985).

The suite is named `eddsa-jcs-2022`, but the signature covers the JCS bytes directly, with no separate hash of a proof configuration [`proof.rs#L159`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/proof.rs#L159) [`proof.rs#L116-L120`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/proof.rs#L116-L120). The W3C `eddsa-jcs-2022` suite instead signs SHA-256 hashes of the proof options and the document ([Data Integrity EdDSA Cryptosuites](https://www.w3.org/TR/vc-di-eddsa/#eddsa-jcs-2022)). A generic Data Integrity library therefore won't produce or verify Atomic's proofs. Implement the steps above.

### Verifying a certificate

`verify(document, delegator_key)` checks, in order [`delegation.rs#L132-L191`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L132-L191) [`proof.rs#L200-L256`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/proof.rs#L200-L256):

1. `@type` is `AgentDelegation` [`delegation.rs#L147`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L147).
2. `contentHash` is present and recomputes [`proof.rs#L209-L220`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/proof.rs#L209-L220).
3. The proof's `@type`, `cryptosuite` and `proofPurpose` are exactly the values above. The signature doesn't cover them, so they are checked separately [`proof.rs#L229-L240`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/proof.rs#L229-L240).
4. The signature verifies over the JCS bytes of the document without `proof` [`proof.rs#L242-L246`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/proof.rs#L242-L246).
5. The DID in `verificationMethod`, the part before `#`, matches the key in either DID form [`proof.rs#L248-L254`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/proof.rs#L248-L254) [`did.rs#L49-L58`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/did.rs#L49-L58).
6. `parse` reads the fields, failing on a missing Required one ([AgentDelegation](#agentdelegation)) [`delegation.rs#L150`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L150).
7. `delegator` is the `did:atomic` of that key, and `delegatorKey` is the same key [`delegation.rs#L152-L169`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L152-L169).
8. `delegate` and `delegateKey` describe the same key [`delegation.rs#L171-L181`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L171-L181).
9. `@id` recomputes from the delegator, the delegate and `issued` ([Delegation ids](#delegation-ids)) [`delegation.rs#L183-L188`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L183-L188).

`verify_self_contained` takes the delegator key from the document's own `delegatorKey`. That proves the document is intact. It doesn't prove the key belongs to the person you think [`delegation.rs#L245-L260`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L245-L260). The client uses it for certificates it holds locally [`delegation.rs#L547-L573`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L547-L573).

### Header encoding

The `Atomic-Delegation` header value is the unpadded base64url encoding of the certificate's JCS bytes, `proof` included [`delegation.rs#L287-L295`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L287-L295). Because the form is canonical, the same certificate always encodes the same way [`delegation.rs#L798-L810`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L798-L810). `attach_identity` re-encodes the parsed document it holds, so the formatting of the stored copy doesn't matter [`delegation.rs#L47-L48`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/delegation.rs#L47-L48) [`mod.rs#L463-L466`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L463-L466).

The decoder, `decode_from_transport`, rejects input longer than 16 KiB (16384 bytes) before decoding it [`delegation.rs#L279-L285`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L279-L285) [`delegation.rs#L336-L342`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L336-L342). It then trims and decodes the base64url and admits the JSON [`delegation.rs#L344-L349`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L344-L349). Admission applies RFC 8785 with the I-JSON profile ([RFC 7493](https://www.rfc-editor.org/rfc/rfc7493)), accepts integers only, limits nesting to 128 levels, and rejects repeated member names [`jcs.rs#L52-L78`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/jcs.rs#L52-L78) [`jcs.rs#L80-L103`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/jcs.rs#L80-L103). The admission code is the external `jcs-admit` crate, version 0.1.3 [`Cargo.lock#L2184-L2185`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.lock#L2184-L2185). Decoding is not trusting: a tampered certificate decodes and then fails verification [`delegation.rs#L813-L821`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L813-L821). The client runs this decoder on `ATOMIC_DELEGATION` [`delegation.rs#L199-L202`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/delegation.rs#L199-L202). A source comment says the verify path handles caller-supplied JSON on every request [`delegation.rs#L279-L285`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L279-L285), which suggests the server shares this code. That isn't confirmed.

`transport_fingerprint` is the unpadded base32 BLAKE3 of the encoded string. Its comment describes it as a key for caching verified certificates [`delegation.rs#L351-L360`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L351-L360).

### Delegation ids

A delegation id is BLAKE3 over the ASCII bytes `atomic:delegation:v1`, the delegator's 32-byte identity id, the delegate's 32-byte identity id, and `issued` as a little-endian signed 64-bit count of Unix seconds [`delegation.rs#L579-L595`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L579-L595). It is written as unpadded base32, and its URN is `urn:atomic:delegation:<base32>` [`delegation.rs#L575-L577`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L575-L577) [`delegation.rs#L607-L624`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L607-L624). Parsing accepts the base32 with or without the URN prefix [`delegation.rs#L612-L619`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L612-L619).

The URN appears as the certificate's `@id` [`delegation.rs#L108`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L108), as the token's `dlg` [`token.rs#L155`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L155), and, URL-encoded, in the management paths for revoking and for checking status [`storage.rs#L484-L495`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L484-L495) [`storage.rs#L527-L536`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L527-L536) [`delegation.rs#L538-L543`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/identity/delegation.rs#L538-L543) [`delegation.rs#L427`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/identity/delegation.rs#L427). See [DelegationId](#delegationid).

### Scope

A [DelegationScope](#delegationscope) limits a certificate on five dimensions:

- **Permissions.** A permission is granted when some listed permission implies it. `full` implies everything. `admin` implies `read`, `manage_views`, `manage_tags` and `admin`, but not `record`, `push` or `pull`. Every other permission implies only itself [`delegation.rs#L117-L130`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L117-L130) [`delegation.rs#L325-L328`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L325-L328). A scope built with no permissions gets `read` [`delegation.rs#L497-L503`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L497-L503).
- **Servers.** An exact match after trimming, removing trailing slashes and lowercasing, never a glob [`delegation.rs#L330-L345`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L330-L345) [`delegation.rs#L391-L394`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L391-L394) [`delegation.rs#L844-L856`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L844-L856).
- **Workspaces, projects and views.** Glob patterns in which `*` matches any run of characters, including none, `?` matches exactly one character, and every other character matches itself. The whole value must match [`delegation.rs#L396-L422`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L396-L422) [`delegation.rs#L821-L829`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L821-L829).
- **Empty lists.** An empty list doesn't restrict its dimension [`delegation.rs#L232-L237`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L232-L237) [`delegation.rs#L811-L819`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L811-L819). `atomic identity agent create` always binds the certificate to the server unless `--local` is given [`create.rs#L142-L150`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/identity/agent/create.rs#L142-L150) [`create.rs#L233-L242`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/identity/agent/create.rs#L233-L242).
- **Maximum changes.** An optional cap on how many changes the delegate may create [`delegation.rs#L262-L264`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L262-L264). Nothing in the client enforces it.

`allows(permission, resource)` requires the permission, then checks each dimension that the [ResourceRef](#resourceref) sets. Dimensions it leaves unset aren't checked [`delegation.rs#L362-L388`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L362-L388). On a `Delegation`, `allows` also requires that the certificate hasn't expired. It checks neither revocation nor the delegator's own grants [`delegation.rs#L722-L732`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L722-L732). A comment says a server must build the `ResourceRef` from the request path, never from a value the client supplies [`delegation.rs#L182-L188`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L182-L188).

### Expiry

`expires` is optional. When it is absent, the certificate never expires [`delegation.rs#L565-L568`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L565-L568). A certificate is expired once `expires` is earlier than the current time on the checking machine [`delegation.rs#L701-L704`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L701-L704). The CLI issues certificates for 30 days by default [`mod.rs#L63`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/identity/agent/mod.rs#L63) [`create.rs#L172-L179`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/identity/agent/create.rs#L172-L179).

### Choosing a certificate

This is client policy. For a delegated identity, `active_for(store, identity, server)` picks the certificate to present [`delegation.rs#L94-L136`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/delegation.rs#L94-L136):

1. If `ATOMIC_DELEGATION` is set and not empty after trimming, it must hold a certificate that decodes, verifies against its own `delegatorKey`, names this agent's `did:atomic` as `delegate`, and hasn't expired. If any check fails, the call fails. It never falls back to the stored certificates [`delegation.rs#L30-L40`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/delegation.rs#L30-L40) [`delegation.rs#L183-L244`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/delegation.rs#L183-L244). No scope or server check is applied to this certificate.
2. Otherwise the client loads every stored certificate whose `delegate` is this agent, keeps those that verify, and sorts them newest `issued` first [`delegation.rs#L538-L541`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L538-L541) [`delegation.rs#L567-L573`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L567-L573) [`delegation.rs#L583-L585`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L583-L585). It takes the first one that hasn't expired, isn't revoked on this machine, and allows `read` on the server [`delegation.rs#L77-L91`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/delegation.rs#L77-L91) [`delegation.rs#L123-L136`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/delegation.rs#L123-L136).

Step 2 asks for `read`, so a stored certificate is only ever presented if it grants `read`, `admin` or `full`. When the agent has no stored certificate at all, the error says so [`delegation.rs#L113-L121`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/delegation.rs#L113-L121). When none qualifies, the error is judged from the newest certificate: revoked, expired, or, for one that is still active, "not valid against" the server with its server scope listed. That last message is also what an active certificate gets when it is scoped to this server but grants nothing that implies `read` [`delegation.rs#L138-L180`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/delegation.rs#L138-L180).

### Revocation and epochs

- **Revocation document.** Only the delegator can revoke. A `DelegationRevocation` must be signed by the delegator, and its `delegator` must name that key [`delegation.rs#L480-L499`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L480-L499).
- **Targeted revocation.** The CLI records the revocation locally first, then POSTs it to the server, and on success reports the grant as deny-listed [`delegation.rs#L517-L552`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/identity/delegation.rs#L517-L552). What the server does with it is not in the source. See [`revoke_delegation`](endpoints/storage.md#revoke_delegation).
- **Epochs.** Most grants are never shown to the server ahead of time, so the server can't list them for revocation. According to the client methods' comments, an agent epoch kills every grant issued to that agent before the moment it is set, and a delegator epoch kills every grant the caller has issued [`storage.rs#L497-L521`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L497-L521). The agent's current epoch appears as `delegationsValidFrom`, whose field comment says grants issued before it are rejected [`storage_types.rs#L156-L158`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage_types.rs#L156-L158). `atomic identity agent revoke` sets the epoch first, then deny-lists each grant it knows about [`revoke.rs#L165-L208`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/identity/agent/revoke.rs#L165-L208). See [`set_agent_epoch`](endpoints/storage.md#set_agent_epoch) and [`set_delegator_epoch`](endpoints/storage.md#set_delegator_epoch).
- **Status.** The CLI passes the delegation URN to the status check [`delegation.rs#L427`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/identity/delegation.rs#L427), which is unauthenticated according to its comment and whose response carries only whether the grant is revoked [`storage.rs#L523-L536`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L523-L536) [`storage_types.rs#L195-L209`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage_types.rs#L195-L209). The client's type for a server delegation record documents four statuses: `active`, `expired`, `revoked` or `superseded` [`storage_types.rs#L175`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage_types.rs#L175). See [`delegation_status`](endpoints/storage.md#delegation_status).
- **Enrollment.** Enrolling an agent sends its `name`, `email`, base32 `publicKey` and signed `certificate` [`storage_types.rs#L560-L569`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage_types.rs#L560-L569). A comment says the separate key lets the server reject a body whose key and certificate disagree before doing any cryptography [`storage_types.rs#L555-L559`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage_types.rs#L555-L559). It is sent under the human's own token [`create.rs#L278-L296`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/identity/agent/create.rs#L278-L296). A CLI comment says publishing a certificate is optional, because the server verifies a presented grant against the delegator's registered key, so a grant works as soon as it is signed [`delegation.rs#L17-L22`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/identity/delegation.rs#L17-L22). See [`enroll_agent`](endpoints/storage.md#enroll_agent) and [`push_delegation`](endpoints/storage.md#push_delegation).

### Delegation requests

When an agent's key is generated somewhere the human never sees, such as a CI runner, the agent signs an `AgentDelegationRequest` with that key. The signature proves it holds the key [`delegation.rs#L381-L400`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L381-L400). The request is verified against the `delegateKey` it carries [`delegation.rs#L402-L437`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L402-L437). The CLI reads requests from a file or from stdin, admits and verifies them, and countersigns them as a certificate [`delegate.rs#L18-L21`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/identity/delegate.rs#L18-L21) [`delegate.rs#L44-L48`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/identity/delegate.rs#L44-L48) [`delegate.rs#L319-L342`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/identity/delegate.rs#L319-L342). No client code sends a request to the server, and at this commit `mint_request` is called only from its own tests [`delegation.rs#L894-L904`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L894-L904), so no CLI command produces one.

### `check_permission`

`check_permission(resolved, permission, resource, identity_name)` passes when `resolved.delegation.allows(permission, resource)` is true, which covers expiry and scope. Otherwise it returns a `DelegationError`. The message lists the granted permissions, the project scope when the project is out of scope, and the `atomic identity delegate ... --can` command that would widen the grant [`delegation.rs#L246-L291`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/delegation.rs#L246-L291). Tests cover a granted push, a refused `admin` and an out-of-scope project [`delegation.rs#L520-L564`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/delegation.rs#L520-L564).

It is a local pre-flight check only. A comment says the server re-checks everything [`delegation.rs#L246-L250`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/delegation.rs#L246-L250). At this commit only its own tests call it. The push pre-flight is `check_push_credentials`, which doesn't check certificates ([`check_push_credentials`](#check_push_credentials)).

- HTTP header names are case-insensitive ([RFC 9110 §5.1](https://www.rfc-editor.org/rfc/rfc9110#section-5.1)). `HttpRemote` writes `Authorization` and `Atomic-Delegation` [`mod.rs#L428`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L428) [`delegation.rs#L277`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L277). `StorageClient` writes the lowercase `atomic-delegation`, because its header-name constructor requires lowercase, and a test keeps the two spellings in step [`storage.rs#L14-L17`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L14-L17) [`storage.rs#L604-L612`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L604-L612).
- The scheme is written `Bearer` with a capital B and one space [`mod.rs#L428`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L428) [`storage.rs#L115`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L115). Signer discovery reads the token back with a case-sensitive `Bearer ` prefix [`signer_refresh.rs#L18`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/signer_refresh.rs#L18).
- `HttpRemote` silently drops any extra header whose name or value isn't a valid HTTP header [`mod.rs#L215-L223`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/mod.rs#L215-L223). `StorageClient` fails at construction instead, for example on a newline in the certificate [`storage.rs#L104-L117`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L104-L117) [`storage.rs#L621-L632`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L621-L632).
- The other headers on these requests (`User-Agent`, `Accept-Encoding`, `Content-Type`) are covered in [Default headers](transport.md#default-headers).

### `attach_identity`

`attach_identity(config, remote_url, identity_override)` adds credentials to an `HttpRemoteConfig`. If any step up to and including minting the token fails, it returns the configuration unchanged, so the request goes out with no credentials [`mod.rs#L356-L449`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L356-L449):

1. Resolve an identity name ([Choosing an identity](#choosing-an-identity)) [`mod.rs#L375-L381`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L375-L381).
2. Open the identity store. On failure, return the configuration unchanged [`mod.rs#L383-L389`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L383-L389).
3. Find the identity, falling back to the default as described above. If none is found, return it unchanged [`mod.rs#L396-L412`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L396-L412).
4. Derive the apex server ([Audience](#audience)). On failure, return it unchanged [`mod.rs#L414-L422`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L414-L422).
5. Mint a token. On success, add `Authorization`, plus `Atomic-Delegation` for a delegated identity with a usable certificate. On failure, return it unchanged [`mod.rs#L424-L448`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L424-L448).

Returning the configuration unchanged is deliberate, so that public reads still work against a server that doesn't require authentication [`mod.rs#L362-L365`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L362-L365). It has a consequence for agents. When a delegated identity's certificate is missing, expired or scoped to another server, minting fails [`token.rs#L142-L143`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L142-L143), and the request is sent with no `Authorization` header at all [`mod.rs#L441-L447`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L441-L447). The token module's comment says such a failure is reported before the network, with the command that fixes it [`token.rs#L35-L37`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L35-L37). `attach_identity` only logs it.

`delegation_header` resolves the certificate a second time, separately from the token [`mod.rs#L458-L475`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L458-L475). If that second lookup fails after the token was minted, the request carries a delegated token, with `act` and `dlg`, but no certificate.

The same function supplies the headers on every other path. The CLI uses it for push [`command.rs#L402-L411`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/push/command.rs#L402-L411), pull [`command.rs#L419`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/pull/command.rs#L419) and clone [`command.rs#L342`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L342). When the CLI goes through the daemon, it copies the resulting headers into the request's `auth_headers` map [`rpc.rs#L5265-L5279`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/rpc.rs#L5265-L5279) [`rpc.rs#L5380-L5381`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/rpc.rs#L5380-L5381) [`rpc.rs#L5397`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/rpc.rs#L5397), which the daemon forwards unchanged (see [PushChanges credentials](../rpc/services/sync.md#push-and-pull-credentials)). The in-process `LocalService` calls it itself [`local.rs#L397-L405`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/local.rs#L397-L405).

Signer discovery reuses the repository remote's `Authorization` and `Atomic-Delegation` values to build a `StorageClient` for the remote's origin, which is its scheme, host and port. A remote without a bearer token starts no discovery [`signer_refresh.rs#L8-L21`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/signer_refresh.rs#L8-L21) [`signer_refresh.rs#L109-L116`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/tests/signer_refresh.rs#L109-L116).

### `check_push_credentials`

`check_push_credentials(remote_url, identity_override)` is the pre-flight check before a push. It passes when three local conditions hold: an identity resolves, by the same rules as `attach_identity`; that identity exists in the local store; and its signing key loads [`mod.rs#L477-L488`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L477-L488) [`mod.rs#L556-L586`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L556-L586). It mints no token, checks no certificate and makes no request. Its doc comment gives the reason it exists: without credentials, the server answers with a 404 for private projects the caller isn't allowed to see, and failing early turns that into an actionable error [`mod.rs#L534-L537`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L534-L537) [`command.rs#L566-L571`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/push/command.rs#L566-L571). That 404 is the comment's claim about the server, not something the client code shows.

On failure it returns `AuthError::AuthenticationFailed` with `remote` set to `<url>: <message>`, where the message comes from the [CredentialIssue](#credentialissue) [`mod.rs#L580-L585`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L580-L585) [`mod.rs#L503-L532`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L503-L532).

It runs before any network I/O on every push path: the CLI [`command.rs#L566-L572`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/push/command.rs#L566-L572), the CLI through the daemon [`rpc.rs#L5380`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/rpc.rs#L5380) and `LocalService` [`local.rs#L397-L399`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/local.rs#L397-L399). `LocalService` maps the error to gRPC `UNAUTHENTICATED` [`local.rs#L425-L433`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/local.rs#L425-L433). A test shows that an explicit identity that doesn't exist fails with `UNAUTHENTICATED`, and the peer sees no request [`local_sync_test.rs#L342-L350`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/tests/local_sync_test.rs#L342-L350). Reads skip the check, because they may be public [`local.rs#L397-L399`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/local.rs#L397-L399) [`README.md#L46-L48`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/README.md?plain=1#L46-L48).

## Types

The Required column is from the receiving side's point of view. **Required** means verification fails without the field, or the reference verifier checks it. **Optional** means the field may be left out. **Unconfirmed** means the client always sends the field, but nothing in the source reads it.

  "contentHash": "blake3:<64 hex>",
  "delegate": "did:atomic:<52 base32 of the agent>",
  "delegateKey": "did:key:z6Mk...",
  "delegateName": "alice+claude",
  "delegator": "did:atomic:<52 base32 of the human>",
  "delegatorKey": "did:key:z6Mk...",
  "delegatorName": "alice",
  "expires": "2026-12-24T09:30:00Z",
  "issued": "2026-11-24T09:30:00Z",
  "proof": {
    "@type": "DataIntegrityProof",
    "cryptosuite": "eddsa-jcs-2022",
    "proofPurpose": "assertionMethod",
    "proofValue": "z<base58btc of 64 bytes>",
    "verificationMethod": "did:atomic:<52 base32 of the human>#key-1"

### DelegationScope

What a certificate allows [`delegation.rs#L232-L269`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L232-L269). Field names are written as in the Rust struct, in snake_case, because the struct has no rename attribute. All five lists are always serialized, even when empty. `max_changes` and `description` are left out when unset.

| Field | JSON type | Required | Value |
|---|---|---|---|
| `permissions` | array of [DelegationPermission](#delegationpermission) | **Required** | It has no serde default, so a scope without it fails to parse. |
| `servers` | array of strings | **Optional** | Exact server URLs ([Scope](#scope)). Empty or absent allows any server. |
| `workspaces` | array of strings | **Optional** | Workspace slug globs. |
| `projects` | array of strings | **Optional** | Project path globs such as `acme/*`. Older documents may use the name `repository_patterns` [`delegation.rs#L254-L256`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L254-L256). |
| `views` | array of strings | **Optional** | View name globs. Older documents may use `view_patterns` or `stack_patterns` [`delegation.rs#L258-L260`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L258-L260) [`delegation.rs#L939-L951`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L939-L951). |
| `max_changes` | integer | **Optional** | The cap on changes the agent may create. It must be below 2^53 to pass admission, which applies the I-JSON safe-integer range [`delegation.rs#L303-L308`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L303-L308) [`jcs.rs#L65-L78`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/jcs.rs#L65-L78). |
| `description` | string | **Optional** | A description for people. |

### DelegationPermission

A snake_case string [`delegation.rs#L73-L100`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L73-L100). | Value | Meaning |
|---|---|
| `read` | Read repository content |
| `record` | Record (commit) changes |
| `push` | Push changes to remotes |
| `pull` | Pull changes from remotes |
| `manage_views` | Create and delete views |
| `manage_tags` | Create and delete tags |
| `admin` | Manage repository settings |
| `full` | Full access (all permissions) |

### CredentialIssue

Why `check_push_credentials` failed [`mod.rs#L489-L501`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L489-L501). ## Open questions

- **Server verification.** atomic-storage is not in the source. Which claims it checks, how much clock skew it allows, whether it tracks `jti`, and whether it checks `aud` [`token.rs#L82-L86`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L82-L86) are all unknown. The only verifier in the source is a test stand-in [`local_sync_test.rs#L66-L102`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/tests/local_sync_test.rs#L66-L102), and it checks `aud` strictly and allows no skew.
- **One token per remote, not per request.** Comments say a fresh token is minted for each request [`token.rs#L5-L6`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L5-L6) [`mod.rs#L479-L483`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L479-L483). The code mints one token per `attach_identity` call and sends it on every request through that remote [`mod.rs#L425-L428`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L425-L428) [`mod.rs#L215-L230`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/mod.rs#L215-L230). Each request may take up to 300 seconds by default [`mod.rs#L61-L66`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/mod.rs#L61-L66), so the later requests of a long push can carry an expired token. How the server answers them isn't stated. Because the Rust client repeats `jti` across requests, a server that works with it can't be refusing repeated `jti` values.
- **Apex derivation on hosts without a tenant label.** The token audience for the project protocol, and the server a stored certificate must be scoped to, come from the derived apex. Its result for single-tenant and other hosts without a tenant label is one open question, on [transport.md](transport.md#open-questions).
- **Signer discovery audience.** Signer discovery reuses a token minted for the apex at the repository remote's own origin, which for a tenant URL is a different host [`signer_refresh.rs#L18-L20`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/signer_refresh.rs#L18-L20).
- **Signer discovery looks up a DID by key.** Signer discovery passes each unresolved signer DID to the by-key lookup, which documents a base32 public key [`signer_refresh.rs#L23-L33`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/signer_refresh.rs#L23-L33) [`storage.rs#L538-L551`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L538-L551). What the server accepts there is one open question, on [storage.md](endpoints/storage.md#open-questions); the request is documented under [`resolve_identity_by_public_key`](endpoints/storage.md#resolve_identity_by_public_key).
- **Delegation failures remove all credentials.** The token module says an unusable certificate fails before the network with a remedy [`token.rs#L35-L37`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/token.rs#L35-L37). `attach_identity` logs the failure and sends the request without `Authorization` [`mod.rs#L441-L447`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L441-L447). The delegation module says it is the one answer for "pre-flighting a push" [`delegation.rs#L3-L11`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/delegation.rs#L3-L11), but `check_push_credentials` never consults it [`mod.rs#L556-L586`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L556-L586), and `check_permission` has no caller outside its tests.
- **`max_changes` or `maxChanges`.** Comments call the scope's numeric field `maxChanges` [`jcs.rs#L70-L72`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/jcs.rs#L70-L72) [`delegation.rs#L303-L306`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L303-L306). The struct has no rename, so the client writes `max_changes` [`delegation.rs#L238-L264`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L238-L264). This page documents what the code writes. Whether the server enforces the cap, and how, is unknown.
- **Environment grants skip scope.** A certificate from `ATOMIC_DELEGATION` is presented without the server-scope and `read` checks that stored certificates get [`delegation.rs#L183-L244`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/delegation.rs#L183-L244) [`delegation.rs#L123-L136`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/delegation.rs#L123-L136).
- **Delegation header limits and caching.** The client's decoder caps an encoded certificate at 16 KiB [`delegation.rs#L279-L285`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L279-L285), and a comment describes server-side caching by fingerprint [`delegation.rs#L351-L360`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-canonical/src/delegation.rs#L351-L360). Whether the server uses the same code and limit is not confirmed. What the server answers when an agent token arrives without a certificate is described only in a comment, as a 401 saying the request "carries no certificate" [`mod.rs#L451-L457`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L451-L457).
- **Userinfo in repository URLs.** Userinfo selects the identity [`mod.rs#L188-L192`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L188-L192), but the same URL then reaches the HTTP client with its userinfo. What that does to the `Authorization` header is one open question, on [transport.md](transport.md#open-questions).
- **Standalone agents.** Registration refuses every agent [`register.rs#L142-L153`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/identity/register.rs#L142-L153), and enrollment requires a certificate [`storage_types.rs#L562-L569`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage_types.rs#L562-L569). The source shows no way for a standalone `agent` identity's key to become known to the server.
- **Registration checks.** The server is said to verify the registration signature [`register.rs#L1-L6`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/identity/register.rs#L1-L6). How it bounds the timestamp and what it does with the unsigned `email` are listed under [Open questions](endpoints/storage.md#open-questions) on storage.md.
- **Delegation status `superseded`.** The server's record documents a `superseded` status [`storage_types.rs#L175`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage_types.rs#L175) that no client code produces or explains.
