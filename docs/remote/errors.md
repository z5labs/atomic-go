# Errors

Every failure of a remote request ends up as one value of `RemoteError`, the error enum of atomic-remote, which covers network failures, HTTP statuses and malformed responses alike ([`error.rs#L9-L17`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/error.rs#L9-L17)). The server's own error model is not in the source. This page records what the client treats as success, what it reads from a failed response, which `RemoteError` it produces, and how the CLI and the daemon show it. Anything only the server decides is listed under [Open questions](#open-questions).

The two HTTP clients behave differently. `HttpRemote`, the project-protocol client, reads error bodies as plain text and picks a variant from the status and the method. `StorageClient`, the management-API client, reads a JSON envelope and almost always produces `HttpError` or `Other`. See [Two clients](transport.md#two-clients).

### Storage API failures

For a status outside 2xx, `StorageClient` takes the message from the body's JSON and produces `HttpError { status, message }` for every status: the `unauthorized`, `forbidden`, `not_found`, `conflict` and `server_error` constructors it picks by status all build that variant ([`storage.rs#L280-L305`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L280-L305), [`error.rs#L296-L334`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/error.rs#L296-L334)). For a 2xx status whose body is not a usable envelope, it produces `Other` ([`storage.rs#L257-L277`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L257-L277)). [Error mapping](endpoints/storage.md#error-mapping) and [Response envelope](endpoints/storage.md#response-envelope) give the full order of checks; the bodies are described [below](#storage-api-json).

### Error bodies

**Project protocol: plain text.** `HttpRemote` reads every error body as text and puts it into the error unchanged, with no JSON parsing; if the body cannot be read, the message is empty ([`queries.rs#L58-L65`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/queries.rs#L58-L65)). The only error body it parses is the `409` of `bind_project_identity`. So a server can send any text, and the client shows it verbatim, for example `HTTP error 500: Internal Server Error` ([`error.rs#L100`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/error.rs#L100), [`error.rs#L511-L515`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/error.rs#L511-L515)).

**Project-identity bind: `{code, message}` or `{error: {code, message}}`.** The `409` body of `bind_project_identity` is read as a [BindServerError](endpoints/project.md#bindservererror) ([`identity.rs#L52-L73`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/identity.rs#L52-L73)). Both members are optional strings, and both spellings are accepted: when the object has an `error` member, `code` and `message` are read from it, otherwise from the top level. The doc comment calls the flat form the expected one and the nested form tolerated ([`identity.rs#L53-L56`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/identity.rs#L53-L56)). Tests use both ([`project_identity_transport.rs#L133-L137`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/tests/project_identity_transport.rs#L133-L137), [`project_identity_transport.rs#L167-L171`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/tests/project_identity_transport.rs#L167-L171)):

```json
{"error": {"code": "IDENTITY_CONFLICT"}}
{"code": "IDENTITY_CONFLICT", "message": "project already bound"}
```

<a id="storage-api-json"></a>**Storage API: JSON.** An error body is recognised in two shapes ([`storage.rs#L280-L295`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L280-L295)):

1. The [ApiResponse](endpoints/storage.md#apiresponse) envelope with an `error` member, such as `{"success":false,"error":{"code":"UNAUTHORIZED","message":"bad token"}}` ([`storage.rs#L646-L653`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L646-L653)).
2. A bare [ApiError](endpoints/storage.md#apierror), `{"code": "…", "message": "…"}`, which the code says some endpoints return on validation and auth failures ([`storage.rs#L288-L292`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L288-L292)).

In both, only `message` is kept; `code` is dropped. Anything else, including plain text, gives the message `HTTP {status}`; a `502` with the body `Bad Gateway` becomes an error whose text contains `502` ([`storage.rs#L294`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L294), [`storage.rs#L664-L669`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L664-L669)). The envelope's `success` member and the error's `code` and `message` members are required by the client's types ([`storage_types.rs#L14-L34`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage_types.rs#L14-L34)). So `{"error":{"code":"X","message":"m"}}` without `success`, which `bind_project_identity` would accept, is not recognised here and gives `HTTP {status}`; so does an `error` without a `message`.

On a 2xx response the envelope must parse and say `success: true` with `data`. A `success: false` body becomes `Other("{code}: {message}")`; this is the only place a storage error `code` reaches an error message ([`storage.rs#L268-L273`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L268-L273)).

### Decode failures and version mismatch

`sync_pull` decodes the `200` body as a zstd-compressed postcard `SyncPack` ([Compression](transport.md#compression)). A zstd or postcard failure becomes `VersionMismatch`, with the running client version, the response's `X-Atomic-Min-Version` value if present, and the decoder's message as the cause. Any other decode failure, which is a body that inflates past 2 GiB, becomes `ProtocolError("failed to decode sync pack: …")` ([`code_sync.rs#L94-L108`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/code_sync.rs#L94-L108), [`sync.rs#L263-L275`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/sync.rs#L263-L275)). The source's reasoning is that an undecodable sync pack almost always means the server runs a different release ([`error.rs#L134-L138`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/error.rs#L134-L138)). `sync_push` has no such path: it does not decode its response beyond an optional JSON summary, which falls back to zero counts when it does not parse ([`code_sync.rs#L58-L60`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/code_sync.rs#L58-L60), [`code_sync.rs#L25-L34`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/code_sync.rs#L25-L34)).

## Error kinds

A client of these remotes meets two error types:

- [`RemoteError`](#remoteerror), below: every failure of an HTTP request, whether it comes from the network, the status or the body.
- [`AuthError`](auth.md#autherror): credential preparation before a request, with the variants `Internal`, `AuthenticationFailed { remote }` and `DelegationError { message }` ([`mod.rs#L36-L45`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/auth/mod.rs#L36-L45)). It comes from local work, not from an HTTP response, and is documented on [auth.md](auth.md#autherror).

## How errors reach the user

**CLI push, pull and clone.** Each command converts a `RemoteError` into its own error type ([`helpers.rs#L384-L445`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/push/helpers.rs#L384-L445), [`helpers.rs#L225-L280`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/pull/helpers.rs#L225-L280), [`helpers.rs#L540-L595`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/helpers.rs#L540-L595)):

| `RemoteError` | Push | Pull's own body and clone |
|---|---|---|
| `ConnectionFailed` | `Remote operation failed: Failed to connect: {error}` | same |
| `AuthenticationFailed` | `Authentication failed for remote '{url}'`, with the server's body dropped | same |
| `RepositoryNotFound` | `Remote returned 'not found' for the project. This means either it doesn't exist, or you're not authenticated/authorized to push to it. …`, pointing to `atomic identity register <server-url>` ([`helpers.rs#L362-L369`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/push/helpers.rs#L362-L369)) | `Repository not found on remote` |
| `ViewNotFound` | the same message, naming `project/view '{view}'` | `View '{view}' not found on remote` |
| `ChangeNotFound` | change-not-found error with the hash | same |
| `TagNotFound` | the generic fallback | `Tag not found for state: {state}` |
| `MissingDependencies` | missing-dependency error for "uploaded change", naming the hashes or `{count} dependencies` | the same for "requested change" |
| `StateMismatch` | conflict: `State mismatch: remote is at {remote}, requested {requested}` | same |
| `Timeout` | `Request timed out after {seconds} seconds` | same |
| `HttpError` with status 413 | the "Change too large" message | the generic fallback |
| `EmptyView` | the generic fallback | `View '{view}' is empty` |
| anything else | `Remote operation failed: {message}` | same |

The CLI's display texts for its remote and authentication errors are `Remote operation failed: {message}` and `Authentication failed for remote '{remote}'` ([`error.rs#L327-L346`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/error.rs#L327-L346)).

**CLI management commands.** Workspace and project commands wrap the `RemoteError`'s message as `Remote operation failed: {message}` without a URL ([`client.rs#L297-L303`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/client.rs#L297-L303)). `atomic-teams` maps statuses to its own errors; see [Error mapping](endpoints/storage.md#error-mapping). A few commands first test `is_not_found()` to give a `404` their own message ([RemoteError](#remoteerror)). `atomic identity register` does not use `RemoteError` at all: on an error status it takes the body's `message`, else `error.message`, else `Server returned {status}` ([`register.rs#L312-L328`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/identity/register.rs#L312-L328)); see [`execute`](endpoints/storage.md#execute).

**The daemon.** The daemon's `PushChanges` handler applies the same push mapping as the CLI, and `PullChanges` a shorter mapping of its own; both send the result as a gRPC status with error code `REMOTE`, whose message is a JSON object with `stage`, `variant`, `url` and `message` ([`services_sync_remote.rs#L51-L66`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L51-L66), [`services_sync_remote.rs#L68-L135`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L68-L135)). In the pull mapping, `AuthenticationFailed` becomes the variant `authentication_failed` with an empty message, `ConnectionFailed` becomes `remote_error` with `Failed to connect: …`, and everything else becomes `remote_error` with the error's text ([`services_sync_remote.rs#L126-L135`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L126-L135)). So a pull that runs in the handler, as it does inside a repository, reports every other failure with the `RemoteError`'s own text rather than the table's. The CLI turns the JSON back into its own error: it prints the failed stage, then maps the variants `remote_error`, `authentication_failed`, `change_not_found`, `missing_dependency` and `conflict` to the matching CLI errors ([`rpc.rs#L5284-L5336`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/rpc.rs#L5284-L5336)). See [PushChanges](../rpc/services/sync.md#pushchanges) and [On the wire](../rpc/errors.md#on-the-wire) in the RPC reference.

## Open questions

- **The project protocol's error bodies.** The client treats every error body as text ([`queries.rs#L58-L65`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/queries.rs#L58-L65)). Whether the server sends plain text, JSON, or the storage envelope on these paths is decided by the server; a Go client should show the body verbatim, as the Rust client does.
- **Which statuses the server uses.** The status-to-variant tables above are what the client accepts. Which statuses the server actually returns for each failure, for example whether a missing change on upload is `400` or `500`, is not in the source; the client checks both ([`upload.rs#L68`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/upload.rs#L68)).
- **Matching on message text.** `MissingDependencies` and `StateMismatch` depend on English substrings of the server's message ([`upload.rs#L73`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/upload.rs#L73), [`upload.rs#L184`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/upload.rs#L184), [`upload.rs#L238`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/upload.rs#L238)). The server's exact wording is not pinned anywhere in the source except the one test body ([`upload.rs#L540-L543`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/upload.rs#L540-L543)), and where that body's `missing changes: ` prefix comes from is not in the source either ([Server text the client recognises](#server-text-the-client-recognises)).
- **Private projects and `404`.** The push mapping's comment says the server answers "not found" to callers not authorised for a private project ([`helpers.rs#L393-L399`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/push/helpers.rs#L393-L399)). That is the author's statement about the server; the source does not show it.
- **`BindServerError` and non-object JSON.** The doc comment says the parser returns nothing when the body "is not a usable JSON object" ([`identity.rs#L53-L56`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/identity.rs#L53-L56)). This page documents the code.
- **Two JSON error shapes.** The bind rejection accepts a nested `{"error": {…}}` without `success` ([`identity.rs#L59-L63`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/identity.rs#L59-L63)); the storage client recognises the nested form only inside an envelope with `success` ([`storage_types.rs#L16-L17`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage_types.rs#L16-L17)). Which shapes the servers emit on which endpoints is not in the source.
- **The storage error `code`.** The client drops `code` on error statuses ([`storage.rs#L282-L292`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/storage.rs#L282-L292)). - **`413` and body limits.** The CLI's message names a server setting `MAX_BODY_SIZE_MB` ([`helpers.rs#L433-L439`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/push/helpers.rs#L433-L439)). - **Unused variants.** `Timeout`, `Io`, `Json`, `EmptyView` and `Cancelled` are declared, but nothing creates them ([`error.rs#L108-L151`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/error.rs#L108-L151)). - **Retryability.** `is_retryable()` covers only `ConnectionFailed` and `Timeout` ([`error.rs#L340-L342`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/error.rs#L340-L342)), so a `503` or a `StorageClient` connection failure is not retryable by that rule, and no caller uses the rule.
