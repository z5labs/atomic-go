# Shared types

This page documents the wire types declared in `atomic-remote/src/types.rs` and `atomic-remote/src/streaming/types.rs`, and the text encodings of the hashes and other identifiers that more than one page of this reference uses. `atomic-remote` is the HTTP client library for Atomic remotes ([`lib.rs#L1-L4`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/lib.rs#L1-L4)), and it re-exports these types at the crate root ([`lib.rs#L155-L168`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/lib.rs#L155-L168)). The container types built from these encodings, [ViewManifest](endpoints/project.md#viewmanifest), [ViewSnapshot](endpoints/project.md#viewsnapshot), [LayerSelection](endpoints/project.md#layerselection) and [ChunkManifest](endpoints/project.md#chunkmanifest), are on the project protocol page.

Every format below is described as the client writes and parses it. The server is not in the source, so what it emits and accepts is listed under [Open questions](#open-questions).

## Identifiers and encodings

### Base32 hash text

Change hashes, Merkle states, SetIds and the other Atomic hashes that the project protocol writes as text use one codec, atomic-core's `Base32` trait ([`mod.rs#L45-L52`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/mod.rs#L45-L52)). The exceptions, view-snapshot keys and content-chunk hashes, are hex; see [Lowercase hex](#lowercase-hex). `Merkle` is the 32-byte type, and `Hash` is a type alias for it, so change hashes and state hashes share the type and the codec ([`hash.rs#L43-L51`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/hash.rs#L43-L51)).

**Encoding.** The alphabet is RFC 4648's `ABCDEFGHIJKLMNOPQRSTUVWXYZ234567` ([`hash.rs#L259-L260`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/hash.rs#L259-L260)). The encoder reads the 32 bytes from the most significant bit, writes one character for every 5 bits, fills the last character's missing low bits with zeros, and writes no `=` padding ([`hash.rs#L262-L287`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/hash.rs#L262-L287)). The result is always 52 characters, 51 full 5-bit groups and one partial, all from that upper-case alphabet ([`hash.rs#L262-L287`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/hash.rs#L262-L287)); a test checks the length ([`hash.rs#L468-L481`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/hash.rs#L468-L481)). This is RFC 4648 base32 with the padding removed (external spec: [RFC 4648 §6](https://www.rfc-editor.org/rfc/rfc4648#section-6)). Because 256 = 51 × 5 + 1, the 52nd character carries one data bit followed by four zero bits ([`hash.rs#L280-L284`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/hash.rs#L280-L284)), so a canonical string always ends in `A` or `Q`.

**Decoding.** The decoder accepts `A`–`Z`, `a`–`z` and `2`–`7`, so decoding is case-insensitive; any other byte, including `=`, `-` and whitespace, fails ([`hash.rs#L295-L302`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/hash.rs#L295-L302)). It fails as soon as the input would produce a 33rd byte, and it fails when it produced fewer than 32 ([`hash.rs#L307-L319`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/hash.rs#L307-L319)), so only a 52-character string decodes. It never checks the four unused low bits of the last character ([`hash.rs#L304-L321`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/hash.rs#L304-L321)), so a string whose last character is not `A` or `Q` still decodes, to the same bytes as its canonical form. A test decodes the lower-case form of a hash to the same value as the upper-case form ([`hash.rs#L386-L397`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/hash.rs#L386-L397)).

**Serde forms.** In a human-readable serde format, a `Merkle` is the base32 string; in a binary format it is a newtype around `[u8; 32]` ([`hash.rs#L198-L221`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/hash.rs#L198-L221)). JSON is human-readable: serde's `is_human_readable` defaults to true (external: serde 1.0.229, [`Cargo.lock#L3896-L3897`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.lock#L3896-L3897), serde_core [`Cargo.lock#L3930-L3931`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.lock#L3930-L3931), [ser/mod.rs#L1459-L1461](https://github.com/serde-rs/serde/blob/7fc3b4c30c94f73a96ebd1553f2b090d928fc3a8/serde_core/src/ser/mod.rs#L1459-L1461)). The binary form, used in postcard and inside change files, is on [Binary hash form](#binary-hash-form).

**Compare decoded bytes, not strings.** The client compares hash text as strings in several places: the sync engine compares a remote Merkle state with its cached one ([`sync.rs#L535-L542`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/sync.rs#L535-L542)) and a remote SetId with its own fold ([`sync.rs#L648-L655`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/sync.rs#L648-L655)), the CLI's pull compares changelist hashes with its local hashes ([`helpers.rs#L71-L80`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/pull/helpers.rs#L71-L80)), and the post-pull SetId check compares strings ([`command.rs#L862-L864`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/pull/command.rs#L862-L864)). Every string the client produces is the canonical upper-case form. A Go client should write only the canonical form, and should decode what it receives and compare bytes, or re-encode it canonically before comparing.

Example. A test in `upload.rs` uses this change hash from a server error message ([`upload.rs#L537-L552`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/upload.rs#L537-L552)):

```text
GJGC6OK6JT77OB2PDGFYEC2BUISJWQNQVT345SNIZ2CKKXGV652A
```

Decoded with RFC 4648 base32 it is these 32 bytes (computed for this reference; the source does not list them):

```text
32 4c 2f 39 5e 4c ff f7 07 4f 19 8b 82 0b 41 a2
24 9b 41 b0 ac f7 ce c9 a8 ce 84 a5 5c d5 f7 74
```

The all-zero hash `Merkle::ZERO` ([`hash.rs#L90-L91`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/hash.rs#L90-L91)) encodes as 52 `A` characters, because every 5-bit group is 0 and `A` is alphabet index 0 ([`hash.rs#L259-L260`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/hash.rs#L259-L260)).

### Binary hash form

Inside a V3 change file and in every postcard payload, a hash is 32 raw bytes, never text.

- **In postcard.** `Merkle` is a newtype struct over `[u8; 32]` ([`hash.rs#L43-L44`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/hash.rs#L43-L44)). When the serializer is not human-readable, its `Serialize` impl writes that newtype, and its `Deserialize` impl reads the newtype back as a `[u8; 32]` ([`hash.rs#L198-L256`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/hash.rs#L198-L256)). Postcard reports itself as not human-readable (external: postcard 1.1.3, [`Cargo.lock#L2938-L2939`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.lock#L2938-L2939); [ser/serializer.rs#L87-L89](https://github.com/jamesmunns/postcard/blob/718aa6a6850456017c19eeff67303c633f875736/source/postcard/src/ser/serializer.rs#L87-L89), [de/deserializer.rs#L208-L210](https://github.com/jamesmunns/postcard/blob/718aa6a6850456017c19eeff67303c633f875736/source/postcard/src/de/deserializer.rs#L208-L210)). It writes a newtype as its inner value and a fixed-size array as its elements with no length prefix ([Postcard encoding](change-format/container.md#postcard-encoding)). A `Hash` field is therefore exactly 32 bytes, in the order of `Merkle.0`, with no length prefix and no tag. A test checks that a hash postcard-encodes to exactly 32 bytes ([`hash.rs#L458-L466`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/hash.rs#L458-L466)). Another encodes a SPAN payload whose owner hash is 32 `0xa5` bytes and expects exactly those 32 bytes after the owner's ID ([`semantic_context.rs#L342-L353`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/semantic_context.rs#L342-L353)).
- **Outside postcard.** The hash dedup table's entries, a CONTENT frame's `chunk_hash` and the trailer are the same 32 raw bytes, copied into the file directly rather than through serde ([`hash_table.rs#L584-L589`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/hash_table.rs#L584-L589), [`section.rs#L412-L420`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/section.rs#L412-L420), [`state_machine.rs#L523-L529`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/state_machine.rs#L523-L529)); see [File layout](change-format/container.md#file-layout).
- **Not every 32-byte field is a `Hash`.** `ChangeSignature.signed_hash` is a `[u8; 32]` serialized as a slice ([`section.rs#L518-L520`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/section.rs#L518-L520), [`section.rs#L574-L586`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/types/section.rs#L574-L586)), so postcard writes a length prefix before the 32 bytes: the varint `0x20`, which is 32; see [ChangeSignature](change-format/sections.md#changesignature). HEADER, DEPS and GRAPH payloads name other changes by a `u16` index into the dedup table instead of by hash; see [HashIndex](change-format/container.md#hashindex).
- **The zero hash.** `Merkle::ZERO`, and its alias `Hash::NONE`, is 32 zero bytes ([`hash.rs#L89-L94`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/hash.rs#L89-L94)). Atomic's writer puts it in slot 0 of the dedup table ([`change.rs#L391-L394`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L391-L394)); see [HashDedupTable](change-format/container.md#hashdeduptable).

The gRPC API carries the same 32 bytes as raw bytes; see [Hash](../rpc/types.md#hash).

### Lowercase hex

Some identifiers are written as 64 lower-case hex characters instead.

- `Merkle::to_hex` writes two lower-case hex digits per byte, and `Merkle::from_hex` requires 64 bytes of input and parses each two-byte pair with `u8::from_str_radix(pair, 16)` ([`hash.rs#L146-L167`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/hash.rs#L146-L167)). That standard-library parser accepts digits of either case and an optional leading `+` (external: [`u8::from_str_radix`](https://doc.rust-lang.org/std/primitive.u8.html#method.from_str_radix)), so `Merkle::from_hex`, `SetId::from_hex` and the chunk manifest's `hex_hash` accept upper case too. Every hex writer in this reference writes lower case. `SetId` has the same pair, and documents its parser as accepting lower or upper case ([`set_id.rs#L220-L240`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/set_id.rs#L220-L240)).
- A chunk hash in a chunk manifest uses the `hex_hash` serde module; see [ChunkManifestEntry](#chunkmanifestentry).
- The key of a `View` object in the `/code` sync protocol, a [ViewSnapshot](endpoints/project.md#viewsnapshot)'s, is the lower-case hex BLAKE3 of the object's bytes ([`lib.rs#L39-L51`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/lib.rs#L39-L51), [`view_snapshot.rs#L113-L117`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/view_snapshot.rs#L113-L117)). atomic-objects documents every object key this way, but the daemon's push keys the other families, `Change`, `Attest`, `Provenance` and `Tag`, by [base32](#base32-hash-text) Atomic hashes ([`services_sync_remote.rs#L688-L695`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L688-L695), [`services_sync_remote.rs#L744-L748`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L744-L748), [`services_sync_remote.rs#L781-L785`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L781-L785), [`services_sync_remote.rs#L799-L808`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L799-L808)); the key of each family is on [ObjectRecord](endpoints/project.md#objectrecord). `blake3::Hash::to_hex` writes lower case (external: blake3 1.8.7, [`Cargo.lock#L656-L657`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.lock#L656-L657), [`Hash::to_hex`](https://docs.rs/blake3/1.8.7/blake3/struct.Hash.html#method.to_hex)). The integrity check compares the computed key with the given key as strings ([`lib.rs#L53-L57`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/lib.rs#L53-L57)), so an upper-case key fails it.

| View snapshot object key | 32 | lowercase hex | a `/code` ref target, and a snapshot's `prev` entries ([`view_snapshot.rs#L64-L69`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/view_snapshot.rs#L64-L69), [`view_snapshot.rs#L113-L117`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-objects/src/view_snapshot.rs#L113-L117)) | [Lowercase hex](#lowercase-hex) |
| Content chunk hash | 32 | lowercase hex | `hash` of a [ChunkManifestEntry](#chunkmanifestentry) | BLAKE3 of the uncompressed chunk ([`types.rs#L88-L92`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/streaming/types.rs#L88-L92)) |
| Ed25519 public key, identity ID, delegation ID | 32 | base32, by a different codec | identity and delegation requests | [Identities and DIDs](auth.md#identities-and-dids) |

How to tell them apart:

- **Hex or base32.** A hex identifier is 64 characters from `0-9a-f`; a base32 one is 52 characters from `A-Z2-7`. The git-binding code tests for a hex key with exactly that rule: 64 characters, each a digit or `a`–`f` ([`pack.rs#L361-L366`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/git_binding/pack.rs#L361-L366)).
- **Among base32 identifiers.** There is no prefix, marker or length difference. A change hash, a Merkle state, a tag hash and a SetId are all 52 characters from the same alphabet ([`hash.rs#L259-L260`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/hash.rs#L259-L260), [`set_id.rs#L314-L316`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/set_id.rs#L314-L316)). Only the field, token or query parameter that holds the string says which identifier it is.
- **Identity keys.** Ed25519 public keys, identity IDs and delegation IDs are written with the external `data-encoding` crate's `BASE32_NOPAD`, not with atomic-core's codec ([`keypair.rs#L51-L54`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/keypair.rs#L51-L54), [`keypair.rs#L92-L96`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/keypair.rs#L92-L96), [`identity.rs#L71-L74`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/identity.rs#L71-L74), [`delegation.rs#L607-L619`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L607-L619); data-encoding 2.11.1, [`Cargo.lock#L1174-L1175`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/Cargo.lock#L1174-L1175)). The alphabet and the unpadded 52-character form are the same, but the decoder is stricter: `BASE32_NOPAD`'s specification has no case translation, so lower case is refused (data-encoding offers a separate [`BASE32_NOPAD_NOCASE`](https://docs.rs/data-encoding/2.11.1/data_encoding/constant.BASE32_NOPAD_NOCASE.html) for that), and `Specification::new` turns trailing-bit checking on, so a last character other than `A` or `Q` is refused too (external: [`lib.rs#L2254-L2264`](https://github.com/ia0/data-encoding/blob/834737d9c3dc957ce1b653959e3f35061dd77ade/lib/src/lib.rs#L2254-L2264), [`lib.rs#L1898-L1908`](https://github.com/ia0/data-encoding/blob/834737d9c3dc957ce1b653959e3f35061dd77ade/lib/src/lib.rs#L1898-L1908)). The decoders then require exactly 32 bytes ([`keypair.rs#L92-L108`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/keypair.rs#L92-L108), [`identity.rs#L76-L92`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/identity.rs#L76-L92)). A delegation ID may also carry a `urn:atomic:delegation:` prefix ([`delegation.rs#L612-L624`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-identity/src/delegation.rs#L612-L624)). [Keys and key encodings](auth.md#keys-and-key-encodings) owns these.

### Change hashes and the V3 file

The change hash in text is the 32-byte identity that `Change::deserialize` returns: the content hash `ChangeReader::verify` yields while it reads the file ([`change.rs#L754-L756`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L754-L756), [`change.rs#L842`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L842)). How those 32 bytes are computed is in [Change hash](change-format/container.md#change-hash); the text form is [base32](#base32-hash-text) of them.

- The daemon's push writes a change object's key with `to_base32` of that hash ([`services_sync_remote.rs#L688-L695`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L688-L695)).
- The client's closure fetch decodes an object key with `Hash::from_base32`, deserializes the bytes, and rejects the object when the identity differs from the key ([`binding_fetch.rs#L162-L187`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/repository/binding_fetch.rs#L162-L187)).
- The git-binding download asks for `?change=` with `to_base32` of the wanted hash and keys the result the same way ([`transport.rs#L637-L643`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/git/transport.rs#L637-L643)).
- Inside the file, hashes such as the dependencies' are raw 32-byte entries of the hash dedup table ([Binary hash form](#binary-hash-form)). The module diagram labels index 0 the self hash ([`mod.rs#L14-L28`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/mod.rs#L14-L28)), but Atomic's writer stores 32 zero bytes there ([`change.rs#L391-L394`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/change.rs#L391-L394)). The change's own hash is in the trailer ([`state_machine.rs#L523-L529`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/format_v3/writer/state_machine.rs#L523-L529)), and in the SIGNATURE payload of a signed change ([`signing.rs#L48`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/change/signing.rs#L48)); see [HashDedupTable](change-format/container.md#hashdeduptable) and [HashIndex](change-format/container.md#hashindex). When a dependency hash appears in text, for example in a server error message, it is the same 52-character base32 ([`upload.rs#L17-L32`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/upload.rs#L17-L32)).

The change hash is not the BLAKE3 of the file's bytes. The git-binding pack keys a change file by the lower-case hex BLAKE3 of its bytes, and its author states that this "is NOT the change hash" ([`pack.rs#L284-L298`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/git_binding/pack.rs#L284-L298)).

### Merkle state

A view's Merkle state is a fold over its change log. Start from `Merkle::ZERO` (32 zero bytes) and, for each change hash in log order, compute `BLAKE3(state || hash)` over the 64 concatenated bytes ([`manifest.rs#L104-L112`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/manifest.rs#L104-L112), [`hash.rs#L123-L132`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/hash.rs#L123-L132)). The order matters: the same changes in a different order give a different state ([`hash.rs#L418-L429`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/hash.rs#L418-L429)).

The `merkle` of a changelist entry is the state after that entry. The CLI's pull rebuilds changelist entries from a manifest exactly this way, entry `i` getting the fold through change `i` ([`command.rs#L602-L617`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/pull/command.rs#L602-L617)).

An empty view has no state on the wire. A [StateResponse](#stateresponse) is the single token `-` ([`types.rs#L394-L396`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L394-L396)); a [RemoteViewInfo](#remoteviewinfo) and a [ViewManifest](endpoints/project.md#viewmanifest) write `-` in the state field ([`types.rs#L686-L692`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L686-L692), [`manifest.rs#L28-L31`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-repository/src/manifest.rs#L28-L31)).

The doc comment on `Merkle` says the initial state is `Blake3(empty)` ([`hash.rs#L33-L39`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/hash.rs#L33-L39)); the fold code seeds with `Merkle::ZERO`. See [Open questions](#open-questions).

### SetId

A `SetId` is an order-invariant identity for a set of change hashes, kept alongside the order-sensitive Merkle state ([`set_id.rs#L5-L17`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/set_id.rs#L5-L17)). It is 32 bytes ([`set_id.rs#L99-L100`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/set_id.rs#L99-L100)).

To compute it:

1. For each member hash `h` (32 bytes), compute `e = BLAKE3("atomic:setid:v1" || h)` ([`set_id.rs#L83-L86`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/set_id.rs#L83-L86), [`set_id.rs#L149-L158`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/set_id.rs#L149-L158)).
2. Read `e` as four little-endian `u64` lanes: bytes 0–7, 8–15, 16–23 and 24–31 ([`set_id.rs#L102-L112`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/set_id.rs#L102-L112)).
3. Add each lane into the accumulator, wrapping mod 2^64, with no carry between lanes. The accumulator starts at all zeros ([`set_id.rs#L160-L173`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/set_id.rs#L160-L173), [`set_id.rs#L204-L218`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/set_id.rs#L204-L218)).
4. Write the four lanes back as little-endian `u64`s in the same order ([`set_id.rs#L114-L122`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/set_id.rs#L114-L122)).

The empty set is all zeros, `SetId::ZERO` ([`set_id.rs#L125-L126`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/set_id.rs#L125-L126)). Adding the same hash twice counts it twice, so deduplicate first ([`set_id.rs#L160-L165`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/set_id.rs#L160-L165)). The members are change and tag hashes; `.provenance` and `.attest` sidecars are excluded, and the comment calls this domain a cross-producer contract that the caller must enforce ([`set_id.rs#L57-L71`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/set_id.rs#L57-L71)).

The text form is a separate copy of the `Merkle` base32 codec, with the same alphabet, case-insensitive decoding and 52-character length ([`set_id.rs#L314-L377`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/set_id.rs#L314-L377), [`set_id.rs#L486-L494`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/set_id.rs#L486-L494)). The sync engine folds its local hashes this way and treats any hash that is not valid base32 as "cannot compute" ([`sync.rs#L467-L486`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/sync.rs#L467-L486)).

### Sequence numbers

Sequence numbers, including a state's `position`, are unsigned 64-bit integers written in decimal ASCII. The client formats them with Rust's `{}`, which writes no sign or leading zeros, and parses them with `parse::<u64>`, which also accepts a leading `+` (external: [`u64::from_str_radix`](https://doc.rust-lang.org/std/primitive.u64.html#method.from_str_radix), which `FromStr` for `u64` uses with radix 10) ([`types.rs#L225-L227`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L225-L227), [`types.rs#L247-L254`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L247-L254), [`types.rs#L404-L406`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L404-L406)).

- A [ChangelistEntry](#changelistentry)'s `sequence` is the entry's 0-based position in the view's log ([`types.rs#L151-L152`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L151-L152)).
- A [StateResponse](#stateresponse)'s `position` is the sequence number of the last change ([`types.rs#L314-L315`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L314-L315)). The CLI sets it to the number of changes minus one when it builds one locally ([`command.rs#L618-L626`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/pull/command.rs#L618-L626)).
- The `from` of [`get_changelist`](endpoints/project.md#get_changelist) is a decimal `u64` in the query string ([`queries.rs#L79-L84`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/queries.rs#L79-L84)).

### View names

The client builds request URLs with `format!` and does not escape the view name it inserts itself ([`queries.rs#L30`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/queries.rs#L30), [`queries.rs#L84`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/queries.rs#L84), [`upload.rs#L266-L270`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/upload.rs#L266-L270)). reqwest then parses the built URL again, so only the URL standard's query percent-encode set is applied, a `#` cuts the query off, and `%`, `+`, `&` and `=` arrive as they are; see [Building request URLs](transport.md#building-request-urls).

| Source | [`new.rs#L72-L76`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/view/new.rs#L72-L76), [`new.rs#L96-L135`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/view/new.rs#L96-L135), [`split.rs#L53-L97`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/split.rs#L53-L97), [`rpc.rs#L3553`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/rpc.rs#L3553) | [`services_query.rs#L1145-L1167`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_query.rs#L1145-L1167) |

### Positions

A `Position` is a byte offset inside a change: a change identifier plus an offset ([`position.rs#L11-L28`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/position.rs#L11-L28)). Its base32 text form is the change's base32, a `.`, then the offset in a variable-length base32: the offset's 5-bit groups from the most significant non-zero group down, with `A` alone for 0 ([`position.rs#L160-L181`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/position.rs#L160-L181)). For example, offset 100 is the groups 3 and 4, written `DE`. The decoder splits at the first `.`, decodes the change part with the change type's codec, reads the offset case-insensitively, accepts leading `A`s, fails on a value that overflows `u64`, and reads an empty offset as 0 ([`position.rs#L183-L207`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/position.rs#L183-L207)). The `Display` form is different: the change, a `:`, and the offset in decimal ([`position.rs#L151-L155`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/position.rs#L151-L155)). No request in this reference carries a position as text; inside a change file positions are binary: what a position's change index means is on [HashIndex](change-format/container.md#hashindex), and how GRAPH payloads use positions is on [GRAPH and SEMANTIC sections](change-format/graph.md).

### ChangelistEntry

One entry of a view's log: its sequence number, change hash, the Merkle state after it, and whether it is tagged ([`types.rs#L140-L162`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L140-L162)). The client reads one per non-blank line of a [`get_changelist`](endpoints/project.md#get_changelist) response ([`mod.rs#L294-L312`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/mod.rs#L294-L312)).

**Wire format.** One line, fields separated by `.`. A trailing `.` marks a tagged entry ([`types.rs#L146-L148`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L146-L148), [`types.rs#L247-L254`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L247-L254)).

```text
{sequence}.{hash}.{merkle}
{sequence}.{hash}.{merkle}.
```

Neither base32 nor decimal digits contain `.`, so the separator is unambiguous for well-formed values ([`hash.rs#L259-L260`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/hash.rs#L259-L260)).

|---|---|---|---|
| `sequence` | `u64`, decimal | **Required** | 0-based position in the log ([`types.rs#L151-L152`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L151-L152)). | `tagged` | `bool` | **Optional** | True when the line ends in `.` (see below) ([`types.rs#L160-L161`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L160-L161), [`types.rs#L204-L217`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L204-L217)). |

**Parsing rules** ([`types.rs#L198-L245`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L198-L245)):

- Leading and trailing whitespace is trimmed. An empty line fails with `Empty` ([`types.rs#L199-L202`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L199-L202)); `parse_changelist` skips blank lines before it gets that far ([`mod.rs#L298-L302`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/mod.rs#L298-L302)).
- When the line ends in `.`, the parser strips every trailing `.` and counts the dots left. Two or more means tagged, and the stripped text is parsed ([`types.rs#L204-L217`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L204-L217)). So `1.A.B..` is tagged. `0.ABC.` is not: fewer than two dots remain, so the original line is split, giving an empty `merkle` and `InvalidFormat`.
- Fewer than three `.`-separated parts fails with `InvalidFormat` ([`types.rs#L219-L223`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L219-L223)). Parts after the third are ignored: `0.A.B.C` parses as hash `A`, merkle `B` ([`types.rs#L229-L230`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L229-L230)).
- One bad line fails the whole response, as a protocol error `Failed to parse changelist entry: {error}` ([`mod.rs#L304-L306`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/mod.rs#L304-L306)); see [Error kinds](errors.md#error-kinds). The `{error}` texts are `empty changelist line`, `invalid changelist format: '{line}'` and `invalid sequence number: '{value}'` ([`types.rs#L286-L294`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L286-L294)).
- The CLI's pull decodes `hash` and `merkle` with the base32 decoder and silently skips an entry when either fails ([`helpers.rs#L82-L92`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/pull/helpers.rs#L82-L92)).

**Example** (placeholder hashes from the tests, not real 52-character values). The body `0.ABC.DEF\n1.GHI.JKL.\n2.MNO.PQR` parses as three entries, the second tagged ([`tests.rs#L139-L147`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/tests.rs#L139-L147)). `42.ABC123.DEF456.` parses as sequence 42, hash `ABC123`, merkle `DEF456`, tagged ([`types.rs#L802-L809`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L802-L809)). Serializing writes the same line back ([`types.rs#L835-L842`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L835-L842)).

### StateResponse

- Fewer than three tokens fails with `InvalidFormat`; tokens after the fourth are ignored ([`types.rs#L398-L412`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L398-L412)).

The CLI builds such a value only in memory ([`command.rs#L618-L626`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/pull/command.rs#L618-L626)).
- A parse failure surfaces as the protocol error `Failed to parse state response: {error}` ([`queries.rs#L53-L55`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/queries.rs#L53-L55)), whose `{error}` is `empty state response`, `invalid state format: '{body}'` or `invalid position: '{value}'` ([`types.rs#L494-L502`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L494-L502)).
- The sync engine treats matching `set_id` strings as "in sync" and skips the changelist ([`sync.rs#L640-L656`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/sync.rs#L640-L656)), and compares `merkle` with its cached state as strings ([`sync.rs#L535-L546`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/sync.rs#L535-L546)).

**Examples** (from the tests). `42 ABC123 DEF456` is position 42, merkle `ABC123`, tag merkle `DEF456` ([`types.rs#L882-L898`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L882-L898)). `42 ABC DEF SID32` adds the SetId `SID32` ([`types.rs#L937-L953`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L937-L953)). `-` is the empty view ([`types.rs#L900-L904`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L900-L904)).

| 6 | `set_id` | optional string | **Optional** | The [SetId](#setid) of the view's effective change set; absent from older servers ([`types.rs#L613-L617`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L613-L617), [`types.rs#L687-L692`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L687-L692)). Not checked as base32. |

**Parsing rules:**

- Both parsers trim the line, split it on tab, and trim each field ([`types.rs#L632-L638`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L632-L638), [`types.rs#L669-L676`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L669-L676)). Trimming the line removes trailing tabs, so a six-field row with an empty last field becomes five fields. A five-field row with an empty `state`, such as `fresh\tshared\t-\t0\t`, becomes four fields and the strict parser refuses it with `expected 5 or 6 tab-separated fields, got 4` ([`types.rs#L633-L644`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L633-L644)). An empty `state` survives only when a non-empty `set_id` follows it. One such row fails the whole `list_view_refs` call, losing the inventory for every view ([`bare.rs#L46-L58`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/bare.rs#L46-L58)), so `atomic view list --remote` fails ([`list.rs#L480-L483`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/view/list.rs#L480-L483)), and pull and clone silently skip their SetId check ([`services_sync_remote.rs#L1592-L1597`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1592-L1597), [`command.rs#L506-L510`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/clone/command.rs#L506-L510)).
- Strict: an empty line fails with `row is empty`, and a row that does not have five or six fields fails with `expected 5 or 6 tab-separated fields, got {n}` ([`types.rs#L633-L644`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L633-L644)). It does not check `parent`, `state` or `set_id` ([`types.rs#L645-L655`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L645-L655)).
- Lenient: returns nothing for a blank line or one without a non-empty `name` and `scope` ([`types.rs#L665-L679`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L665-L679)). Fields after the sixth are ignored ([`types.rs#L674-L687`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/types.rs#L674-L687)). The comment says this lets an older server's JSON answer to `?views` parse as an empty list ([`queries.rs#L385-L388`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/queries.rs#L385-L388)).
- After a pull, the CLI and the daemon find the row whose `name` equals the remote view's name and compare its `set_id` with the local view's SetId text as strings ([`command.rs#L856-L864`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/pull/command.rs#L856-L864), [`services_sync_remote.rs#L1592-L1608`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L1592-L1608)). A row with no `set_id` skips the check ([`command.rs#L877`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/pull/command.rs#L877)).

### ChunkManifestEntry

- **SetId domain.** The SetId comment requires producers to fold exactly change and tag hashes ([`set_id.rs#L57-L71`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/set_id.rs#L57-L71)). The sync engine folds whatever local hash set it is given ([`sync.rs#L467-L486`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/sync.rs#L467-L486)), and the daemon folds a snapshot's `own_set_id` from the view's change log ([`services_sync_remote.rs#L348-L354`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_sync_remote.rs#L348-L354)). The sync engine's caller passes the local change hashes ([`sync.rs#L632-L634`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/sync.rs#L632-L634)). Whether the server's advertised SetId includes tag hashes, and so whether a client's change-only set can ever match it, is not visible.
- **View names.** Neither the CLI's nor the daemon's rules refuse tab, newline, `&`, `#`, `%`, `+` or `=` ([`new.rs#L76`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/view/new.rs#L76), [`services_query.rs#L1147-L1167`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_query.rs#L1147-L1167)), and the client does not percent-encode view names in query strings ([`queries.rs#L30`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-remote/src/http/queries.rs#L30)). A name containing a tab or newline would break inventory rows and manifest headers, and one containing `&` or `#` would change the query string. How the server handles such names is not stated. The two rule sets also disagree on the maximum length, 255 bytes against 100 ([`new.rs#L72-L73`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-cli/src/commands/view/new.rs#L72-L73), [`services_query.rs#L1154-L1159`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/libatomic/src/daemon/services_query.rs#L1154-L1159)).
- **What a draft snapshot holds.** The producers copy a view's stored log into `own_changes` and fold `own_set_id` from it. Comments disagree on whether a draft's log includes the inherited prefix; the question is kept once, under [Open questions](endpoints/project.md#open-questions) on project.md, and the code's behaviour is on [ViewSnapshot](endpoints/project.md#viewsnapshot).
- **Object key encoding.** Which key check the server applies to each object family is kept once, under [Open questions](endpoints/project.md#open-questions) on project.md; the per-family keys are on [ObjectRecord](endpoints/project.md#objectrecord).
- **Layer selection on the server.** What the server includes for a [Layer](#layer) selection, and what it does with an empty `layers=` value, is kept once, under [Open questions](endpoints/project.md#open-questions) on project.md.
- **Chunk negotiation.** [ChunkManifestEntry](#chunkmanifestentry) values would be exchanged by a chunk-level have/need negotiation that no request implements; that question is kept once, under [Open questions](transport.md#open-questions) on transport.md.
- **Position text.** The base32 `Position` form is defined in atomic-core ([`position.rs#L160-L207`](https://github.com/atomicdotdev/atomic/blob/a6c3e359456e83cf5a967a2e8265f11e0ba45d80/atomic-core/src/types/position.rs#L160-L207)), but no caller in `atomic-remote`, `atomic-cli`, `libatomic` or `atomic-repository` was found. It is documented in case a server response uses it.
